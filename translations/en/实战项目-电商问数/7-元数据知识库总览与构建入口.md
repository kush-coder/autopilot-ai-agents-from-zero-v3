## 1. Why Build the Metadata Knowledge Base First

This point has actually already been foreshadowed in Chapters 1 and 2. Before the data Q&A agent can actually generate SQL, it must first have a retrievable, organizable, and reusable knowledge foundation. Otherwise, it will later have difficulty reliably completing the following actions:

- Finding which tables and fields to query
- Understanding the business meaning and modeling role of fields
- Identifying field values mentioned in user questions
- Mapping business metrics to underlying fields

Therefore, from an engineering implementation perspective, the metadata knowledge base is not an "add-on capability" but rather a prerequisite for the data Q&A agent to work reliably.

The metadata here mainly includes four categories: table information, field information, field values, and metric information. Once this content is stored in a structured way and both vector indexes and full-text indexes are established, the subsequent agent can truly achieve: **understand the context first, then generate.**

## 2. Metadata Knowledge Base Entry Point Overview

An important design idea in this chapter is: **do not rush to implement all business details, but first set up the script entry point, execution method, and call chain clearly.** Because if the script itself cannot run reliably, then no matter how much business logic is written later, it will not be able to run.

### 2.1 Code Structure Directory Overview

The logic for building the metadata knowledge base is not simple. It involves at least: reading configuration files, writing to the metadata database, reading from the data warehouse, writing to the vector database, and writing to the full-text index.

If all of this logic were crammed into a single `build()` function, that function would quickly become long and messy, making it difficult to maintain and explain later.

Therefore, the project adopts a very classic layered approach. If you have done conventional backend development, you can map it to the following structure:

- `controller`: receives requests and serves as the entry point
- `service`: organizes business processes
- `repository`: handles specific storage reads and writes

In this project, although what we are writing is not an HTTP API but a script, this analogy still works well:

- `scripts` can be analogized to `controller`
- `services` is responsible for core business logic
- `repositories` is responsible for interacting with `MySQL / Qdrant / Elasticsearch`

You can understand it this way:

- In an API program, `controller` receives HTTP parameters
- In this script, `scripts` receives command-line arguments

Both are essentially "program entry points."

If we further map the "build metadata knowledge base" component to the current project directory, its core code structure is roughly as follows:

### 2.2 Distinguishing the Four Types of Roles: Configuration Files, Business Entities, ORM Models, and Mappers

#### 2.2.1 Role Overview

When you get to this point, many students will have a series of very natural questions:

- Since there are already configuration files, why do we still need business entities?
- Since the final step is writing to the database, why not just use ORM models directly?
- The directories `entities`, `models`, and `mappers` all seem related to "tables, fields, and metrics." What exactly are the differences between them?

These are excellent questions, because when Chapter 8 actually expands on the code, the main thread is essentially about the flow among these four types of roles. You can first view them in the following four layers.

![Code directory structure of the four types of roles](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/7/7-2-1-1.png)

**Type 1: Configuration files**

Configuration files are "external inputs" that tell the program: **what to process this time.**

In this project, they correspond to:

- `conf/meta_config.yaml`

They are mainly responsible for describing:

- Which tables to sync
- Which fields each table has
- What the roles, descriptions, and aliases of the fields are
- Which fields also need to sync real values later
- Which metrics need to go into the knowledge base

So a configuration file is more like a "task specification" or "sync checklist." But it is not yet the most core object when the program actually does its work internally, because it typically only describes **business semantics and sync scope**, and does not necessarily include complete runtime information.

For example, the field type `type` may not be written in the configuration, and the field's sample value `examples` may also not be written in the configuration. This information often needs to be queried and filled in from the `DW` database at runtime.

**Type 2: Business entities**

Business entities are "data objects that flow uniformly within the program," telling the system: **how I intend to represent these tables, fields, and metrics internally.**

In this project, they correspond to:

- `app/entities/table_info.py`
- `app/entities/column_info.py`
- `app/entities/metric_info.py`
- `app/entities/column_metric.py`

You can think of business entities as the system's internal "standard parts."

Their role is to organize information from different sources into a structure that the rest of the system can reuse. For example: part of the information comes from configuration files; part comes from data warehouse queries; later it may also be used to write to MySQL, Qdrant, or Elasticsearch.

Therefore, the focus of business entities is not "how to store in the database," but rather: **how the system internally represents a table, a field, and a metric in a unified way.**

If you have done frontend development, you can think of them as DTOs / domain objects that actually exist at runtime. They are a bit like type definitions in TypeScript, but they are not just static type hints; they are Python objects that really get created at program runtime.

For example, later in the code, this will actually be created:

```python
table_info = TableInfo(
    id="fact_order",
    name="fact_order",
    role="fact",
    description="订单事实表",
)
```

This `table_info` is not just a type annotation for the editor to see; it is an object that actually exists at runtime.

**Type 3: ORM models**

ORM models are "database mapping objects" that tell the ORM framework: **how these Python classes map to tables and columns in the database.**

In this project, they correspond to:

- `app/models/table_info_mysql.py`
- `app/models/column_info_mysql.py`
- `app/models/metric_info_mysql.py`
- `app/models/column_metric_mysql.py`

Their focus is: what this database table is called, how these fields map to Python attributes, and how the ORM should perform inserts, queries, and updates. So ORM models lean more toward "database-facing" rather than "business-semantics-facing."

In other words: business entities care about "how the system expresses things internally," while ORM models care about "how database table structures are mapped." These two objects may look similar in terms of fields, but their responsibilities are completely different.

**Type 4: Mappers**

`mappers` is neither a new business object nor a new database model. It is essentially just a **translation layer**.

In this project, they correspond to:

- `app/repositories/mysql/meta/mappers/table_info_mapper.py`
- `app/repositories/mysql/meta/mappers/column_info_mapper.py`
- `app/repositories/mysql/meta/mappers/metric_info_mapper.py`
- `app/repositories/mysql/meta/mappers/column_metric_mapper.py`

The problem they solve is this: the `service` layer is better suited to handling business entities, while the `repository` layer needs ORM models when persisting to the database. So someone in the middle must be responsible for the conversion, and that someone is `mapper`.

Essentially, they are:

- A translator between `TableInfo` <-> `TableInfoMySQL`
- A translator between `ColumnInfo` <-> `ColumnInfoMySQL`

Their responsibility is not to "define new data," but rather: **convert business entities into ORM models, or convert ORM models back into business entities.**

If we look at these four types of roles together, they can be summarized as follows:

- Configuration files: decide "what to sync this time"
- Business entities: decide "how the system internally represents this data in a unified way"
- ORM models: decide "how this data maps to database tables"
- `mappers`: responsible for converting between business entities and ORM models

#### 2.2.2 Role Relationships and Call Chain

The real chain you will see later in Chapter 8 can actually be abstracted as follows:

```text
meta_config.yaml
  -> MetaConfig
  -> TableInfo / ColumnInfo / MetricInfo
  -> Mapper 转换
  -> TableInfoMySQL / ColumnInfoMySQL / MetricInfoMySQL
  -> Meta MySQL
```

If we also clarify "who calls whom," it can be viewed as the following business chain:

1. The script entry point `build_meta_knowledge.py` starts the process.
2. `MetaKnowledgeService.build(config_path)` reads the configuration file.
3. `OmegaConf` parses the configuration file into a configuration object `MetaConfig` in the program.
4. The `service` layer constructs business entities such as `TableInfo` and `ColumnInfo` based on `MetaConfig`.
5. During the construction of business entities, `service` calls `DWMySQLRepository` to query the data warehouse and fill in the real field types and sample values.
6. Once the business entities are ready, `service` calls `MetaMySQLRepository` to persist them.
7. `MetaMySQLRepository` does not directly require the upper layer to pass ORM models. Instead, it first calls `mapper` to convert business entities into ORM models.
8. Finally, the ORM models write to `Meta MySQL` through methods such as `session.add_all()`.

In this chain, the call relationship at each layer is actually very clear:

- `script` calls `service`
- `service` calls `repository`
- `repository` calls `mapper`
- `mapper` is responsible for object conversion
- ORM models ultimately participate in database reads and writes

In other words, `mapper` is not a role that independently initiates business logic. It is more like a translator sandwiched inside `repository`.

#### 2.2.3 Minimal Example

Suppose the configuration file contains a table like this:

```yaml
tables:
  - name: fact_order
    role: fact
    description: 订单事实表
    columns:
      - name: order_amount
        role: measure
        description: 订单金额
        alias: ["销售额", "成交金额"]
```

Then roughly the following things will happen later:

1. First, read from the configuration:
   `fact_order`, `order_amount`, `measure`, `订单金额`, `销售额`
2. Then query from `DW`:
   the actual type of `order_amount`, such as `float`
3. Then assemble the business entity at the `service` layer:

```python
ColumnInfo(
    id="fact_order.order_amount",
    name="order_amount",
    type="float",
    role="measure",
    examples=[...],
    description="订单金额",
    alias=["销售额", "成交金额"],
    table_id="fact_order",
)
```

4. At the `repository` layer, convert it into `ColumnInfoMySQL` through `ColumnInfoMapper`
5. Finally, the ORM writes `ColumnInfoMySQL` into the `column_info` table

This makes the picture very clear:

- The configuration file provides the starting point
- The business entity carries the internal system representation
- `mapper` completes the object translation
- The ORM model completes the database mapping

If you thoroughly understand this section first, then when you look at Chapter 8 later, you will find that chapter is really just expanding this chain into concrete code.

### 2.3 Explanation of the Synchronization Script

First, get a clear picture of the overall flow of this chain. This script does not just handle "loading into the database"; it orchestrates an entire knowledge construction process.

Overall, it needs to complete 5 steps:

1. Read the configuration file
2. Write the specified table information and field information into `Meta MySQL`
3. Create vector indexes for field information and write them into `Qdrant`
4. Create full-text indexes for field values that need synchronization and write them into `Elasticsearch`
5. Write metric information and metric-field relationships into `Meta MySQL`, and create vector indexes for the metrics

If you map this chain to different storage systems, you get the following summary table:

| Storage Component        | What It Mainly Stores                               | Role in This Project       |
| --------------- | ---------------------------------------- | -------------------- |
| `MySQL`         | Table information, field information, metric information, field-metric relationships | Stores structured metadata     |
| `Qdrant`        | Field vectors, metric vectors                       | Supports semantic retrieval         |
| `Elasticsearch` | Actual field values                             | Supports keyword and value-range retrieval |

Therefore, the term "metadata knowledge base" in Shopkeeper Data Q&A does not refer to a single database, but to an entire knowledge organization scheme that serves data querying.

First, let's look at the entry point of the synchronization script itself. The script path in the project is: `shopkeeper-agent/app/scripts/build_meta_knowledge.py`

This script itself does not carry complex business details; it is more like a general dispatcher, mainly responsible for:

- Initializing the client
- Creating repository objects
- Creating service objects
- Calling the service layer's `build(config_path)`
- Closing the connection at the end

That is to say, the role of the "synchronization script" is more accurately described as **orchestrating the entire metadata knowledge base construction chain**, rather than directly writing all the construction details into the script.
The actual main workflow for building the metadata knowledge base is located in: `shopkeeper-agent/app/services/meta_knowledge_service.py`

This is a very typical engineering habit that is worth developing early on: **the entry point only handles orchestration, while complex business logic is pushed down to the service layer.**

If you want to get a little closer to the code, you can look at the orchestration skeleton of `MetaKnowledgeService.build(...)`. Leaving out the details for now, its main flow generally looks like this:

Corresponding file path in the project: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def build(self, config_path: Path):
    # 1. 读取并解析配置
    context = OmegaConf.load(config_path)
    schema = OmegaConf.structured(MetaConfig)
    meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))

    # 2. 处理表和字段
    if meta_config.tables:
        column_infos = await self._save_tables_to_meta_db(meta_config)
        await self._save_column_info_to_qdrant(column_infos)
        await self._save_value_info_to_es(meta_config, column_infos)

    # 3. 处理指标
    if meta_config.metrics:
        metric_infos = await self._save_metrics_to_meta_db(meta_config)
        await self._save_metric_info_to_qdrant(metric_infos)
```

This code is very much worth getting an overall impression of first, because later Chapters 8 through 10 are essentially expanding these few lines of flow section by section.

## 3. Why Make It "Configuration-Driven"

This is one of the most important design ideas in this chapter. First, let's clarify what "configuration-driven" means here. It does not simply mean "the project has both a script and a configuration file"; rather, it means: **the script itself does not hardcode the business scope; instead, the configuration file determines what content will be synchronized this time.**

The script handles "how to do it," and the configuration handles "what content to do." In Shopkeeper Data Q&A, specifically, the configuration file determines:

- Which tables to synchronize
- Which fields in each table should be included in the metadata knowledge base
- Which fields need their actual values synchronized to `Elasticsearch`
- Which metrics should be included in the knowledge base
- Which fields each metric is related to

So the "configuration-driven" approach mentioned here essentially means: **it is not the code that determines what to synchronize, but the configuration that determines what to synchronize.**

Many people initially think: "Since I want to synchronize data warehouse metadata, wouldn't it be enough to just scan all the tables?"

Theoretically, yes, but in engineering practice this is usually not done, for at least three reasons.

1. **Not all tables are worth synchronizing**

A real data warehouse often contains many tables: intermediate tables, temporary tables, deprecated tables, and technical tables that only serve some offline task. Even if these tables really exist, they are not necessarily suitable for exposure to the data query system. The query assistant really only cares about a small subset of tables that are "business-meaningful, suitable for querying, and suitable for explanation."

2. **Data warehouse content will inevitably change incrementally in the future**

The data warehouse may have `100` tables today, and `10` more may be added tomorrow. If the construction logic is completely hardcoded, every new table would require code changes, and maintenance costs would keep rising.

A more reasonable approach is: the code handles "how to synchronize," and the configuration handles "what to synchronize." This way, when a new table goes live, you only need to change the configuration, not the core logic.

3. **Whether a field's actual values should be synchronized should also be configurable**

Not every field needs to have its actual values synchronized to `Elasticsearch`.

For example, fields like `province`, `region_name`, `member_level` are values users are likely to state directly in natural language, so they are suitable for synchronizing field values and building full-text indexes.

But technical identifier fields like `order_id`, `customer_id`, `product_id` generally do not need to have all their values written into `Elasticsearch`.

Therefore, whether to synchronize field values should also be controlled by configuration. This is why the project specifically designs a `YAML` configuration file as input to the synchronization script.

## 4. Python Script Execution Methods and Module Imports

Although this section is placed in the metadata knowledge base chapter, it is essentially about a more general Python question: **how should modules within a package be executed, and why does running a file directly often cause `No module named app`.**

This problem does not only occur in the synchronization script; it also occurs in other debug files placed under the `app/` package. The core point can be summed up in one sentence:

**In a package-structured project, do not run `app/.../*.py` directly as a standalone file; instead, execute it as a module.**

### 4.1 Typical Symptom: Why the Error Occurs

If you execute the following directly in the project root directory:

```bash
python3 app/scripts/build_meta_knowledge.py
```

You will likely see an error similar to:

```text
Traceback (most recent call last):
  File ".../app/scripts/build_meta_knowledge.py", line 8, in <module>
    from app.core.log import logger
ModuleNotFoundError: No module named 'app'
```

That is to say, if the synchronization script itself is run as a "normal file" instead of as a module, it will encounter the same kind of problem. As long as the file uses this kind of absolute import:

```python
from app.core.log import logger
```

the same kind of problem may arise.

### 4.2 Root Cause: The Interpreter Looks for Modules Based on sys.path

To understand this problem, just focus on `sys.path`. It is essentially: **a list of paths that Python uses to search for modules after startup.**

When you directly execute:

```bash
python3 app/scripts/build_meta_knowledge.py
```

the interpreter is more likely to put the script's directory `app/scripts/` into the module search path. But what we really want it to recognize is the project root directory `shopkeeper-agent/`, because the `app` package is located under that.

The following diagram can help you intuitively see this path relationship: when executing a script file directly, the interpreter is more likely to start looking for modules from `app/scripts/`, rather than from the project root directory.

![When directly executing build_meta_knowledge.py, the interpreter tends to look for modules starting from app/scripts/, while the app package is actually located under the project root directory](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/7/7-4-2-1.png)

So the problem becomes: the interpreter starts looking for modules from `app/scripts/`; but there is no upper-level package called `app` under this directory; so an absolute import like `from app...` fails.

That is to say, in many cases it is not that the code is wrong, but rather that **the startup method is incorrect**.

### 4.3 Recommended Approach: Run as a Module

In a package-structured project, the more recommended approach is: **run the module within the package using `python -m` from the project root directory.**

For example:

```bash
uv run python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

Two things to remember here:

- `-m` means running as a module
- The current working directory must be one level above the `app` package, that is, the backend project root directory

This way, the interpreter will more naturally treat the current directory as the starting point for module search, thereby correctly finding the `app` package.

### 4.4 python -m, uv run, and PYTHONPATH

These three things are easy to confuse, but each actually handles a different concern:

- `python -m ...`: solves "how modules are found"
- `uv run ...`: solves "which Python and which set of dependencies to use"
- `PYTHONPATH`: manually adds a directory to the module search path

So the real key to solving the `No module named 'app'` problem is `-m` and the current working directory, not `uv run` itself.

`PYTHONPATH` can of course also solve the problem, for example:

```bash
export PYTHONPATH=$(pwd)
python3 app/clients/qdrant_client_manager.py
```

But it is more suitable for temporary debugging and not suitable as a long-term unified execution convention for the team.  
Therefore, in the current project, the most recommended approach is still:

```bash
uv run python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

### 4.5 Why PyCharm Can Run It

This is because the IDE often adds extra run configuration for you, such as working directory, content root, environment variables, and interpreter selection, all of which affect the module search path after Python starts.

Therefore:

- The fact that `PyCharm` can run it does not mean the command syntax is the most reliable
- A terminal error does not mean the code itself is wrong

From the perspective of team collaboration and deployment, a more reliable approach is still to fix the execution command in the terminal.

## 5. Script Argument Parsing: How to Use argparse

Now that the script execution method is clear, the next practical problem is: **after the script starts, how does it know which configuration file to read this time?**

The answer is: pass the configuration file path through command-line arguments. In the current project, this argument is:

```bash
-c conf/meta_config.yaml
# 或者
--conf conf/meta_config.yaml
```

### 5.1 What Are Command-Line Arguments

Command-line arguments are the extra information you pass to a program when executing it.

For example, in this command:

```bash
uv run python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

The actual "arguments" are:

- `-c`
- `conf/meta_config.yaml`

Together they mean: **pass the configuration file path to the script.** In this project, this step is crucial because the synchronization script does not hardcode "which tables and metrics to synchronize"; instead, the configuration file determines the synchronization scope. That is to say, the script itself handles "how to build," while the configuration file handles "what to build."

### 5.2 Introduction to argparse

Official documentation: https://docs.python.org/zh-cn/3.13/library/argparse.html

The `argparse` module in the Python standard library is specifically designed for parsing command-line arguments.

According to the official Python documentation, it is a **parser for command-line options, arguments and subcommands**. To put it in simpler terms: **the program first declares which arguments it supports, and then `argparse` is responsible for parsing the input from the command line.**

This is also why in real projects, it is generally not recommended to directly use `sys.argv[1]` or `sys.argv[2]` to hard-code value retrieval. Because as soon as the arguments become slightly more complex, you will run into these problems:

Here is a quick explanation of what these two notations mean.  
`sys.argv` is the list Python uses to store command-line arguments. For example, when you run:

```bash
python demo.py hello world
```

Then:

```python
import sys
print(sys.argv)
```

You usually get:

```python
['demo.py', 'hello', 'world']
```

At this point:

- `sys.argv[0]` is the script name `demo.py`
- `sys.argv[1]` is the first argument `hello`
- `sys.argv[2]` is the second argument `world`

In other words, `sys.argv[1]` and `sys.argv[2]` are essentially a way of "hard-retrieving command-line arguments by position." It works in extremely simple scripts, but as soon as the argument order changes, more arguments are added, or you need to support optional arguments like `-c` or `--conf`, it becomes increasingly fragile.

- The argument order may change
- Some arguments may be optional
- Argument names and values need to be recognized as pairs
- When users enter something wrong, the program should automatically show the correct usage

And `argparse` is specifically designed for these scenarios.

### 5.3 The Most Common 4-Step Pattern

For beginners, the most common usage of `argparse` actually comes down to 4 steps:

```python
from argparse import ArgumentParser

parser = ArgumentParser()
parser.add_argument("-c", "--conf")
args = parser.parse_args()
print(args.conf)
```

What do these 4 steps do?

1. `ArgumentParser()`: Create an argument parser
2. `add_argument("-c", "--conf")`: Declare that the script supports both `-c` and `--conf`
3. `parse_args()`: Actually start parsing the command-line input
4. `args.conf`: Retrieve the argument values from the parsing result

There are two very important beginner concepts here.

First, `-c` and `--conf` are two ways of writing the same argument:

- `-c` is the short form, which is faster to type
- `--conf` is the long form, which is more readable

Second, what `parse_args()` returns is not a dictionary, but a `Namespace` object.  
So we usually retrieve values through attributes, for example:

```python
args.conf
```

### 5.4 Common argparse Capabilities

Based on the official documentation, the following points are the most worth mastering at the beginner stage.

#### 5.4.1 Automatically Generate Help Information

By default, `ArgumentParser` automatically adds `-h/--help` to the script.

For example, if you run:

```bash
uv run python -m app.scripts.build_meta_knowledge -h
```

It will automatically output the script's usage instructions. This is also one of the reasons why `argparse` is more suitable for real projects than manually writing `sys.argv`.

#### 5.4.2 Distinguish Between Positional and Optional Arguments

The official documentation specifically emphasizes two common types of arguments:

- Positional arguments: identified directly by position, for example `filename`
- Optional arguments: prefixed with `-` or `--`, for example `-c`, `--conf`

The current project uses **optional arguments**, because:

- They are more readable
- The order is more flexible
- They are better suited for adding more arguments later

#### 5.4.3 Add Descriptions to Arguments

If you want to make the help information friendlier, the most common approach is to add `help=` to arguments.

For example:

```python
parser.add_argument(
    "-c",
    "--conf",
    help="meta_config.yaml 的路径",
)
```

This way, when users run `-h`, they can see what this argument does.

#### 5.4.4 Specify Default Values or Required Constraints

In the official documentation, the two most commonly used argument configurations are:

- `default=`: Use the default value when not provided
- `required=True`: Require the user to provide this argument

For example, a more complete version could be:

```python
parser.add_argument(
    "-c",
    "--conf",
    required=True,
    help="meta_config.yaml 的路径",
)
```

This means: if the user does not pass `-c/--conf`, the program will directly report an error and show the correct usage.

### 5.5 Back to the Current Project: What Argument Parsing Does

The argument parsing code in the current project script is:

```python
if __name__ == "__main__":
    parser = ArgumentParser()
    parser.add_argument("-c", "--conf")
    args = parser.parse_args()

    config_path = Path(args.conf)
    asyncio.run(build(config_path))
```

Translating it into plain language, it is essentially:

1. First declare: this script supports one configuration argument `-c/--conf`
2. Then parse that argument from the command line
3. Get the configuration file path
4. Pass this path to `build(config_path)`

So when you run:

```bash
uv run python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

The key input the program ultimately gets is:

```python
args.conf == "conf/meta_config.yaml"
```

Which is then further converted into:

```python
Path("conf/meta_config.yaml")
```

The service layer then loads the configuration file based on this path.

### 5.6 Why Convert to Path

Compared with passing the path around as an ordinary string, converting it into a `Path` object has at least two benefits: the semantics are clearer—others can immediately tell that this is a path, not ordinary text—and it is more convenient for subsequent joining, existence checks, and file reading.

So although this is just a small move, it reflects a good coding habit.

### 5.7 Section Summary

1. Command-line arguments are extra information passed into the program from the terminal at startup.
2. The core flow of `argparse` is: create the parser, declare arguments, parse arguments, and read results.
3. `-c/--conf` is the key argument through which the script actually puts "configuration-driven" into practice at the command-line entry point.
4. In the current project, what the script ultimately gets is the configuration file path, converts it into a `Path`, and passes it to `build(config_path)`.

## 6. Quick Overview of Core Files

In this part, the following core files and directories are the most worth reading first:

- `conf/meta_config.yaml`: Configuration file that determines "what to sync"—which tables, fields, and metrics should be synced this time
- `app/conf/meta_config.py`: Configuration structure definition file that determines how the configuration should be represented in the program

- `app/services/meta_knowledge_service.py`: Core service layer file containing the core business logic, determining "how exactly to build"—responsible for reading the configuration and organizing the metadata building logic

- `app/repositories/...`: Repository layer, responsible for interacting with underlying storage such as MySQL, Qdrant, and Elasticsearch
- `app/entities/...`: Business entity layer, responsible for uniformly representing core objects such as tables, fields, metrics, and values

### 6.1 meta_config.yaml: Configuration File

It is a configuration file for humans to read, essentially a "sync checklist" that declares:

- Which tables should enter the knowledge base
- Which fields in each table are worth syncing
- Which fields need their actual values synced to `Elasticsearch`
- Which metrics should enter the knowledge base
- Which fields each metric is related to

In other words, what it determines is the **sync scope**.

### 6.2 meta_config.py: Configuration Structure Definition

It is the configuration structure for the program to read. In other words, `meta_config.yaml` is YAML text, and the program cannot directly use it as a business object;  
so we need to define a set of structures in Python so that the program knows:

- What type `tables` should be
- What fields each element in `columns` should have
- What fields each element in `metrics` should have

In other words, what it determines is **how the configuration file should be represented in the program**.

In this build pipeline, it is imported and used by `app/services/meta_knowledge_service.py`:

```python
from app.conf.meta_config import MetaConfig
```

Then, together with `OmegaConf`, it converts `meta_config.yaml` into a `MetaConfig` object that can be directly accessed in the program.

### 6.3 build_meta_knowledge.py: Sync Script Entry

It is the entry script for the entire build process.

This layer is mainly responsible for:

- Receiving command-line arguments
- Initializing clients
- Creating repository objects
- Creating service objects
- Calling `MetaKnowledgeService.build(config_path)`

In other words, what it determines is **where to enter this build pipeline**.

### 6.4 meta_knowledge_service.py: Core Business Logic

The actual build logic is not written in the script entry, but in the service layer.

This layer is mainly responsible for:

- Reading the configuration file
- Determining based on the configuration whether to process `tables` or `metrics` first
- Calling the repository to read from the data warehouse, write to the metadata database, and build indexes

In other words, what it determines is **how exactly to build**.

### 6.5 The Role of app/models

As you have already seen, the project contains both:

- `app/models/...`
- `app/entities/...`
- `app/repositories/mysql/meta/mappers/...`

They all appear to be related to "tables, fields, and metrics," but their responsibilities are different.

The `app/models` layer contains the ORM models.  
Its role is to map the tables in the metadata database into Python classes that SQLAlchemy can read and write directly.

Earlier in `2.2`, we already clarified the responsibilities of these four roles: "configuration file, business entities, ORM models, and mappers."
There is no need to repeat the definitions here; I will only add one point that is directly related to the current directory structure:

- `models`: Database-oriented, responsible for table structure mapping
- `entities`: Business-oriented, responsible for uniformly representing core internal objects
- `mappers`: Responsible for converting between ORM models and business entities

So the coexistence of `app/models/column_info.py` and `app/entities/column_info.py` here is not a duplicate design, but because they are solving problems at two different levels.

### 6.6 Repository Layer Division of Labor

After understanding `models`, looking at the `repository` layer will be much smoother.

The core role of this layer can be remembered in one sentence: **the service organizes the process, and the repository executes the specific reads and writes.**

In other words, the service layer should not directly hold `session` ("a session object between the program and the database," which is used when actually executing queries, writes, and transaction commits) and scatter database operations everywhere; instead, these operations should be consolidated into the repository.  
The benefit of doing this is clear: the service layer can focus on "what to do first and what to do next"; storage read/write logic does not get scattered across various business functions; and later, if the SQL, ORM, or index writing methods change, the scope of adjustments will be more concentrated.

In the current project, the repository is not just a single layer "divided by technology stack," but is further split by data source and storage target.

Let us first look at the MySQL layer:

- `app/repositories/mysql/meta/`: Oriented toward the metadata database, responsible for writing and querying the system's own metadata tables
- `app/repositories/mysql/dw/`: Oriented toward the data warehouse, responsible for querying table structures, field types, and field values in the data warehouse

This is also why the project has two MySQL repositories at the same time:

- `MetaMySQLRepository`: Responsible for interacting with the metadata database
- `DWMySQLRepository`: Responsible for interacting with the data warehouse

Although both are based on MySQL, their responsibilities are different.

For example:

- `MetaMySQLRepository` is more like "writing to your own business database," responsible for saving table information, field information, and metric information, as well as reading certain metadata that has already been stored
- `DWMySQLRepository` is more like "reading an external data source," responsible for querying field types, field example values, or later performing SQL validation-related operations

In addition to MySQL, you'll also see the following later:

- `app/repositories/qdrant/`: responsible for reading and writing field vectors and metric vectors
- `app/repositories/es/`: responsible for writing and querying full-text indexes of field values

So the division of responsibilities in the repository layer can be summarized into two levels:

- First, split by underlying storage type: MySQL, Qdrant, Elasticsearch
- Then, split by specific responsibilities: for example, under MySQL, further divided into `meta` and `dw`

In this chapter, it's enough to clearly understand the responsibility boundaries of the repository. In later chapters, we'll dive into the specific implementations of `MetaMySQLRepository`, `DWMySQLRepository`, and other repositories separately.

At this point, you can grasp the most important sentence: **the configuration file determines "what to sync," the entry script determines "where to enter from," the service layer determines "how specifically to do it," `mappers` is responsible for object conversion, and the ORM models are responsible for "how to map to database tables."**

## 7. Detailed Explanation of meta_config.yaml

Let's start with the configuration file itself. Before actually writing Python code, it's more important to first clarify: **what this configuration file should actually look like.**

Corresponding project file path: `shopkeeper-agent/conf/meta_config.yaml`

This configuration file uses YAML format to specify information about the tables and metrics to be synced. First, let's look at its structural template:

```yaml
tables: # 表信息
  - name: <table_name> # 真实表名
    role: dim | fact # 表角色
    description: <table_description> # 表的业务含义说明
    columns:
      - name: <column_name> # 真实字段名
        role: primary_key | foreign_key | dimension | measure # 字段角色
        description: <column_description> # 字段的业务含义
        alias: [<alias1>, <alias2>] # 字段同义词
        sync: true | false # 该字段取值是否需要同步到 ES 建立全文索引

metrics: # 指标信息
  - name: <metric_name> # 指标名称，如 GMV、AOV
    description: <metric_description> # 指标的业务含义与计算口径说明
    relevant_columns: [<table_name.column_name>] # 指标相关字段
    alias: [<alias1>, <alias2>] # 指标同义词
```

In the current simulated data warehouse environment, there are a total of 5 tables and 2 metrics that need to be synced to the metadata knowledge base. The following YAML is a specific configuration example:

```yaml
tables:
  - name: dim_region
    role: dim
    description: 地区维度表，用于描述订单发生的地理区域信息。
    columns:
      - name: province
        role: dimension
        description: 订单所属的省份名称。
        alias: [省份, 省, 所在省份]
        sync: true

metrics:
  - name: GMV
    description: 全称 Gross Merchandise Value，表示所有订单的成交金额总和。
    relevant_columns:
      - fact_order.order_amount
    alias: [成交总额, 订单总额]
```

### 7.1 Top-Level Structure: tables and metrics

This point is important.

The sync content is first divided into two major categories:

- `tables`: describes the tables and fields to be synced
- `metrics`: describes the metrics to be synced

In this way, the service layer can later directly write judgments like this:

```python
if meta_config.tables:
    # 处理表和字段

if meta_config.metrics:
    # 处理指标
```

That is to say, the top-level structure of the configuration file itself corresponds to two processing branches in the service layer.

### 7.2 tables: Table Configuration Structure

`tables` is a list, and each element in the list represents a table to be synced.

Each table contains at least the following information:

- `name`: table name
- `role`: whether this table is a dimension table or a fact table
- `description`: the business meaning of this table
- `columns`: which fields under this table should enter the knowledge base

The `role` here is also crucial:

- `dim`: dimension table
- `fact`: fact table

It is not just an explanation written for humans to read, but information that will be used later when the agent understands the data warehouse structure.

### 7.3 columns: Field Configuration Structure

`columns` is also a list, and each element inside represents a field.

Each field mainly has 5 configurations:

- `name`: field name
- `role`: field role
- `description`: field business meaning
- `alias`: field alias
- `sync`: whether to sync actual values to `Elasticsearch`

Field-level `role` generally includes the following:

- `primary_key`
- `foreign_key`
- `dimension`
- `measure`

The `alias` here is very important, because when users ask questions, they often don't directly use the actual field names but rather business colloquialisms.  
For example, the alias of `order_amount` can be: `销售额`, `订单金额`, `收入`.

This makes it easier to align natural language with actual fields later during retrieval.

### 7.4 sync: Field Value Sync Switch

`sync` is one of the most easily overlooked but very critical fields in this configuration file.

- `sync: true`: indicates that the actual values of this field need to be synced to `Elasticsearch`
- `sync: false`: indicates that only field metadata is kept, and actual values are not synced

Note that what it controls is not "whether this field should enter the knowledge base," but: **whether to additionally build a full-text index of field values for this field.**

That is to say, all fields appearing in the configuration will enter the system as field metadata; only those fields with `sync: true` will continue to have their actual values synced to ES.

### 7.5 metrics: Metric Configuration Structure

`metrics` is also a list, and each element inside represents a metric.

Each metric mainly has the following information:

- `name`: metric name
- `description`: metric meaning
- `relevant_columns`: which fields this metric is related to
- `alias`: metric alias

For example:

```yaml
metrics:
  - name: GMV
    description: 全称 Gross Merchandise Value，表示所有订单的成交金额总和。
    relevant_columns:
      - fact_order.order_amount
    alias: [成交总额, 订单总额]
```

The `relevant_columns` here is very important because it connects the "metric" with the "underlying fields." Later, when writing data to the metadata database, the `column_metric` relationship table is generated based on this field.

### 7.6 Why type and examples Are Not Configured

This is also a point that easily confuses beginners. Many students find it a bit strange when they first see this:

- The `column_info` in the metadata database clearly has `type`
- Field information will also have `examples` later
- Why are these two fields missing from the configuration file

The reason is actually very simple: **if information can be automatically queried by the program, try not to require users to fill it in manually.**

For example:

- `type` can be obtained directly by querying the field type from the data warehouse
- `examples` can be obtained directly by querying sample field values from the data warehouse

This approach has two clear benefits: the configuration file becomes more concise, and automatic reading is usually more accurate than manual entry. Therefore, the configuration file here only requires you to fill in content that **cannot be automatically inferred by the program and must be declared by the business side**, such as: table and field roles, description information, aliases, and whether to sync values.

## 8. Detailed Explanation of build_meta_knowledge.py

This section has a very important design principle: **the script entry should not be packed with business logic from the start.** It is more suitable to serve as a "general orchestrator" rather than a "general implementation."

Corresponding project file path: `shopkeeper-agent/app/scripts/build_meta_knowledge.py`

To make the main flow clear first, the code below retains the "core skeleton of the entry script." The complete implementation in the current repository also additionally initializes dependencies such as `Qdrant`, `Embedding`, and `Elasticsearch`, but these are all just dependency preparations at the entry layer, not specific business processing.

```python
import argparse
import asyncio
from pathlib import Path

from app.clients.mysql_client_manager import (
    dw_mysql_client_manager,
    meta_mysql_client_manager,
)
from app.repositories.mysql.dw.dw_mysql_repository import DWMySQLRepository
from app.repositories.mysql.meta.meta_mysql_repository import MetaMySQLRepository
from app.services.meta_knowledge_service import MetaKnowledgeService


async def build(config_path: Path):
    # 整条构建链路会同时访问两套 MySQL
    # meta 用来写结构化元数据
    # dw 用来读取真实表结构和字段示例值
    # 1. 初始化两个 MySQL 客户端：
    #    一个连元数据库，一个连数仓模拟库
    meta_mysql_client_manager.init()
    dw_mysql_client_manager.init()

    # 2. 打开两个异步 Session，分别供两个 repository 使用
    async with (
        meta_mysql_client_manager.session_factory() as meta_session,
        dw_mysql_client_manager.session_factory() as dw_session,
    ):
        # 3. 创建 repository 对象
        meta_mysql_repository = MetaMySQLRepository(meta_session)
        dw_mysql_repository = DWMySQLRepository(dw_session)

        # 4. 创建 service 对象，并把 repository 注入进去
        meta_knowledge_service = MetaKnowledgeService(
            meta_mysql_repository,
            dw_mysql_repository,
        )

        # 5. 真正进入服务层的构建逻辑
        await meta_knowledge_service.build(config_path)

    # 6. 结束后关闭客户端连接
    await meta_mysql_client_manager.close()
    await dw_mysql_client_manager.close()


if __name__ == "__main__":
    # 7. 解析命令行参数
    #    由外部决定本次构建使用哪份配置文件
    parser = argparse.ArgumentParser()
    parser.add_argument("-c", "--conf")
    args = parser.parse_args()

    # 8. 将字符串路径转成 Path
    #    再启动异步 build
    asyncio.run(build(Path(args.conf)))
```

What's most worth grasping in this code first is not any specific line of implementation, but that it clearly defines "what the entry layer should do":

- Parse command-line arguments
- Initialize dependencies
- Create repositories and services
- Call the service layer's `build(config_path)`
- Close connections after the process ends

That is to say, the focus of `build_meta_knowledge.py` is: **to bring up the entire metadata knowledge base construction pipeline.**

As for "how tables and fields are written to the database," "how field vector indexes are built," and "how field value full-text indexes are written," these should not continue to be crammed into the entry script, but will be expanded separately in later specific chapters.

### 8.1 Why the Entry Script Does Not Directly Write Business Logic

If you write all the logic of "reading configuration files, querying the data warehouse, writing to the metadata database, and building indexes" in the script, the entry file will quickly become long and messy.

The benefits of the current approach are:

- `scripts` folder: only responsible for entry and orchestration
- `service` folder: only responsible for business orchestration
- `repository` folder: only responsible for storage read and write

This is why it is important to insist on "layering" here.

### 8.2 Why build() Accepts config_path

This point is also crucial. What the entry script ultimately receives is not the configuration file content itself, but the configuration file path. Then it passes this path to:

```python
await meta_knowledge_service.build(config_path)
```

In this way, the service layer can decide for itself:

- How to read the configuration file
- How to convert the configuration file into objects
- How to decide which branches to process based on the configuration

That is to say, the script is only responsible for **passing in the "entry parameters"**, rather than expanding all details at the script layer.

## 9. Detailed Explanation of meta_knowledge_service.py

If the entry script is only responsible for "bringing up the process," then the service layer is responsible for "connecting the specific business together."

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

To highlight the main flow of "configuration loading -> table processing pipeline -> metric processing pipeline," what is retained below is a teaching-simplified overall orchestration skeleton. For now, let's only look at "what it decides to do first and what to do later," without going into the specific details of table field ingestion.

The current skeleton of `MetaKnowledgeService.build()` is as follows:

```python
from pathlib import Path

from omegaconf import OmegaConf

from app.conf.meta_config import MetaConfig
from app.core.log import logger
from app.repositories.mysql.dw.dw_mysql_repository import DWMySQLRepository
from app.repositories.mysql.meta.meta_mysql_repository import MetaMySQLRepository


class MetaKnowledgeService:
    def __init__(
        self,
        meta_mysql_repository: MetaMySQLRepository,
        dw_mysql_repository: DWMySQLRepository,
    ):
        # meta repository 负责结构化元数据的落库
        self.meta_mysql_repository: MetaMySQLRepository = meta_mysql_repository
        # dw repository 负责到教学数仓中读取真实表结构和示例值
        self.dw_mysql_repository: DWMySQLRepository = dw_mysql_repository

    async def build(self, config_path: Path):
        # 1. 读取配置文件并转换成结构化配置对象
        #    后续流程统一围绕 MetaConfig 展开
        context = OmegaConf.load(config_path)
        schema = OmegaConf.structured(MetaConfig)
        meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
        logger.info("加载配置文件")

        # 2. 根据配置文件判断后续要进入哪条构建链路
        if meta_config.tables:
            logger.info("检测到 tables 配置，表链路入口已准备就绪")
            logger.info("表信息与字段信息构建流程后续继续补充")
            logger.info("字段向量索引与字段值全文索引逻辑后续继续补充")

        # 3. 根据配置文件同步指定的指标信息
        if meta_config.metrics:
            logger.info("检测到 metrics 配置，指标链路入口已准备就绪")
            logger.info("指标入库与指标向量索引逻辑后续继续补充")

        logger.info("当前阶段完成：配置加载与元数据知识库构建骨架准备")
```

### 9.1 What to Look at First in This Code

First, it reads the configuration file first, then decides what to do. That is to say, **configuration takes priority over business actions**.

Second, it first checks `tables`, then checks `metrics`. This exactly corresponds to the top-level structure of the configuration file mentioned earlier.

Third, it has already broken down the subsequent metadata construction into several very clear sub-pipelines:

- Writing table information and field information to the metadata database
- Building field information vector indexes
- Building field value full-text indexes
- Writing metric information and building metric vector indexes

That is to say, the focus of this layer is not to "directly expand every detail," but to first clarify **the business orchestration order of the entire metadata knowledge base**.

As for "how exactly tables and fields are constructed, how the data warehouse is queried, and how data is written into the database" inside `_save_tables_to_meta_db(...)`, it will be expanded in detail in the next chapter.

### 9.2 Why the Service Layer Holds a Repository Instead of a Session

This is also a very critical point when understanding code layering.

If the service layer directly holds `session` and writes SQL everywhere, the layering will quickly break down.  
A more reasonable dependency relationship should be:

```text
scripts
  -> service
  -> repository
  -> session / client
```

That is to say: the service layer is responsible for "organizing the process," and the repository layer is responsible for "executing specific reads and writes."

In this way, as the logic becomes more and more complex later, the code structure will not quickly spiral out of control.

### 9.3 Why build() Should Be Written as an Async Method

The reason can also be seen very intuitively from this code.

In `build()`, these things need to be done frequently:

- Query data warehouse field types
- Query data warehouse sample field values
- Later, also write to the metadata database, write to Qdrant, and write to ES

Almost all of these are I/O operations, so the entire construction process is naturally more suitable to be written as an async function.

## 10. How MetaConfig and OmegaConf Read the Configuration

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

As you have seen earlier, the first step in the service layer is:

```python

schema = OmegaConf.structured(MetaConfig)
meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
```

If these three lines are not broken down and examined, beginners can easily find them a bit abstract. In fact, their purpose is very clear: YAML text -> structured configuration object

### 10.1 The Role of MetaConfig

Corresponding project file path: `shopkeeper-agent/app/conf/meta_config.py`

The core structure of this file is as follows:

```python
from dataclasses import dataclass
from typing import Optional


@dataclass
class ColumnConfig:
    name: str
    role: str
    description: str
    alias: list[str]
    sync: bool


@dataclass
class TableConfig:
    name: str
    role: str
    description: str
    columns: list[ColumnConfig]


@dataclass
class MetricConfig:
    name: str
    description: str
    relevant_columns: list[str]
    alias: list[str]


@dataclass
class MetaConfig:
    # 允许只同步表，或只同步指标，所以两个字段都做成 Optional
    tables: Optional[list[TableConfig]] = None
    metrics: Optional[list[MetricConfig]] = None
```

It can be summarized in one sentence: `MetaConfig` defines "what this configuration file should look like in the program."

And precisely because of these data classes, what the service layer sees later is no longer a pile of loose dictionaries, but a set of objects with stable structure and clearly defined fields.

There is also a point here that is easily overlooked but very much worth explaining separately:

Why are `tables` and `metrics` written as `Optional[...] = None`?

This is because in actual usage, you do not always need to synchronize both tables and metrics at the same time. Sometimes you may only want to synchronize tables, and sometimes you may only want to supplement a few metrics. Therefore, declaring them as optional items better matches how the script will actually be used later.

### 10.2 OmegaConf Three-Step Loading Process

Now, looking back at these three lines of code, things should be much clearer:

```python
context = OmegaConf.load(config_path)
schema = OmegaConf.structured(MetaConfig)
meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
```

It can be broken down into three steps.

#### 10.2.1 OmegaConf.load(config_path): Read the YAML

```python
context = OmegaConf.load(config_path)
```

What this step does is very straightforward: it first reads the contents of the YAML file based on the path. At this point, what you get is still just the "configuration content" and has not really been converted into an `MetaConfig` object.

#### 10.2.2 OmegaConf.structured(MetaConfig): Prepare the Structure Template

```python
schema = OmegaConf.structured(MetaConfig)
```

This step can be understood as: "First tell the program that a valid configuration should conform to the `MetaConfig` structure." In other words, this step prepares a "standard-answer structure template."

#### 10.2.3 merge + to_object: Generate the Configuration Object

```python
meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
```

This line actually does two things in succession:

1. `OmegaConf.merge(schema, context)`: Merge the "structure template" with the "actual configuration content"
2. `OmegaConf.to_object(...)`: Convert the result into a real Python object

So what you finally get is no longer loose YAML content, but a real object that can be used directly in code:

```python
MetaConfig
```
