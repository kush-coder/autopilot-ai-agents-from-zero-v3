## 1. Overall Architecture Overview

### 1.1 First Look at the Overall Pipeline

Chapter 1 already answered what the "Shopkeeper Data Q&A" project is and explained why it is a typical `NL2SQL` scenario. Therefore, in this chapter, we focus on: **how this system actually runs from an engineering perspective.**

In one sentence, the way this system works can be summarized as follows:

**First organize the knowledge about tables, fields, metrics, and field values in the data warehouse into a searchable metadata knowledge base, then let the data Q&A agent generate, validate, and execute SQL based on this knowledge base.**

The entire pipeline can be viewed in the following order:

1. The user first asks a question in natural language
2. The agent first understands the question and extracts key information suitable for retrieval
3. The system then retrieves relevant tables, fields, metrics, and field values from the metadata knowledge base
4. This information is organized into context that is easier for the large language model to understand
5. The large language model generates SQL, then performs validation and necessary error correction
6. Finally, the SQL is executed against the data warehouse and the query results are returned

The most critical design idea here is: **don't let the large language model directly face the entire warehouse and "blindly write SQL"; instead, let it first obtain organized and filtered metadata context.**

Because even if the large language model knows SQL, it naturally has no idea what exists in your actual warehouse:

- Which tables can be queried
- Which fields represent sales amount, region, or membership tier
- What "North China," "Gold Member," or "Total Transaction Amount" actually correspond to in the database

So in essence, the "Shopkeeper Data Q&A" system is always doing two things:

1. First build and maintain the metadata knowledge base
2. Then implement the data Q&A agent based on the metadata knowledge base

The former addresses "what the system knows," and the latter addresses "how the system uses this knowledge to answer questions."

### 1.2 Core Modules and Basic Services Involved in This Project

If you break down the entire system, it can roughly be divided into two layers:

- The upper layer consists of business modules: data warehouse, sync scripts, metadata knowledge base, and data Q&A agent
- The lower layer consists of basic services: `MySQL`, `Qdrant`, `Elasticsearch`, `Embedding` service, large language model orchestration framework, etc.

Let's first look at the business module layer:

- **Data warehouse**: Responsible for storing real analytical data. In the current teaching environment, `Hive` is not actually deployed; instead, `MySQL` is used to simulate the warehouse, containing mainly the `fact_order`, `dim_customer`, `dim_product`, `dim_region`, and `dim_date` tables.
- **Configuration files and sync scripts**: Responsible for defining the synchronization scope, i.e., which tables, fields, and metrics to extract from the data warehouse and sync them into the metadata knowledge base.
- **Metadata knowledge base**: Responsible for organizing the extracted metadata into a searchable, explainable, and retrievable knowledge foundation.
- **Data Q&A agent**: Responsible for invoking this knowledge when users ask questions, completing retrieval, filtering, SQL generation, SQL validation, and SQL execution.

Now look at the basic services that support these modules:

| Basic Service | What This Project Uses | Main Role |
| ------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Data warehouse / metadata database | `MySQL` | In the current project, `MySQL` plays two roles simultaneously: one is the teaching warehouse `dw`, which stores analytical data; the other is the `meta` metadata database, which stores structured metadata such as `table_info`, `column_info`, `metric_info`, and `column_metric` |
| Vector database | `Qdrant` | Stores vectors for field information and metric information, used for semantic similarity retrieval |
| Full-text search service | `Elasticsearch` | Stores field value indexes, used to map natural language values such as "North China" and "Gold Member" to actual field values |
| Embedding service | `TEI` + `BAAI/bge-large-zh-v1.5` | Responsible for converting text such as field names, field descriptions, metric descriptions, and user questions into vectors for `Qdrant` retrieval |
| Agent orchestration framework | `LangGraph` | Responsible for chaining keyword extraction, multi-route retrieval, merge and filtering, SQL generation, SQL validation, and SQL execution into a step-wise executable workflow |

If you only remember one sentence, it can be summarized as: `MySQL` handles structured storage, `Qdrant` handles semantic retrieval, `Elasticsearch` handles field value retrieval, `TEI` handles vectorization, and `LangGraph` organizes the entire data Q&A process.

### 1.3 Understanding the Entire Pipeline with the Architecture Diagram

![Overall architecture of the Shopkeeper Data Q&A system: data warehouse, configuration and sync scripts, metadata knowledge base, and data Q&A agent](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-1-2-1.png)

When looking at this diagram for the first time, the easiest part to get confused by is the many arrows and modules. A simpler way to view it is: **the entire system actually has only two main threads.**

1. **Build phase: prepare the knowledge first**
2. **Query phase: use that knowledge to answer questions**

Let's first look at the first main thread, namely the **build phase**.

1. The configuration file first tells the sync script which tables, fields, and metrics to include in the metadata knowledge base this time.
2. The sync script then combines the configuration file with data warehouse query results to organize the final metadata content to be built. Among them, business semantics, roles, and aliases of tables and fields mainly come from the configuration file; field types, field example values, and some real values are supplemented by the script through further queries against the data warehouse.
3. This content is not directly handed to the large language model; instead, it is first organized and written into the metadata knowledge base.
4. When writing, it is persisted through three routes:
   `meta MySQL` stores structured metadata, `Qdrant` stores the semantic index of vectorized fields and metrics, and `Elasticsearch` stores the real values of some fields for later full-text search.

Once this pipeline is complete, the system is no longer just "aware that there are a bunch of warehouse tables," but has a searchable, explainable metadata knowledge base that the data Q&A agent can invoke.

Now look at the second main thread, namely the **query phase**.

1. The user first asks a natural language question, such as "Calculate the total sales amount in North China."
2. The data Q&A agent first understands the question, then retrieves relevant fields, metrics, and field values from the metadata knowledge base.
3. The system organizes these retrieval results into context that is easier for the large language model to understand.
4. The large language model generates SQL based on this context.
5. The system then performs SQL validation and corrects errors if necessary.
6. Only after the SQL passes does it actually execute against the data warehouse, and the results are returned to the user.

So the most critical point of this system is not "whether the large language model can write SQL," but rather: **before writing SQL, has the system prepared the correct context first?**

If you prefer to remember things in a "module + tech stack" way, you can directly refer to the following table:

| Module | Role | What This Project Uses |
| ---------- | ---------------------------------------- | --------------------------------- |
| Data warehouse | Stores real analytical data | `MySQL` (used to simulate the warehouse in the teaching environment) |
| Sync scripts | Extract metadata from the data warehouse | Python scripts + configuration-driven |
| Metadata database | Stores structured metadata | `MySQL` |
| Vector retrieval | Retrieves relevant fields and metrics | `Qdrant` |
| Full-text search | Retrieves real field values | `Elasticsearch` |
| Vectorization service | Converts field descriptions, metric descriptions, and user questions into vectors | `TEI` + `BAAI/bge-large-zh-v1.5` |
| Agent orchestration | Chains retrieval, filtering, SQL generation, validation, and execution | `LangGraph` |

Stringing them into the most memorable single sentence is:

**In the build phase, use `MySQL + Qdrant + Elasticsearch + TEI` to build the metadata knowledge base; in the query phase, use `LangGraph` to drive the data Q&A agent to invoke this knowledge and ultimately generate and execute SQL.**

## 2. Metadata Knowledge Base

### 2.1 First Understand What a Metadata Knowledge Base Is

In the previous section, we already saw from a high level that what the data Q&A agent truly relies on is not the entire data warehouse itself, but organized, searchable, and explainable data warehouse metadata. Following this line of thought, the metadata knowledge base is essentially the "semantic foundation" of the entire system.

First, let's distinguish two concepts that are easily confused:

- The **data warehouse** stores real analytical data such as orders, products, regions, and time.
- The **metadata knowledge base** stores data about data, such as "what tables and fields exist, what fields mean, what possible values a field may have, and how metrics are defined."

In other words, the data warehouse is responsible for "providing queryable data," and the metadata knowledge base is responsible for "helping the agent understand that data."

One more layer needs to be distinguished: **the metadata database is not equivalent to the metadata knowledge base, but it is part of the metadata knowledge base.**

In the current project, the metadata knowledge base is not a single standalone database, but is composed of the following three parts working together:

- Metadata database: uses `MySQL` to store the most complete and authoritative structured metadata.
- Vector index: uses `Qdrant` for semantic retrieval of fields and metrics.
- Full-text index: uses `Elasticsearch` for keyword matching of field values.

Without this knowledge base layer, even though the large language model may know SQL syntax, it still has no idea:

- What tables and fields actually exist in the current warehouse
- What the business definition of a certain metric is in this project
- Which field or field value a natural language expression in the user's question should map to

So the role of the metadata knowledge base is not to directly generate SQL on behalf of the large language model, but rather to prepare "which tables, fields, values, and metrics should be focused on" before SQL generation. Without this step, subsequent SQL generation can easily become unstable.

If we must use an easy-to-remember analogy, it can be put this way: **the data warehouse is more like a "data warehouse room," while the metadata knowledge base is more like "the manual, index cards, and retrieval system for that warehouse."**

If you are more accustomed to memorizing with a "table," first look at the following summary table:

| Component | What It Mainly Stores | What Problem It Solves | Typical Usage Timing |
| ------------------------ | ------------------------------------------ | -------------------------------------------------- | ------------------------ |
| `MySQL` Metadata Database         | Table information, field information, metric information, relationships between fields and metrics | Stores the most complete and authoritative structured metadata                   | Retrieve complete information by looking up tables after recall |
| `Qdrant` Vector Index        | Vector representations of fields and metrics                       | Solves the problem of "users can recall the same thing even with different wording"                   | Field recall, metric recall       |
| `Elasticsearch` Full-Text Index | Actual values of fields                             | Solves the problem of "how natural language values in questions map to real field values" | Field value retrieval               |

### 2.2 Metadata Database

From the above, we already know that the metadata knowledge base is not a monolith, but rather the collaborative result of `MySQL + Qdrant + Elasticsearch`. Next, let's start with the most foundational layer, namely the metadata database.

The metadata database is responsible for storing complete, authoritative structured metadata. It is not business data itself, but rather "data about data." In the current project, this part is mainly stored in `MySQL` and includes four core tables used to save table information, field information, metric information, and the relationships between fields and metrics in the data warehouse.

![Four core tables of the metadata database: metric_info, column_metric, column_info, table_info, and their relationships](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-2-1.png)

Examples of the specific contents of each table are as follows. To quickly build intuition, first remember the Chinese meanings of these tables:

- `metric_info`: Metric information table
- `column_metric`: Field-to-metric association table
- `column_info`: Field information table
- `table_info`: Table information table

One point that is easily misunderstood needs to be clarified here: **Although these four tables in the metadata database are ultimately written by synchronization scripts, their sources are not exactly the same.**

More specifically, they are usually organized from a combination of "configuration files + data warehouse query results":

- `table_info` and `column_info` are mainly built around tables and fields in the data warehouse
- `metric_info` and `column_metric` come more from metric information and its field associations defined in configuration files

In other words, these four tables are not all "synced directly from the data warehouse unchanged." Instead, they are the result of the synchronization script reading configurations, querying the data warehouse, organizing relationships, and then uniformly writing them into the metadata database.

To expand on this a little further, it can be understood like this:

- `table_info`: Information such as table names, table roles, and table descriptions usually comes mainly from the table definitions in configuration files. The synchronization script generates the final table information records based on these configurations.
- `column_info`: Business semantic information such as field names, field roles, field descriptions, and field aliases usually comes mainly from configuration files; field types and some sample values are supplemented by the synchronization script actually querying the data warehouse. Therefore, it depends on both configuration and the real structure in the data warehouse.
- `metric_info`: Information such as metric names, metric descriptions, metric aliases, and related fields is usually not scanned directly from the data warehouse table structure, but rather comes from metric definitions in configuration files. This is because metrics like `GMV` and `AOV` are inherently more business-oriented definitions rather than information naturally present in the database.
- `column_metric`: This table stores the "relationships between metrics and fields." It is also usually compiled by the synchronization script based on the metric definitions in the configuration and `relevant_columns`, rather than being automatically derived by scanning the data warehouse.

From a design perspective, these four tables are not split arbitrarily; each assumes a different responsibility. Rather than lumping them together, it is better to understand them table by table with reference to the example tables above.

- **The `table_info` table answers: what tables exist and what these tables do**

  Looking at the example above, you can see that `fact_order` is marked as `fact`, while `dim_customer`, `dim_product`, `dim_region`, and `dim_date` are marked as `dim`. Here, `role` is used to distinguish fact tables from dimension tables, and `description` is used to explain the business purpose of each table. This way, when the large language model receives `table_info`, it knows not only that "there is a table called `fact_order`," but also that it is an order fact table primarily recording core metrics such as order quantity and amount.

- **The `column_info` table answers: what fields exist in the tables and how these fields should be understood and used**

  This is the most critical of the four tables. For example, in the record `dim_region.region_name`, the system knows not only that the field name is `region_name`, but also that its type is `varchar(64)`, its role is `dimension`, its sample values may include `华南`, `华东`, and `华北`, its description is "region name," and its aliases may include "area," "region," and "large region." With this information, the system can later understand that when a user asks for "North China sales," `华北` is very likely to map to this field.

  Several fields in `column_info` are particularly important:
  - `type` determines how SQL should be written, since strings, integers, and dates are handled differently.
  - `role` is used to distinguish primary keys, foreign keys, dimension fields, and measure fields. Dimension fields are better suited for grouping and filtering, measure fields are better suited for aggregations such as `sum`, `avg`, and `count`, and primary and foreign keys are relevant to multi-table `join`.
  - `description` helps the large language model understand the business meaning of the field.
  - `alias` helps the system match different phrasings during vector retrieval. For example, "membership tier" and "user tier" may both actually point to `member_level`.
  - `examples` helps the model understand the actual format of real values. For example, if a user asks to "calculate sales for Hebei Province," the system must know whether the database stores `河北` or `河北省`; similarly, for a gender field, whether it stores `男/女`, `male/female`, or `1/0`. These differences directly affect whether the generated SQL is correct.

  Of course, `examples` is only suitable for storing a sample of values, not all values. For fields with very few possible values, such as gender or quarter, including all of them poses no problem; however, for fields with many possible values, such as brand names or product names, it is better to leave them to the full-text index for processing later.

- **`metric_info` answers: what business metrics exist and what these metrics mean**

  Examples include `GMV` and `AOV` above. The system cannot only know that "this abbreviation exists"; it must also know its business meaning, aliases, and which fields it is related to. In real business scenarios, many metrics are internal conventions, and a large language model may not inherently understand them. If a user asks about "total transaction value" or "average order amount," the system needs `metric_info` to understand that the user is actually asking about `GMV` or `AOV`.

  There is another design detail worth noting here: `metric_info` stores `relevant_columns`. From a normalization perspective, this information could arguably be expressed through a relationship table, but redundantly storing it directly here makes it more convenient for the system to retrieve "which fields a given metric depends on" when assembling prompts, reducing the cost of additional queries.

- **`column_metric` answers: which fields are related to a given metric**

  This table has the simplest structure, but its purpose is very clear: to separately store the relationships between fields and metrics. For example, `fact_order.order_amount` corresponds to `GMV`, and `fact_order.order_quantity` corresponds to `AOV`. The value of doing this is that it expresses the "many-to-many relationship between metrics and fields" more clearly and also facilitates future expansion.

If these four tables are compressed into a single sentence, they can be remembered as follows:

- `table_info` manages "tables"
- `column_info` manages "fields"
- `metric_info` manages "metrics"
- `column_metric` manages "relationships between fields and metrics"

With this structured metadata, the system knows which field "sales amount" might correspond to, which column in which dimension table "region" might map to, and what "GMV" actually means, making it possible to further perform accurate retrieval and SQL generation.

If this section is summarized in one sentence, it can be understood this way: the design goal of a metadata database is not merely to "record tables and fields," but to organize in advance as much key information as possible that can affect the accuracy of SQL generation, so that when SQL is actually generated, the large language model can "have a solid basis to rely on." Further, SQL generation quality usually depends on two core factors: the foundational capability of the model itself, and the design quality of the metadata knowledge base. Model capability determines the upper limit of understanding, reasoning, and generation, while metadata design determines whether the model can obtain sufficiently accurate, complete, and business-context-aligned information when generating SQL.

### 2.3 Vector Index

Relying solely on exact matching is often insufficient for natural language data querying scenarios. For example, a user might say "total transaction value," while the field description says "order amount"; a user might say "user tier," while the field metadata says "membership tier." In such cases, keyword-by-keyword exact matching is very likely to fail.

Therefore, some field information and metric information from the metadata database needs to be further converted into a semantic vector index, giving the system the ability to "find things even when they are semantically similar."

The vector index primarily applies to two types of information: `column_info`, that is, field information, and `metric_info`, that is, metric information.

One point should be specifically clarified here: this project does not build a separate vector index for `table_info`. The reason is not that table information is unimportant, but that field information already carries `table_id`. In other words, once fields are retrieved, we can trace back to the corresponding table information through the `table_id` to which the fields belong. Therefore, in the actual design, there is no need to build an additional independent vector retrieval system for table information.

In other words, the approach of this project is:

- First retrieve field information and metric information
- Then use the `table_id` in the fields to retrieve the corresponding table information from the metadata database

This design reduces duplicate indexes while making the overall retrieval logic more centralized.

- **column_info**

The fields in `column_info` that require a vector index are shown in the figure below:

![Diagram showing the fields in column_info used for building the vector index (name, description, alias, etc.)](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-3-1.png)

A concrete example is shown in the figure below:

![Example showing one row of column_info metadata split into multiple vectors by name, description, and alias, and written into the vector database](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-3-2.png)

The core idea here is not to "build just one vector for an entire row of field information," but to build separate vectors for multiple key texts within the same row. Taking `column_info` as an example, one field record typically corresponds to multiple vector points:

- The field name `name` generates one vector
- The field description `description` generates one vector
- Each field alias `alias` also generates its own vector

This means that one row in `column_info` is often not a single point in the vector database, but multiple points. The advantage of this is that no matter whether a user question is closer to the original field name, the field description, or a field alias, the system has a higher probability of retrieving the correct field, thereby improving recall.

The "recall rate" here can be simply understood as follows: for a user question, there are actually several truly relevant fields or metrics. If the system can find as many of these relevant objects as possible, the recall rate is high; if they are relevant but the system fails to retrieve them, the recall rate is low. This is exactly why we build vector indexes for `name`, `description`, and `alias` at the same time, with the goal of minimizing the situation where "relevant information is not found."

Looking further, each vector point stores not only the vector itself, but also the corresponding `payload`. You can think of `payload` as "the business information attached to this vector point." In this project, what is stored in `payload` is the complete field information, not just a simple field ID. This way, when the system retrieves the most similar vector point in `Qdrant`, it can directly extract the complete field information from `payload`, avoiding an additional database lookup.

Of course, this is also an engineering trade-off. If only IDs were stored, the data in the vector database would be lighter, but after retrieval you would still need to query the database again; if the complete field information is stored directly, reading after retrieval is more convenient, but when the field information in the metadata database changes, the `payload` in the vector database must also be updated synchronously. This project chooses the latter so that the query path is more direct.

- **metric_info**

The fields in `metric_info` that require a vector index are shown in the figure below:

![Diagram showing the fields in metric_info used for building the vector index (name, description, alias, etc.)](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-3-3.png)

A concrete example is shown in the figure below:

![Example showing metric_info metric metadata vectorized separately by name, description, and alias, and written into the vector database](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-3-4.png)

The approach for `metric_info` is completely analogous to `column_info`. For each metric record, we likewise build vector indexes separately for `name`, `description`, and `alias`. This way, when a user question contains an abbreviation, alias, or a more colloquial expression for a business metric, the system can more easily retrieve the correct metric.

In actual implementation, we send texts such as field names, field descriptions, and field aliases, as well as metric names, metric descriptions, and metric aliases separately into the Embedding model. After obtaining vectors, we store them in `Qdrant` for subsequent semantic retrieval.

If we summarize this part in one sentence, it can be understood as follows: the goal of vector indexing is not to mechanically "store a bunch of embeddings", but to ensure that user questions can more reliably retrieve the truly relevant fields and metrics from different expressions.

### 2.4 Full-text Index

In addition to fields and metrics, a data Q&A system has another very critical category of information that needs to be retrieved: the actual values of fields.

For example, a user may mention: North China, Gold Member, or a specific product name.

This kind of information is often not a "field name", but rather "values within a field". To enable the system to accurately map these natural language descriptions to real values in the database, we also need to build a full-text index.

This is actually connected to the design of `column_info.examples` mentioned earlier. The role of `examples` is to first tell the large language model what value formats a field may roughly have. However, if a field has a very large number of actual values, such as brand names, product names, region names, or category names, it is impossible to stuff all values directly into `examples` and hand them to the model. That would not only make the context very long, but also slow down overall generation efficiency.

Therefore, this project adopts a more engineering-friendly approach: for field values that are likely to appear in SQL filter conditions in the future, a separate full-text index is built. When user questions contain texts such as "North China", "Gold Member", or "Mobile & Digital", the system first retrieves the most relevant real values from the full-text index, and then feeds these retrieval results back into the subsequent prompt and SQL generation process.

There is also a criterion to understand here: not all fields are suitable for full-text indexing. Generally speaking, **full-text indexes mainly target "text-type dimension fields", because these fields are the most likely to appear as filter conditions.** For example, region, province, brand, category, product name, and membership level are all very suitable for building a full-text index.

On the contrary, measure fields such as `order_amount` and `order_quantity` are usually used for aggregation statistics rather than keyword filtering; numeric fields such as `year`, `month`, and `day` may participate in filtering, but they are not suitable for full-text retrieval. Therefore, the full-text index does not cover all fields, but selectively covers those that are "text-type, dimension-type, and likely to serve as filter conditions".

A specific example is shown in the figure below:

![Mapping example of dimension table field values written into the full-text index table value_info (id, value, column_id)](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-2-4-2.png)

In the project implementation, this capability is provided by `Elasticsearch`. Each field value is written into `ES` as an independent index record, which contains at least three core pieces of information:

- `id`: the unique identifier of that value
- `value`: the actual value of the field
- `column_id`: which field this value belongs to

The benefit of this approach is that after the system retrieves a value, it not only knows "what text was matched", but also "which field this value belongs to", so the retrieval result can be attached back to the corresponding field.

For example, if a user question mentions "South China", after the full-text index retrieves this value, the system not only knows that it matched the text `华南`, but also knows that it belongs to `dim_region.region_name`. Therefore, when organizing field information later, this value can be added to the candidate values of the corresponding field, providing a basis for generating SQL conditions such as `WHERE region_name = '华南'`.

From a more ideal design perspective, field value retrieval could actually be further developed into "hybrid retrieval", that is, combining full-text retrieval and vector retrieval at the same time. This is because in some special cases, the wording in a user question may not exactly match the real values in the database, and may involve aliases, pinyin, synonymous expressions, and so on. In such cases, relying solely on full-text retrieval may sometimes miss results, while hybrid retrieval is usually more robust.

However, in this project, the implementation has been simplified from an engineering standpoint: field value retrieval mainly uses full-text retrieval. This is because in most common scenarios, field values are more concerned with "whether the text is similar" rather than "whether the semantics are abstractly similar", so full-text retrieval can already cover the vast majority of needs. If further improvement is needed later, adding vector retrieval on top of this would be a more natural optimization direction.

If we summarize this section in one sentence, it can be understood as follows: what the full-text index solves is not the question of "what a field is called", but the question of "what values are actually stored in the field". Its core role is to help the system map natural language descriptions in user questions to filter values that actually exist in the database.

### 2.5 Metadata Synchronization Script

The previous sections discussed "what is in the metadata knowledge base". The next section answers another engineering question: **how does that content get there?**

In actual engineering, the metadata knowledge base is not manually entered bit by bit, but is built and maintained through synchronization scripts. In this project, a very important foundational task is to write a "metadata synchronization script". Its role can be summarized in one sentence: based on a configuration file, synchronize specified tables, specified fields, and specified metrics into the metadata knowledge base.

If you want to first see intuitively what these raw data warehouse tables look like, you can refer back to the [data warehouse table example](1-%E9%A1%B9%E7%9B%AE%E6%A6%82%E8%BF%B0%E4%B8%8E%E6%95%B0%E4%BB%93%E5%9F%BA%E7%A1%80.md#_44-example-tables-from-the-current-projects-data-warehouse) in Chapter 1. What the synchronization script reads is exactly the structural information, field information, and some sample values in such fact tables and dimension tables.

This process roughly includes:

1. Read the configuration file to determine which tables, which fields, and which metrics need to be synchronized
2. Read the corresponding table structures, field types, and some field value samples from the data warehouse
3. Write the complete metadata into `MySQL`
4. Build vector indexes for field information and metric information
5. Build full-text indexes for field values suitable for retrieval

The benefit of this design is that the entire knowledge base construction process is configurable, repeatable, and incrementally expandable.

For example:

- If there are initially 100 tables in the data warehouse, we can synchronize all 100 tables into the knowledge base at once through the configuration file
- If 10 more tables are added later, we only need to update the configuration file and run the synchronization script again to add the new content

In other words, the metadata knowledge base is not statically hard-coded, but can continuously evolve as the data warehouse changes.

If you want to look at the code later alongside the explanation, it is enough to know for now that there are two related files:

- `app/scripts/build_meta_knowledge.py`
- `app/services/meta_knowledge_service.py`

This part will be further expanded in later chapters, so for now it is enough to have a general impression.

## 3. Data Q&A Agent

What truly turns user questions into query results is the data Q&A agent in the project.

This agent is implemented based on `LangGraph`. It is not the simple single-round "Prompt + LLM" pattern, but rather a graph-structured process that can execute step by step, be observed, and self-correct.

![Full workflow of the LangGraph-based data Q&A agent: nodes for keyword extraction, multi-route retrieval, merging and filtering, SQL generation and validation, and more](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-1-1.jpg)

Looking down along this flowchart, the entire data Q&A agent is essentially a workflow of "first understanding the question, then retrieving information, and finally generating and executing SQL".

To grasp the main thread first, this entire process can also be compressed into three stages:

1. **Understand the question**
   First extract keywords suitable for retrieval from the user question, and retain the original question as a semantic fallback.
2. **Prepare the context needed for SQL**
   First perform coarse retrieval of relevant fields, metrics, and values, then organize, complete, and filter them into context more suitable for SQL generation.
3. **Generate and execute SQL**
   After the context is complete, generate SQL, then validate it, correct it if necessary, and finally actually execute it.

With this "three-stage" perspective in mind, it will be easier to understand why there are steps such as "retrieval, merging, and filtering" in the middle. They are all actually preparing for SQL generation.

### 3.1 Step 1: Extract Keywords

![Data Q&A agent "Extract Keywords" step: using jieba and TF-IDF to extract core words from the user question for retrieval](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-1-2.png)

The first node at the top of the flowchart is "Extract Keywords".

The role of this step is to first extract the core words in the user question that are truly helpful for the query, and remove as many irrelevant expressions as possible. For example, if a user says:

- Help me calculate the total sales amount in North China

The system does not necessarily need to take the entire sentence verbatim for subsequent retrieval. Instead, it can prioritize extracting more critical words, such as: North China, total sales amount. The purpose of this is to make the subsequent retrieval more focused and cleaner.

In terms of implementation, this step is completed with the help of word segmentation and keyword extraction tools. In the current project, this step uses the keyword extraction capability provided by `jieba`. `jieba` is a commonly used Python library for Chinese word segmentation and keyword extraction, and internally it uses the `TF-IDF` approach.

`TF-IDF` can be intuitively understood as follows: it does not simply count "which word appears more often", but rather evaluates "which word is more important and more representative in the current sentence". If a word appears in a relatively key position in the current question, and is not the kind of ordinary word that appears everywhere in all kinds of sentences, then it is more likely to be recognized as a keyword. Conversely, words like "的", "了", and "一下", which repeatedly appear in many sentences, are usually not suitable as keywords.

Therefore, in this project, the role of `TF-IDF` can be simply understood as: extract as much as possible the core words that are truly helpful for database queries from the user question, and filter out those irrelevant words that interfere with retrieval first, thereby making the subsequent field retrieval, metric retrieval, and field value retrieval more accurate.

Of course, keyword extraction is not 100% perfect, and in theory there is a possibility of missing important information. Therefore, in the actual workflow, the original question itself is also retained as a form of supplementary insurance. This can avoid information loss caused by relying solely on keywords.

> One point needs particular understanding here: the significance of keyword extraction is to first distill the core words in the question that are most suitable for retrieval, improving the efficiency and accuracy of subsequent retrieval; while retaining the original question is to avoid missing semantic details during keyword extraction, serving as fallback information for complete semantics. In other words, keywords and the original question are not an either-or relationship. Instead, "one is responsible for focused retrieval, while the other supplements complete semantics".

### 3.2 Step 2: Retrieve Three Types of Information in Parallel

From "Extract Keywords" downward, the flowchart branches into three paths at the same time:

- Retrieve field information
- Retrieve metric information
- Retrieve field values

There is no strict sequential dependency among these three steps, so they can be executed in parallel. The benefit of parallelism is that on the one hand it saves time, and on the other hand it aligns with the actual query logic, because a question often involves fields, metrics, and field values at the same time.

Here, this step can be regarded as a **coarse retrieval**. That is, the goal of this step is not to immediately obtain the final answer, but to first find as many "potentially relevant materials" as possible. It is better to cast a wider net first than to miss truly relevant information from the very beginning.

- **Retrieve field information**

![Data Q&A agent "Retrieve field information": retrieves column_info fields related to the user question based on the vector index](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-2-1.png)

This step mainly retrieves the fields most relevant to the question from the vector index. For example, if the question contains expressions like "region" or "total sales", the system should try to find potentially relevant fields such as `region_name` and `order_amount`.

To improve recall, the system does not rely solely on the initially extracted keywords; it also uses the LLM to perform further "keyword expansion". In other words, the system asks the model to supplement with terms more suitable for field retrieval, starting from the goal of "I want to look up field information"—for example, expanding "total sales" into expressions like "sales amount". The essence of this is to improve field recall.

- **Recall metric information**

![Data Q&A agent "Recall metric information": retrieve metric_info metric definitions related to the user question based on the vector index](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-2-2.png)

This step is similar to field recall and also uses vector retrieval, except the target is now the business metrics in `metric_info`. For example, when a user asks about "total sales", the system should not only think of the specific field `order_amount`, but also have the chance to recall metric definitions such as `GMV`.

Keyword expansion is also performed here. The wording in user questions is not necessarily exactly the same as the metric names. By expanding keywords, the system can more easily match the "question phrasing" with the "metric definitions in the metadata".

- **Recall field values**

![Data Q&A agent "Recall field values": map natural language in the question to actual field values in the database through the full-text index](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-2-3.png)

This step mainly uses full-text retrieval, with the goal of finding the actual field values mentioned in the question. For example: North China region; Gold member; mobile phones and digital products.

These pieces of information are not field names, but the values stored in the fields, so they need to be searched in the full-text index.

From an ideal design perspective, field value retrieval would actually be better implemented as a hybrid of "full-text retrieval + vector retrieval", because some scenarios may involve aliases, pinyin, or different writing styles. However, in the current project, in order to keep the main workflow clear first, this step has been simplified and mainly uses full-text retrieval. If further optimization is needed later, it will be relatively natural to add hybrid retrieval capability to this step.

### 3.3 Step 3: Merge recalled information

![Data Q&A agent "Merge recalled information": organize fields, metrics, and field values into hierarchical context grouped by table](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-3-1.png)

After the three routes of coarse recall are completed, the system obtains three relatively scattered sets of results:

- A batch of field information
- A batch of metric information
- A batch of field values

But this information still cannot be directly handed to the LLM at this point, because it is scattered, fragmented, and unstructured, while the LLM needs structured, grouped information when generating SQL.

Therefore, the next step in the flowchart is "Merge recalled information".

The core goal of this step is to organize the scattered recall results into two sets of context more suitable for subsequent use:

- Table information and its field information
- Metric information and its related field descriptions

A few key actions need to be specially understood here:

1. After fields are recalled, they can be regrouped by table based on the `table_id` in each field, organizing them into a structure of "which available fields a given table has".
2. After metrics are recalled, the fields related to the metrics must also be considered, because a metric often depends on one or more fields.
3. After field values are recalled, these values must be reattached to the fields they belong to, making the `examples` or candidate value information of the fields more complete.

This step can be viewed this way: the preceding recall is about "fishing out the parts", while this step is about "assembling the context". If `3.2` is first finding as much relevant material as possible, then `3.3` organizes these materials into the form actually needed for SQL generation.

One very important result form also needs to be specially understood here: after this information is organized, the table information is usually structured similarly to `yaml/table_infos.yaml`. In other words, the system does not directly hand the LLM a "scattered field list"; instead, it first organizes it into hierarchical information "grouped by table, with fields attached under each table".

[table_infos.yaml](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/yaml/table_infos.yaml ":include :type=code")

The benefits of this structure are very intuitive:

- The LLM can see at a glance which tables exist
- What role each table plays, whether it is a fact table or a dimension table
- Which fields each table contains
- What the type, role, example values, description, and aliases of each field are

Combined with this example, we can further understand why "Merge recalled information" is not just simple concatenation:

- Fields under the same table are regrouped rather than continuing to remain scattered in a list.
- Information such as the field's `examples`, `description`, and `alias` is also retained, making it easier to understand "what the field is called, what values it may contain, and what else users might call it" when generating SQL later.
- Fact tables like `fact_order` and dimension tables like `dim_region` appear together, because the LLM later needs to know not only which metric to aggregate, but also from which dimension to analyze it.
- Foreign key fields such as `customer_id`, `date_id`, `product_id`, and `region_id` are also retained, because they are often necessary for subsequent multi-table joins.

In addition to table information, the merged metric information is also organized into a separate hierarchical result file, usually similar to the structure of `yaml/metric_infos.yaml`.

[metric_infos.yaml](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/yaml/metric_infos.yaml ":include :type=code")

Combined with this example, it is easier to understand the metric organization logic in the "Merge recalled information" stage:

- The system does not keep only an isolated metric name; it also organizes the metric's `description`, `relevant_columns`, and `alias` together.
- The role of `description` is to tell the LLM what this metric actually means in business terms, preventing the model from seeing only an abbreviation without knowing its meaning.
- `relevant_columns` associates the metric with specific fields. For example, `GMV` corresponds to `fact_order.order_amount`, making it easier to know which field should be aggregated when generating SQL later.
- `alias` retains common user phrasings, such as "total transaction amount", "total order amount", and "average unit price", so that the system does not rely solely on the original metric name when understanding natural language questions.

In other words, the true goal of the "Merge recalled information" step is not just to "combine the results", but to organize both table information and metric information into hierarchical context that is suitable for the LLM to read and understand. Showing `yaml/table_infos.yaml` and `yaml/metric_infos.yaml` here is essentially meant to illustrate this point.

### 3.4 Step 4: Filter metric information and filter table information

Even after merging, the information currently obtained is not necessarily the final best result, because the goal of the previous step was to "organize it first", not to make it "already sufficiently precise". At this point, two types of problems usually remain:

- Some fields, tables, and metrics were recalled, but are not strongly related to the current question
- Some fields were brought in to complete primary-foreign key relationships, but are not themselves the focus of the question

Therefore, the flowchart next splits into two filtering steps:

- Filter metric information
- Filter table information

![Data Q&A agent "Filter metric information": semantically refine the recalled metric metadata in combination with the user question](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-4-1.png)

Both of these steps are essentially a **fine-grained refinement**. The system uses the LLM, together with the user's original question, to perform another round of semantic judgment on the recall results, removing irrelevant and redundant items and keeping only the tables, fields, and metrics most relevant to the current query intent.

This step is very important, because the preceding recall is more like "better to recall a little more than to miss too much", while this step cleans up the "extra parts". You can remember this whole chain as: **coarse recall first, then structured organization, and finally fine-grained filtering.**

After filtering is complete, the metric information is also organized into a more concise result file. For example, `yaml/filtered_metric_infos.yaml` in the current project is an example result of the "Filter metric information" step.

[filtered_metric_infos.yaml](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/yaml/filtered_metric_infos.yaml ":include :type=code")

Combined with this example, it is easier to understand what the "Filter metric information" step mainly does:

- It does not retain all metric definitions recalled earlier, but only keeps the metrics truly relevant to the current question.
- If the current question is about aggregating "total sales", then what is ultimately retained is likely to be the core metric `GMV`.
- `description` tells the LLM the business meaning of this metric, preventing the model from recognizing only the name without understanding its definition.
- `relevant_columns` associates this metric with specific fields, such as `fact_order.order_amount` here, making it easier to locate which field should be aggregated when generating SQL later.
- `alias` retains different phrasings such as "total transaction amount" and "total order amount", making it convenient for the system to align expressions in user questions with actual metric definitions.

There is also an engineering detail worth noting: some primary key and foreign key fields are not easily recalled naturally during vector retrieval, but they are often indispensable for multi-table joins when actually writing SQL. Therefore, in the implementation, the system also retrieves the necessary primary and foreign keys from the metadata database, and then handles them uniformly during the filtering stage. In other words, the filtering stage is not purely about "removing things"; it also ensures that the key structures truly needed for SQL generation are not lost.

![Data Q&A agent "Filter table information": retain the tables and fields related to the current question to form a concise table structure context](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-4-2.png)

After filtering is complete, the table information is usually organized into a more concise result file. For example, `yaml/filtered_table_infos.yaml` in the current project is an example result of the "Filter table information" step.

[filtered_table_infos.yaml](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/yaml/filtered_table_infos.yaml ":include :type=code")

Combined with this example, it is easier to understand what the "Filter table information" step mainly does:

- It does not retain all tables and all fields recalled earlier exactly as they were; instead, it keeps only the portion truly needed for the current question.
- If the current question is related to "regional sales", then ultimately only the two core tables `fact_order` and `dim_region` may remain.
- Fields directly related to the question, such as `order_amount` and `region_name`, are retained.
- Although `region_id` is not a field directly mentioned in the user's question, it is also retained because it serves the primary-foreign key relationship.

In other words, the goal of the "Filter table information" step is not only to "remove irrelevant content", but to retain the table structure context truly necessary for generating SQL and organize it into a YAML structure more suitable for subsequent use. Only at this point has the system truly obtained context material that is "relevant, complete, and ready for SQL generation".

### 3.5 Step 5: Add additional context

![Data Q&A agent "Add additional context": supplement environment information such as current time, database type, and version that affects SQL correctness](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-5-1.png)

After filtering, the system has obtained relatively clean table information, field information, and metric information, but before actually generating SQL, the flowchart still includes a step called "Add additional context". What this step does is: after the "business context" is already complete, fill in the "environment context" as well.

What this step supplements is mainly environment information that does not directly belong to the table structure but affects SQL correctness, for example:

- Current time
- Current database type
- Current database version

This step may seem inconspicuous, but it is actually very practical. For example, if a user asks, "Calculate the total sales for last year" or "Calculate the sales amount for last month," the model must know what the "current time" is in order to correctly derive the time range.

As another example, the SQL dialects of different databases or data warehouse engines are not entirely identical. Even if they are all SQL overall, they may differ in functions, syntax details, and version support. Therefore, if you can tell the large language model the database type and version in advance, the SQL it generates will often be closer to the actual execution environment.

### 3.6 Step 6: Generate SQL

![Data Q&A agent "Generate SQL": the large language model generates the query statement after context such as tables, fields, metrics, and values is complete](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-6-1.png)

At this step, the system finally has the main context required for generating SQL:

- The user's original question
- The filtered table information, field information, and related metric descriptions
- The field values that may be needed, as well as supplementary context such as the current time and database environment

Only when all of this information is passed to the large language model together does it truly have the foundation for generating SQL with relatively high quality.

It can also be said that all of the preceding steps ultimately serve this moment: allowing the model to generate SQL on the premise of "knowing what to query, knowing which table fields can be used, knowing how to write the values, and knowing what the environment is."

### 3.7 Step 7: Validate SQL

After the SQL is generated, the flowchart does not execute it immediately; instead, it first enters "Validate SQL." The purpose of this step is to perform a preliminary check before actual execution, so that syntax issues or obvious errors can be discovered as early as possible.

In the current project, this step is mainly accomplished through `EXPLAIN`. It does not actually execute the SQL query itself, but first asks the database to analyze the SQL. If the SQL syntax is correct, it usually passes smoothly; if the SQL itself contains errors, the database will report an error directly.

Therefore, this step can be understood as follows: do not rush to query the data yet; first check whether this SQL can at least be accepted by the database.

### 3.8 Step 8: Correct SQL

If "Validate SQL" passes, the flowchart proceeds directly downward. If validation fails, the right side of the flowchart goes to "Correct SQL."

This step takes the context used earlier when generating the SQL, together with the error message returned by the database, and passes them back to the large language model, allowing it to correct the SQL based on the error information.

From a more complete engineering design perspective, the corrected SQL could theoretically return to the validation step for another round of cyclic validation, which would be more robust. However, the current project simplifies this: after correction, it directly enters the execution phase without continuing multiple rounds of iteration, in order to avoid making the process overly complex.

### 3.9 Step 9: Execute SQL

When the SQL passes validation, or is ready to be executed after correction, the final step in the flowchart is "Execute SQL." This step actually sends the SQL to the database for execution, obtains the result, and returns it to the user. Only at this point is the entire data Q&A pipeline fully closed.

### 3.10 Summary of This Section

If we summarize this diagram in more concise terms, it can be understood as follows:

1. First understand the question.
2. Then retrieve fields, metrics, and values in parallel.
3. Integrate the retrieval results and filter them cleanly.
4. Supplement the environmental context.
5. Generate SQL.
6. Validate, and correct if necessary.
7. Finally execute and return the result.

Expressed in more engineering-oriented terms, the core work of this agent can actually be condensed into one sentence: based on the user's question, retrieve relevant fields, field values, and metric information, and then have the large language model generate SQL based on that information.

This design has several clear advantages:

- The responsibility of each step is clear, making it easy to understand and maintain.
- The process is observable, making it convenient for the frontend to display the agent's execution status in real time.
- When an error occurs, it can be corrected at a local node, so overall it is more stable than a single large language model generation and is more suitable for real engineering scenarios.

You can understand it this way: we are not treating the "large language model" directly as the final answer, but rather placing it into a designed workflow so that it can complete the data Q&A task under controlled context and rules.
