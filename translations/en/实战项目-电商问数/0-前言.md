If you are looking for an AI project that is truly suitable for getting started and advancing, rather than just calling a large model API once, writing a few prompts, and demonstrating SQL generation results, then this "Shopkeeper Data Q&A" tutorial is perfect for you.

## 1. Why It Is Suitable for Beginner to Intermediate Learning

Many AI project tutorials tend to go to two extremes:

- Either too lightweight, only demonstrating a single model call, leaving you unsure how to build a real project afterward
- Or too heavyweight, cramming in a large amount of production-grade capabilities from the start, making it easy for beginners to get lost in engineering complexity

"Shopkeeper Data Q&A" chooses a middle path that is more suitable for learning: **it retains the most core and essential engineering pipeline of a real data Q&A system, but does not pursue being large and comprehensive from the very beginning.**

You will see why an intelligent data Q&A project cannot rely solely on a large model to generate SQL directly, but must first solve the following problems:

- With multiple fact tables and dimension tables, how does the system know which tables to query
- When users say "North China," "Gold Member," or "Apple brand," how does the system locate the actual fields and values
- Why should fields, metrics, and field values be indexed separately
- What are the respective responsibilities of the metadata database, vector index, and full-text index
- Why can't the recalled information be directly passed to the model, but instead needs to be merged, filtered, and supplemented
- Why does SQL still need to be validated, error-corrected, and then executed after generation
- Why does the backend API need to use streaming responses so the frontend can see the execution process

This is also why it is very suitable for learning technologies such as `MySQL`, `LangGraph`, and `Qdrant`: these technologies do not appear in isolation, but are all placed within a clear business objective.

You are not learning a database, a vector store, or a framework API in isolation, but rather learning how they work together to complete a real agent application.

## 3. What Exactly Does This Project Do

In real enterprises, business personnel usually cannot write SQL, and data analysts cannot possibly remember all table structures, field meanings, and metric definitions at all times. This leads to a very typical need:

- Can users ask questions directly in natural language?
- Can the system automatically find relevant tables, fields, and metrics?
- Can it automatically generate SQL and return results that can truly be used for analysis?

"Shopkeeper Data Q&A" aims to solve exactly this problem.

The following diagram can first help you build an overall impression: after a user poses a natural language question, the system goes through backend orchestration, field and table structure retrieval, natural language to SQL conversion, database query, SSE streaming push, and finally presents the results to the user.

![Shopkeeper Data Q&A NL2SQL system architecture: user question, backend orchestration, field table retrieval, SQL generation, database query, and frontend display](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/0/0-2.jpg)

From the user's perspective, it is simply an "intelligent data analysis assistant that knows how to query data":

1. The user first asks a question in natural language
2. The system understands the question and extracts key information suitable for retrieval
3. It then recalls relevant tables, fields, metrics, and field values from the metadata knowledge base
4. It organizes this information into context that is more suitable for the large model to understand
5. The large model then generates SQL, and performs necessary validation and error correction
6. Finally, it executes the SQL in the data warehouse and returns the process and results to the frontend

When a query actually runs, the frontend does not just wait for the final result, but can see the execution process of the LangGraph workflow: extracting keywords, recalling field information, recalling metric information, recalling field values, merging recall information, filtering context, generating SQL, validating SQL, executing SQL, and finally displaying query results.

![Shopkeeper Data Q&A query result page: displays LangGraph execution flow, SQL closed-loop progress, and final GMV query results](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/0/0-3.png)

Therefore, the focus of this project has never been just the "large model," but the entire pipeline below:

- How to design and simulate the data warehouse
- How to build the metadata knowledge base
- How to perform hybrid retrieval of fields, metrics, and field values
- How the agent can generate more reliable SQL based on context
- How the backend service delivers agent capabilities to the frontend
- How logs and exceptions help troubleshoot a complete request pipeline

The following chapters will all revolve around this main thread: first organize the tables, fields, metrics, and field values in the data warehouse into a metadata knowledge base, then enable the data Q&A agent to complete retrieval, reasoning, SQL generation, validation, execution, and result return based on this knowledge base.

## 4. What It Is Suitable for Learning, and What It Deliberately Does Not Cover

This project is very suitable for learning the following:

| Learning Direction        | How It Is Reflected in the Project                                                                  |
| --------------- | ------------------------------------------------------------------------------- |
| `MySQL`         | Simulates a teaching data warehouse, stores the metadata database, and executes final SQL queries                                   |
| Data Warehouse Fundamentals        | Understand fact tables, dimension tables, metrics, field roles, and analytical queries                                  |
| Metadata Modeling      | Build structured metadata such as `table_info`, `column_info`, `metric_info`, and `column_metric` |
| `Qdrant`        | Store field and metric vectors for semantic recall                                                |
| `Elasticsearch` | Store actual field values for keyword and value range retrieval                                          |
| `Embedding`     | Convert text such as fields, metrics, and questions into vectors                                                |
| `LangGraph`     | Orchestrate keyword extraction, parallel recall, context merging, SQL generation, validation, and execution                      |
| `FastAPI`       | Provide query APIs, organize dependency injection and lifecycle management                                        |
| `SSE`           | Return the data Q&A process, execution results, and exception information to the frontend in real time                                      |
| Engineering Layering        | Learn how configuration, clients, repository layer, service layer, agent nodes, and API layer collaborate                    |

At the same time, the boundaries should also be made clear:

**"Shopkeeper Data Q&A" is suitable for beginner to intermediate learning, and is not a complete enterprise-grade production system.**

It focuses on covering the most core main pipeline of a data Q&A system: teaching data warehouse, metadata knowledge base, hybrid retrieval, LangGraph workflow, SQL generation, validation, and execution, FastAPI API, SSE response, frontend-backend integration, and log tracing.

However, it will not expand on all production-grade capabilities in the first project, such as:

- User permission and data permission control
- Multi-tenant isolation
- Complex SQL security auditing
- Query caching and performance governance
- Complete evaluation system
- Monitoring, alerting, and distributed tracing platforms
- Canary release and production deployment governance
- More complex multi-turn data Q&A memory systems

These capabilities are certainly important, but if all of them were included in the first hands-on project, the learning cost would be very high, and the main thread could easily be drowned out.

Therefore, this project is better suited to play a clear role: **first help you run through and thoroughly explain the most critical, most essential, and most worthwhile main pipeline of an intelligent data Q&A project.**

## 5. Core Technology Stack of This Project

To truly turn this pipeline into a runnable project, this hands-on project currently mainly uses the following technologies:

| Module           | Technology Stack                            | Purpose                                                                         |
| -------------- | --------------------------------- | -------------------------------------------------------------------------------- |
| Teaching Data Warehouse       | `MySQL`                           | Simulates a data warehouse in a teaching environment, storing fact tables and dimension tables                                     |
| Metadata Database       | `MySQL`                           | Stores structured metadata such as `table_info`, `column_info`, `metric_info`, and `column_metric` |
| Vector Database     | `Qdrant`                          | Stores semantic vector indexes for fields and metrics                                                     |
| Full-Text Retrieval       | `Elasticsearch`                   | Stores actual values of some fields, supporting keyword and value range retrieval                                       |
| Embedding Service     | `TEI` + `BAAI/bge-large-zh-v1.5`  | Responsible for text vectorization                                                                   |
| Agent Orchestration     | `LangGraph`                       | Organizes the multi-stage workflow of the data Q&A agent                                                     |
| LLM Invocation     | `LangChain`                       | Encapsulates model invocation and some pipeline capabilities                                                       |
| Backend API       | `FastAPI`                         | Provides backend services and API capabilities                                                           |
| ORM and Data Access | `SQLAlchemy`                      | Manages access related to the metadata database and data warehouse                                                   |
| Streaming Response       | `SSE`                             | Returns the query process and results to the frontend in real time                                                     |
| Chinese Word Segmentation       | `Jieba`                           | Supports some text preprocessing and keyword processing                                                   |
| Environment and dependency management | `uv`                              | Manage Python project environments and dependencies                                                       |
| Frontend project       | `React` + `Vite` + `Tailwind CSS` | Hosts the query frontend pages and interactive display                                                       |

**The backend uses `FastAPI + LangGraph` to organize the query workflow, uses `MySQL + Qdrant + Elasticsearch` to build the metadata knowledge base, and then leverages a large language model to complete SQL generation, validation, and error correction, finally returning the execution process and results to the frontend through SSE.**

## 6. Project Directory Structure

```text
shopkeeper-agent/
├── app/                  # 后端源码主目录
│   ├── agent/            # 问数智能体与 LangGraph 图流程
│   │   └── nodes/        # 关键词抽取、召回、过滤、SQL 生成、校验、执行等节点
│   ├── api/              # 对外 HTTP 接口层，对应 FastAPI 路由、依赖注入和请求参数结构
│   ├── clients/          # 各类基础服务客户端，例如 MySQL、ES、Qdrant、Embedding 服务
│   ├── conf/             # 配置类与配置加载工具，把 YAML 配置转换成代码可直接使用的对象
│   ├── core/             # 通用基础能力，例如日志、生命周期管理、请求上下文等
│   ├── entities/         # 业务实体定义，承接比 ORM 更贴近业务含义的数据结构
│   ├── models/           # ORM 模型，主要对应 MySQL 中的表结构
│   ├── prompt/           # 提示词加载工具，负责读取和组织静态 Prompt 资源
│   ├── repositories/     # 数据访问层，封装 MySQL / Qdrant / ES 的具体读写逻辑
│   ├── scripts/          # 工具脚本，例如构建元数据知识库、初始化或同步数据
│   └── services/         # 业务逻辑层，负责把客户端、仓储层和智能体能力真正串起来
├── conf/                 # 项目级 YAML 配置文件，例如数据库、向量库、ES、LLM、日志等配置
├── docker/               # 本地开发环境相关文件，例如 docker-compose 和自定义镜像资源
│   ├── elasticsearch/    # Elasticsearch 相关文件，例如 Dockerfile、插件或初始化资源
│   ├── embedding/        # Embedding 服务相关文件，例如模型目录或推理服务配置
│   └── mysql/            # MySQL 初始化 SQL、建表脚本或测试数据导入文件
├── frontend/             # React + Vite + Tailwind CSS 前端项目
├── logs/                 # 本地运行时日志输出目录
└── prompts/              # 静态提示词文件，和 app/prompt 中的加载工具配合使用
```
