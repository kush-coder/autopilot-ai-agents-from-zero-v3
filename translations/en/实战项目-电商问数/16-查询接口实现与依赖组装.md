Chapter 15 already verified that `StreamingResponse + SSE` works correctly, but at that time it returned `fake_streamer()` mock data. This chapter will replace it with the real data query agent.

The final call chain is as follows:

```text
前端 / Apifox
  -> POST /api/query
  -> query_router.py 接收请求
  -> Depends(get_query_service) 获取 QueryService
  -> QueryService.query(...)
  -> graph.astream(...)
  -> StreamingResponse 按 SSE 格式持续返回
```

After completing this chapter, the data query agent is no longer just a command-line internal script, but a backend interface that can be called over HTTP.

## 1. API Code Directory Structure

At this stage, the API code mainly involves the following files:

```text
shopkeeper-agent/
├─ main.py  # FastAPI 入口脚本，负责创建应用并注册路由
└─ app/
   ├─ api/
   │  ├─ routers/
   │  │  └─ query_router.py  # 查询接口路由，接收请求并返回流式响应
   │  ├─ schemas/
   │  │  └─ query_schema.py  # 查询接口请求体结构
   │  ├─ dependencies.py  # 查询接口依赖项，负责组装 QueryService
   │  └─ lifespan.py  # FastAPI 生命周期事件，负责初始化和关闭外部客户端
   └─ services/
      └─ query_service.py  # 查询接口核心业务逻辑，负责调用问数工作流
```

They can first be divided into five layers:

| Layer      | File               | Main responsibility                                       |
| ---------- | ------------------ | --------------------------------------------------------- |
| Entry      | `main.py`          | Create the FastAPI app, register lifecycle and routes     |
| HTTP       | `query_router.py`  | Define `/api/query`, receive requests, return streaming responses |
| Business   | `query_service.py` | Create `State` / `Context`, call LangGraph, and wrap SSE messages |
| Dependency | `dependencies.py`  | Assemble Service, Repository, Session, Client             |
| Lifecycle  | `lifespan.py`      | Initialize clients at app startup, release connections at app shutdown |

The relationship between these files can be summarized in one sentence:

```text
main 挂路由
router 接请求
service 调工作流
dependencies 组装对象
lifespan 管理应用级资源
```

## 2. Entry Point and Routes: Let HTTP Requests Come In

This section solves only one problem: how external requests enter our Python code.

### 2.1 main.py: Create the App and Mount Routes

Project file path: `shopkeeper-agent/main.py`

```python
from fastapi import FastAPI

from app.api.lifespan import lifespan
from app.api.routers.query_router import query_router

# lifespan 交给 FastAPI 管理，用于在服务启动和关闭时统一初始化与释放外部客户端
app = FastAPI(lifespan=lifespan)

# 把查询路由注册进应用；没有挂载时，/docs 和真实 HTTP 请求都访问不到该接口
app.include_router(query_router)
```

The two most critical lines here are:

```python
app = FastAPI(lifespan=lifespan)
app.include_router(query_router)
```

`lifespan` is responsible for resource management during service startup and shutdown, while `include_router` is responsible for mounting the interfaces defined in `query_router.py` onto the FastAPI app.

If you forget `app.include_router(query_router)`, even if `query_router.py` contains `/api/query`, the FastAPI app will not know this interface exists, and it naturally will not appear in the `/docs` page.

### 2.2 query_router.py: The Route Layer Only Handles HTTP-Related Matters

Project file path: `shopkeeper-agent/app/api/routers/query_router.py`

```python
from typing import Annotated

from fastapi import APIRouter, Depends
from starlette.responses import StreamingResponse

from app.api.dependencies import get_query_service
from app.api.schemas.query_schema import QuerySchema
from app.services.query_service import QueryService

# 当前模块只维护查询相关接口，避免后续所有 API 都挤在 main.py 中
query_router = APIRouter()


@query_router.post("/api/query")
async def query_handler(
    # FastAPI 会把前端 JSON 请求体自动解析成 QuerySchema
    query: QuerySchema,
    # FastAPI 会调用 get_query_service，递归组装它依赖的仓储和客户端
    query_service: Annotated[QueryService, Depends(get_query_service)],
):
    return StreamingResponse(
        # query.query 是用户问题字符串；QueryService.query 返回异步生成器
        query_service.query(query.query),
        media_type="text/event-stream",
    )
```

The route layer only does three things:

```text
1. 接收 QuerySchema 请求体
2. 通过 Depends 拿到 QueryService
3. 把 QueryService.query(...) 交给 StreamingResponse
```

It does not directly create Qdrant, ES, or MySQL Repositories, nor does it directly execute graph nodes. The thinner the route layer, the easier it is to maintain the interfaces later.

The most important line in this section is:

```python
query_service: Annotated[QueryService, Depends(get_query_service)]
```

It expresses that the current interface requires a `QueryService`, and this object is provided by `get_query_service()`. The route only declares "what I need"; how it is created is left to `dependencies.py`.

## 3. QueryService: Turning One Request into One Graph Execution

`QueryService` is the core of this chapter. It converts the natural language question passed in from the HTTP layer into a single LangGraph workflow execution.

If `QueryService` were not extracted, the route function would be filled with all this logic:

```text
解析请求体
创建 DataAgentState
创建 DataAgentContext
准备 Repository 和 Client
调用 graph.astream(...)
把 chunk 包成 SSE
处理异常
```

This would make the route layer understand HTTP, workflows, and underlying dependencies simultaneously, and the boundaries would quickly blur. After extracting `QueryService`, the division of labor becomes much clearer:

```text
query_router.py
  -> 负责 HTTP 层：接请求、返响应

query_service.py
  -> 负责业务层：调问数智能体、组织流式输出
```

### 3.1 Migrating from Test Script to API

Previously, when testing the LangGraph workflow, the core code was roughly:

```python
state = DataAgentState(query="统计华北地区的销售总额")
context = DataAgentContext(...)

async for chunk in graph.astream(
    input=state,
    context=context,
    stream_mode="custom",
):
    print(chunk)
```

After migrating to the API, there are three main changes:

| Test script                 | API interface version                 |
| --------------------------- | ------------------------------------- |
| User question hardcoded     | Uses `query` passed in via the request body |
| Context manually created in the test script | Created by `QueryService` after receiving dependencies |
| `print(chunk)` output to console | `yield data: ...\n\n` streamed to the frontend |

### 3.2 QueryService Core Code

Project file path: `shopkeeper-agent/app/services/query_service.py`

```python
import json

from langchain_huggingface import HuggingFaceEndpointEmbeddings

from app.agent.context import DataAgentContext
from app.agent.graph import graph
from app.agent.state import DataAgentState
from app.repositories.es.value_es_repository import ValueESRepository
from app.repositories.mysql.dw.dw_mysql_repository import DWMySQLRepository
from app.repositories.mysql.meta.meta_mysql_repository import MetaMySQLRepository
from app.repositories.qdrant.column_qdrant_repository import ColumnQdrantRepository
from app.repositories.qdrant.metric_qdrant_repository import MetricQdrantRepository


class QueryService:
    def __init__(
        self,
        meta_mysql_repository: MetaMySQLRepository,
        embedding_client: HuggingFaceEndpointEmbeddings,
        dw_mysql_repository: DWMySQLRepository,
        column_qdrant_repository: ColumnQdrantRepository,
        metric_qdrant_repository: MetricQdrantRepository,
        value_es_repository: ValueESRepository,
    ):
        # MySQL 仓储分别负责元数据补全和真实数仓环境信息读取
        self.meta_mysql_repository = meta_mysql_repository
        self.dw_mysql_repository = dw_mysql_repository

        # 召回链路依赖的向量检索、Embedding 和全文检索能力由依赖层注入
        self.embedding_client = embedding_client
        self.column_qdrant_repository = column_qdrant_repository
        self.metric_qdrant_repository = metric_qdrant_repository
        self.value_es_repository = value_es_repository

    async def query(self, query: str):
        # State 只放会被图节点读写和合并的业务数据，外部工具对象不塞进 State
        state = DataAgentState(query=query)

        # Context 保存本次图执行需要复用的外部依赖，节点通过 runtime.context 读取
        context = DataAgentContext(
            column_qdrant_repository=self.column_qdrant_repository,
            embedding_client=self.embedding_client,
            metric_qdrant_repository=self.metric_qdrant_repository,
            value_es_repository=self.value_es_repository,
            meta_mysql_repository=self.meta_mysql_repository,
            dw_mysql_repository=self.dw_mysql_repository,
        )

        try:
            # stream_mode="custom" 对应节点内部 writer(...) 写出的进度消息
            async for chunk in graph.astream(
                input=state,
                context=context,
                stream_mode="custom",
            ):
                # SSE 要求每条消息以 data: 开头，并以两个换行符结束
                # ensure_ascii=False 保留中文进度文案，default=str 兜底处理日期等非 JSON 类型
                yield f"data: {json.dumps(chunk, ensure_ascii=False, default=str)}\n\n"
        except Exception as e:
            # 流式接口已经开始返回后不能再改 HTTP 状态码，因此把异常也包装成一条 SSE 消息
            error = {"type": "error", "message": str(e)}
            yield f"data: {json.dumps(error, ensure_ascii=False, default=str)}\n\n"
```

The most important parts of this code are not `json.dumps`, but rather the two objects: `state` and `context`.

### 3.3 How to Distinguish state and context

`state` stores the business data that continuously changes during this task, for example:

```text
query
keywords
retrieved_column_infos
retrieved_metric_infos
table_infos
metric_infos
sql
result
```

`context` stores the external capabilities that nodes need at runtime, for example:

```text
Embedding Client
ColumnQdrantRepository
MetricQdrantRepository
ValueESRepository
MetaMySQLRepository
DWMySQLRepository
```

You can remember it this way:

```text
state：任务数据，图执行过程中会变
context：工具资源，节点执行时拿来用
```

Do not stuff objects like Repository and Client into `state`. They are not intermediate business results but external capabilities that nodes need to call during execution, and are more appropriately placed in `context`.

### 3.4 Why Exceptions Must Also Be Wrapped as SSE

With a normal interface, when an error occurs, you can directly return a 500 status code. But a streaming interface is different: once `StreamingResponse` begins writing data, the HTTP response headers have usually already been sent, and you can no longer arbitrarily change the status code afterward.

Therefore, in the current version, exceptions are first wrapped as an SSE message:

```python
error = {"type": "error", "message": str(e)}
yield f"data: {json.dumps(error, ensure_ascii=False, default=str)}\n\n"
```

After receiving this message, the frontend can display the error state according to `type=error`. The next chapter will further refine node-level exception handling, frontend-backend integration, and `request_id` log tracing.

## 4. dependencies.py: Delegating Object Creation to the Dependency Layer

The route has already declared:

```python
query_service: Annotated[QueryService, Depends(get_query_service)]
```

This means the project must provide `get_query_service()`.

If you directly create `QueryService` in the route, the route will know too many underlying details:

```text
Qdrant 客户端怎么取
ES 客户端怎么取
MySQL Session 怎么创建和释放
Repository 怎么实例化
QueryService 需要哪些参数
```

These are not things the HTTP layer should care about. Therefore, this project consolidates dependency assembly into:

```text
shopkeeper-agent/app/api/dependencies.py
```

### 4.1 First Look at the Final Dependency Tree

What this chapter ultimately needs to assemble is `QueryService`, and the dependency tree is roughly as follows:

```text
get_query_service
  -> get_meta_mysql_repository
      -> get_meta_session
  -> get_embedding_client
  -> get_dw_mysql_repository
      -> get_dw_session
  -> get_column_qdrant_repository
  -> get_metric_qdrant_repository
  -> get_value_es_repository
```

Going further down, these dependencies will use the client managers initialized during the lifecycle:

```text
embedding_client_manager.client
qdrant_client_manager.client
es_client_manager.client
meta_mysql_client_manager.session_factory
dw_mysql_client_manager.session_factory
```

Therefore, `dependencies.py` and `lifespan.py` form a cooperative pair:

```text
lifespan.py
  -> 应用启动时初始化客户端管理器

dependencies.py
  -> 每次请求中取出客户端或 Session，组装 Repository 和 QueryService
```

### 4.2 MySQL Session Is a Request-Level Resource

The MySQL Session in the project is managed using a dependency with `yield`:

```python
async def get_meta_session():
    """创建一次请求内使用的元数据库 Session"""

    # yield 之后的清理逻辑由 async with 负责，FastAPI 会在请求结束后继续执行退出流程
    async with meta_mysql_client_manager.session_factory() as meta_session:
        yield meta_session


async def get_dw_session():
    """创建一次请求内使用的数仓 Session"""

    async with dw_mysql_client_manager.session_factory() as dw_session:
        yield dw_session
```

The execution order can be understood as:

```text
请求需要 Session
  -> 创建 Session
  -> yield 给 Repository 使用
  -> 请求结束
  -> 退出 async with，释放 Session
```

Do not make Session a global object here. A database Session usually belongs to the unit of work for a single request, whereas client managers and connection pools are things that belong in the application lifecycle.

### 4.3 How Repository and Client Are Assembled

Once you have a Session, you can create the MySQL Repository:

```python
async def get_meta_mysql_repository(
    session: Annotated[AsyncSession, Depends(get_meta_session)],
) -> MetaMySQLRepository:
    """基于请求级 Session 创建元数据仓储"""

    return MetaMySQLRepository(session)


async def get_dw_mysql_repository(
    session: Annotated[AsyncSession, Depends(get_dw_session)],
) -> DWMySQLRepository:
    """基于请求级 Session 创建数仓仓储"""

    return DWMySQLRepository(session)
```

The Qdrant and ES Repositories use the clients already initialized during the application startup phase:

```python
async def get_column_qdrant_repository() -> ColumnQdrantRepository:
    """创建字段向量检索仓储"""

    return ColumnQdrantRepository(qdrant_client_manager.client)


async def get_metric_qdrant_repository() -> MetricQdrantRepository:
    """创建指标向量检索仓储"""

    return MetricQdrantRepository(qdrant_client_manager.client)


async def get_value_es_repository() -> ValueESRepository:
    """创建字段取值全文检索仓储"""

    return ValueESRepository(es_client_manager.client)
```

The Embedding client follows the same approach:

```python
async def get_embedding_client() -> HuggingFaceEndpointEmbeddings:
    """获取应用启动阶段初始化好的 Embedding 客户端"""

    return embedding_client_manager.client
```

### 4.4 Finally Assemble QueryService

All dependencies ultimately converge into `get_query_service()`:

```python
async def get_query_service(
    meta_mysql_repository: Annotated[
        MetaMySQLRepository, Depends(get_meta_mysql_repository)
    ],
    embedding_client: Annotated[
        HuggingFaceEndpointEmbeddings, Depends(get_embedding_client)
    ],
    dw_mysql_repository: Annotated[DWMySQLRepository, Depends(get_dw_mysql_repository)],
    column_qdrant_repository: Annotated[
        ColumnQdrantRepository, Depends(get_column_qdrant_repository)
    ],
    metric_qdrant_repository: Annotated[
        MetricQdrantRepository, Depends(get_metric_qdrant_repository)
    ],
    value_es_repository: Annotated[ValueESRepository, Depends(get_value_es_repository)],
) -> QueryService:
    """组装一次查询所需的业务服务"""

    # QueryService 只接收已经创建好的依赖对象，不关心这些对象具体来自哪里
    return QueryService(
        meta_mysql_repository=meta_mysql_repository,
        embedding_client=embedding_client,
        dw_mysql_repository=dw_mysql_repository,
        column_qdrant_repository=column_qdrant_repository,
        metric_qdrant_repository=metric_qdrant_repository,
        value_es_repository=value_es_repository,
    )
```

This is the value of FastAPI sub-dependencies: we only declare the dependency relationships, and FastAPI automatically resolves the entire dependency tree upward from the leaf nodes.

## 5. lifespan.py: Preparing External Clients at Application Startup

`dependencies.py` can obtain `qdrant_client_manager.client` and `es_client_manager.client` only if these managers have already been initialized.

Therefore, the following must be executed during the application startup phase:

```python
qdrant_client_manager.init()
embedding_client_manager.init()
es_client_manager.init()
meta_mysql_client_manager.init()
dw_mysql_client_manager.init()
```

Project file path: `shopkeeper-agent/app/api/lifespan.py`

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.clients.embedding_client_manager import embedding_client_manager
from app.clients.es_client_manager import es_client_manager
from app.clients.mysql_client_manager import (
    dw_mysql_client_manager,
    meta_mysql_client_manager,
)
from app.clients.qdrant_client_manager import qdrant_client_manager


@asynccontextmanager
async def lifespan(app: FastAPI):
    """管理应用启动和关闭两个阶段的外部资源"""

    # 启动阶段：先建立各类外部服务客户端，后续依赖函数会从 manager 中取已初始化对象
    qdrant_client_manager.init()
    embedding_client_manager.init()
    es_client_manager.init()
    meta_mysql_client_manager.init()
    dw_mysql_client_manager.init()

    # yield 之前是启动逻辑，yield 之后是关闭逻辑；中间阶段由 FastAPI 正常处理请求
    yield

    # 关闭阶段：统一释放外部连接，避免进程退出前留下未关闭的网络连接
    await qdrant_client_manager.close()
    await es_client_manager.close()
    await meta_mysql_client_manager.close()
    await dw_mysql_client_manager.close()
```

Looking at it according to `yield`:

```text
yield 前：
  FastAPI 应用启动时执行
  初始化 Qdrant、Embedding、ES、MySQL 客户端管理器

yield 处：
  应用进入运行状态
  开始接收请求

yield 后：
  应用关闭前执行
  释放外部客户端连接
```

Note that `embedding_client_manager` is not closed here, because the current project code only provides asynchronous shutdown logic for the Qdrant, ES, and MySQL managers. The documentation follows the actual code and does not fabricate additional shutdown methods.
