In the previous chapter, we already persisted table information and field information into `Meta MySQL`. What that step solves is: **the system first has a stable, structured set of field metadata.** But structured metadata alone is not enough. That is because what the data Q&A system will face later is not standard SQL hand-written by programmers, but natural language questions from users.

For example, users may ask questions like: calculate the total sales amount for Hebei Province; query the number of orders placed by gold members; calculate sales volume for the digital category; look at the order amount in the North China region; what is the recent `GMV`; how to interpret `AOV`.

Three types of information appear in these questions at the same time: one type is expressions such as "total sales amount," "order amount," and "category," which are more like field meanings; another type is expressions such as "Hebei Province," "gold member," "digital," and "North China," which are more like actual field values; and yet another type is `GMV`, `AOV`, and average order value, which are more like business metrics. This means that what the system needs to solve later is not a single "field retrieval" problem, but three things that work together: identifying which field an expression is semantically closer to, determining whether something is an actual value of a given field, and determining whether something is a business metric that has already been defined in the system.

Therefore, starting from this chapter, we bring together the previously scattered field and metric chains and understand the entire main line uniformly from the higher-level perspective of "building field and metric retrieval capabilities."

## 1. Why Field Retrieval Cannot Rely on a Single Capability

Let us begin with a concrete question: a field vector index can help the system find a field, but it cannot guarantee that the values in filter conditions will be written correctly.

If the system only builds a field vector index, what it is good at solving is: whether "sales amount" resembles `order_amount`; whether "member level" resembles `member_level`; whether "region" resembles `region_name`. In other words, it is good at **field semantic recall**.

But if the user's question is "calculate the total sales amount for Hebei Province," even if the system already knows that "total sales amount" is more like `order_amount` and that "Hebei Province" is most likely related to the region field, there is still one critical unresolved question: **does the database actually store "Hebei" or "Hebei Province"?**

If this question is not answered accurately, the SQL generated later can easily be wrong. For example, consider the following SQL:

```sql
select sum(order_amount)
from fact_order
join dim_region on fact_order.region_id = dim_region.region_id
where province = '河北省'
```

If the actual data warehouse stores "Hebei," then this SQL is syntactically correct, but the result will be wrong.

Therefore, field values must also have a separate retrieval chain. What it needs to solve is:

- Whether "North China" is an actual value of some field
- Whether "gold member" is a value that actually exists in some field
- Which field's value domain "digital" should fall into

That is to say, the vector index answers: **which field does it resemble**, while the full-text index answers: **is it an actual value in this field**. This also shows that although the field vector index and the field value full-text index are two different implementation chains, they essentially serve the same larger goal: **making the field retrieval capability truly complete.**

## 3. Part One: Building the Field Vector Index

The problem the field vector index is meant to solve is: **how to enable semantic retrieval over field information.**

### 3.1 Main Pipeline of the Field Vector Index

Project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def _save_column_info_to_qdrant(self, column_infos: list[ColumnInfo]):
    await self.column_qdrant_repository.ensure_collection()

    # 暂存“待向量化文本 + 业务 payload”，此时还不是 Qdrant 的 PointStruct
    points: list[dict] = []
    for column_info in column_infos:
        points.append(
            {
                # 一个字段会拆成多个 point，所以 point id 不能直接复用 column_info.id
                "id": uuid.uuid4(),
                # 字段名也作为一个语义入口，例如 order_amount
                "embedding_text": column_info.name,
                # payload 保存完整字段上下文，方便检索命中后直接使用
                "payload": asdict(column_info),
            }
        )

        points.append(
            {
                "id": uuid.uuid4(),
                # 字段描述更接近用户自然语言表达，例如“订单金额”
                "embedding_text": column_info.description,
                "payload": asdict(column_info),
            }
        )

        for alia in column_info.alias:
            points.append(
                {
                    "id": uuid.uuid4(),
                    # 每个别名单独建 point，用来覆盖“销售额”“成交金额”等不同说法
                    "embedding_text": alia,
                    "payload": asdict(column_info),
                }
            )

    embeddings: list[list[float]] = []
    embedding_texts = [point["embedding_text"] for point in points]
    # 分批调用 Embedding，避免单次请求过大
    embedding_batch_size = 20
    for i in range(0, len(embedding_texts), embedding_batch_size):
        batch_embedding_texts = embedding_texts[i : i + embedding_batch_size]
        # 返回顺序要和输入文本顺序一致，后面才能和 id、payload 对齐
        batch_embeddings = await self.embedding_client.aembed_documents(
            batch_embedding_texts
        )
        embeddings.extend(batch_embeddings)

    ids = [point["id"] for point in points]
    payloads = [point["payload"] for point in points]

    # 最终写入 Qdrant：id + vector + payload
    await self.column_qdrant_repository.upsert(ids, embeddings, payloads)
```

This code does four things:

1. First make sure the collection in `Qdrant` used for storing field vectors exists
2. Split each field into multiple points to be vectorized
3. Call the `Embedding` service to generate vectors in batches
4. Write `id`, `embedding`, and `payload` together into `Qdrant`

![A field is split into multiple vector records by field name, description, and aliases](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/9/9-3-2-1.png)

### 3.2 Why a Single Field Does Not Generate Only One Point

This is the core design of the field vector index: a field does not create only one point; instead, multiple semantic entry points are created around that field.

For example, consider a field:

- Field name: `order_amount`
- Description: order amount
- Aliases: sales amount, transaction amount, total order amount

If you only create one vector point for `order_amount`, then when users later say "sales amount," it may not necessarily be recalled easily.  
Therefore, the current implementation uses:

- One point for the field name
- One point for the field description
- One point for each field alias

The purpose of this is to allow as many different natural language expressions as possible to recall the same field.

To describe this process more concretely, a `ColumnInfo` is often first expanded into an intermediate set of data like this:

```python
# 同一个字段会被拆成多个语义入口，但 payload 都指向同一个 ColumnInfo
[
    {
        # 字段名入口
        "id": "随机 point id 1",
        "embedding_text": "order_amount",
        "payload": {...完整 column_info...},
    },
    {
        # 字段描述入口
        "id": "随机 point id 2",
        "embedding_text": "订单金额",
        "payload": {...完整 column_info...},
    },
    {
        # 字段别名入口
        "id": "随机 point id 3",
        "embedding_text": "销售额",
        "payload": {...完整 column_info...},
    },
    {
        # 另一个字段别名入口
        "id": "随机 point id 4",
        "embedding_text": "成交金额",
        "payload": {...完整 column_info...},
    },
]
```

The most important thing about this example is not what the dictionary looks like, but to first establish a clear understanding: **the system is not performing a single-point vectorization of a "field"; it is separately vectorizing multiple semantic entry points of the field.**

In this way, when users later say "sales amount," "order amount," or "transaction amount," although the wording differs, each has a chance to hit the same business field.

### 3.3 Reviewing Four Qdrant Concepts

When studying this section, it is easy to get stuck not on the business logic, but on a few basic concepts of `Qdrant`.

Grasp these four words: `collection` can be compared to a collection table in a vector database, `point` is an actual record written into `Qdrant`, `vector` is the numerical representation of a piece of text after encoding by a vector model, and `payload` is the business data stored together with the vector.

In the current project:

- `embedding_text` ultimately becomes `vector`
- `asdict(column_info)` ultimately becomes `payload`

That is to say, what is stored in the vector database is not just an isolated string of vectors, but "vector + complete field context."

If we restate these four concepts in a sentence closer to the code, it is:

```text
一个字段
  -> 拆成多个 point
  -> 每个 point 先有一段 embedding_text
  -> embedding_text 被编码成 vector
  -> vector 和 payload 一起写入同一个 collection
```

Many students, when first reading `Qdrant`, tend to confuse `point` with `payload`. They are not on the same level: `point` is the entire vector record, and `payload` is the business information attached to that vector record. In other words, `payload` is part of `point`, not something parallel to `point`.

If we simplify and draw what is actually written into a `Qdrant` point, it would look roughly like this:

```python
PointStruct(
    # point 自己的存储 ID，不等同于字段 ID
    id="0b7f...",
    # embedding_text 编码后的向量，检索时主要比较它
    vector=[0.12, -0.08, ...],
    # 命中后返回给业务层的字段上下文
    payload={
        "id": "fact_order.order_amount",
        "name": "order_amount",
        "description": "订单金额",
        "table_id": "fact_order",
        ...
    },
)
```

With this understanding, it becomes very clear: what vector retrieval actually compares is `vector`, but after a hit, what is most valuable to the business is the field context brought back in `payload`.

### 3.4 Why uuid Is Used for Point IDs

Here, `id` does not directly reuse `column_info.id`; instead:

```python
# 为每个向量 point 单独生成唯一 ID，避免同一字段拆成多个 point 时互相覆盖
uuid.uuid4()
```

The reason is simple: one field is split into multiple points. If you directly use `column_info.id`, then the same field name, field description, and field alias would conflict.

Therefore, a more reasonable approach is: **the field itself maintains a stable field ID, while each point separately generates its own unique point ID.**

There are two different sets of identifiers here: `column_info.id` represents the stable identity of the business field itself, and `point.id` represents the storage identity of a particular vector point. These two coexist without conflict; in fact, they solve problems at two different levels: the business layer needs to know "which field this actually is," while the vector database storage layer needs to know "which point this actually is."

This is also why `payload` keeps the field's own `id` instead of deleting the field's `id` just because `point.id` already exists externally.

### 3.5 Why the Entire ColumnInfo Is Stored Directly in payload

In the current implementation:

```python
# 把 ColumnInfo 转成普通字典，作为 Qdrant payload 随向量一起保存
"payload": asdict(column_info)
```

It does not store only the field name, nor only a small fragment; it stores the entire dictionary representation of `ColumnInfo` directly.

The benefit of doing this is that after a later vector retrieval hit, the system can directly retrieve the complete field context without needing to go elsewhere to assemble information such as the field description, field role, and owning table.

From a storage perspective, this does introduce a small amount of "information redundancy," because for multiple points split from the same field, most of the `payload` content is the same; only `embedding_text` differs.

But here the project clearly prioritizes something else: **a simple query chain.** Because once a point is hit later, the system can immediately obtain complete field information, without needing to perform the extra step of "first locating the point, then querying MySQL again by field ID to supplement the missing information."

For the main line in this tutorial, this design is very worthwhile: store a bit more duplicated information during writing, so that one fewer assembly step is required during reading.

### 3.6 What ColumnQdrantRepository Is Responsible for in This Chain

Project file path: `shopkeeper-agent/app/repositories/qdrant/column_qdrant_repository.py`

```python
class ColumnQdrantRepository:
    # 字段向量统一写入这个 collection
    collection_name = "column_info_collection"

    def __init__(self, client: AsyncQdrantClient):
        self.client = client

    async def ensure_collection(self):
        if not await self.client.collection_exists(self.collection_name):
            await self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    # 必须和 Embedding 模型输出维度一致
                    size=app_config.qdrant.embedding_size,
                    # 用余弦距离衡量文本语义相似度
                    distance=Distance.COSINE,
                ),
            )

    async def upsert(
        self,
        ids: list[str],
        embeddings: list[list[float]],
        payloads: list[dict],
        batch_size: int = 10,
    ):
        # 三个列表必须保持同一顺序，才能正确拼成 Qdrant 需要的向量记录
        points: list[PointStruct] = [
            PointStruct(id=id, vector=embedding, payload=payload)
            for id, embedding, payload in zip(ids, embeddings, payloads)
        ]
        for i in range(0, len(points), batch_size):
            await self.client.upsert(
                collection_name=self.collection_name,
                # 分批写入，降低单次 upsert 压力
                points=points[i : i + batch_size],
            )
```

This repository layer is mainly responsible for two things:

1. Make sure the collection field is already created
2. Write the prepared vector points stably into `Qdrant`

The responsibility boundary here is also very clear: `Service` decides which points a field should be split into, and `Repository` is responsible for collection creation and batch storage.

There are two more implementation details worth understanding here.

The first detail is this configuration in `ensure_collection()`:

```python
VectorParams(
    # collection 的向量维度必须和 Embedding 输出维度一致
    size=app_config.qdrant.embedding_size,
    # 字段语义召回通常用余弦距离比较文本向量相似度
    distance=Distance.COSINE,
)
```

It shows that when a collection is created, two key constraints have already been determined: what the vector dimension is, and how similarity is compared.

The `size` here must remain consistent with the output dimension of the embedding model you actually use; otherwise, errors will occur later when writing vectors.
The `Distance.COSINE` here indicates that later similarity retrieval will mainly use cosine similarity to compare whether "the direction of two vectors is close."

The second detail is this line in `upsert()`:

```python
# 按相同下标把 id、向量、payload 重新拼回一个 point
for id, embedding, payload in zip(ids, embeddings, payloads)
```

Its meaning is not complicated, but it is important: although the preceding `Service` layer maintains three lists separately — `ids`, `embeddings`, `payloads` — before actually storing data, they must be reassembled one-to-one by the same index to form a complete `PointStruct`.

It is easier to understand this pipeline in order:

```text
中间结构 points
  -> 抽出 embedding_texts 批量做向量化
  -> 得到 embeddings
  -> 再和 ids / payloads 按相同顺序拼回完整 point
  -> PointStruct
  -> Qdrant
```

If you keep this step clear in your mind, then later when you look at `zip(...)`, you will not think of it as just a "syntactic trick"; you will understand that it performs the responsibility of "reassembling parallel arrays back into complete vector points."

### 3.7 Why both embedding and upsert need batching

There are two "batching" actions here: one occurs during the vectorization stage, and the other occurs when vectors are written into storage. The former is to reduce the call pressure on the model service, and the latter is to reduce the write pressure on the vector database. Together, they make the construction pipeline more stable.

Therefore, this implementation pipeline is better understood in this order: "first collect points -> then batch embedding -> finally batch upsert." Treating these two batching actions as two different "pressure-relief valves" makes the whole process much easier to grasp.

For example, suppose there are `53` texts to be vectorized. If embedding processes `20` per batch, it may be split into `20 + 20 + 13`; if upsert processes `10` per batch, it may be split into `10 + 10 + 10 + 10 + 10 + 3`.

Although both are called "batching," the pressure they relieve is different: embedding batching mainly reduces call pressure on the model service, while upsert batching mainly reduces write pressure on the vector database.

This is also why the course code does not send all texts at once for vectorization, nor write all points directly into `Qdrant` in one go.

## 4. Part 2: Building the full-text index for field values

The problem that the full-text index for field values aims to solve is: **how to let the system know which real values in fields can be matched.**

### 4.1 Main flow of the full-text index for field values

Project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def _save_value_info_to_es(
    self, meta_config: MetaConfig, column_infos: list[ColumnInfo]
):
    await self.value_es_repository.ensure_index()

    # 把配置整理成“字段 id -> 是否同步真实值”的快速查询表
    column2sync: dict[str, bool] = {}
    for table in meta_config.tables:
        for column in table.columns:
            # 字段 id 要和 ColumnInfo.id 的拼法保持一致
            column2sync[f"{table.name}.{column.name}"] = column.sync

    value_infos: list[ValueInfo] = []
    for column_info in column_infos:
        # 根据字段 id 判断该字段是否需要同步取值
        sync = column2sync[column_info.id]
        if sync:
            # 从数仓查询该字段的 distinct 真实值，作为全文索引的数据来源
            current_column_values = await self.dw_mysql_repository.get_column_values(
                column_info.table_id, column_info.name, 100000
            )
            current_values_infos = [
                ValueInfo(
                    # 字段 id + 字段值，组成一条值记录的唯一 id
                    id=f"{column_info.id}.{current_column_value}",
                    # 真正参与 ES 全文检索的文本
                    value=current_column_value,
                    # 记录这个值属于哪个字段，方便命中后反查字段上下文
                    column_id=column_info.id,
                )
                for current_column_value in current_column_values
            ]
            value_infos.extend(current_values_infos)

    # Repository 负责把 ValueInfo 转成 ES bulk 写入格式
    await self.value_es_repository.index(value_infos)
```

This code does five things:

1. First ensure that the Elasticsearch index used to store field values exists
2. Read the configuration and find out which fields are allowed to synchronize real values
3. Query the set of real values for these fields from `DW`
4. Wrap each real value into `ValueInfo`
5. Batch write into Elasticsearch

There is also a small action here that is worth understanding separately: first constructing

```python
# 用字段 id 快速判断该字段是否需要同步真实取值
column2sync: dict[str, bool] = {}
```

Then organizing the field synchronization switches from the configuration into:

```python
# key 是字段 id，value 表示这个字段是否需要同步真实取值
{
    "dim_region.region_name": True,
    "dim_region.region_id": False,
    "dim_customer.member_level": True,
}
```

The benefit of doing this is that later, when iterating over `column_infos`, you can directly use `column_info.id` to check whether this field should synchronize real values, without having to go back and nested-loop through the configuration object.

What is done here is a very typical "small index table" action: the original configuration is more suitable for human reading, while `column2sync` is more suitable for quick programmatic judgment. This kind of "first organize the configuration into a dictionary that is easy for the program to use" pattern is very common in engineering code.

### 4.2 Why not all fields should synchronize real values

A clear judgment principle should be established first here: not all fields are worth building a full-text index for. Only those dimension fields that actually appear in user questions are suitable for synchronizing real values into ES.

The corresponding configuration is controlled in `meta_config.yaml` through `sync`:

```yaml
columns:
  - name: province
    role: dimension
    sync: true

  - name: region_id
    role: primary_key
    sync: false
```

The meaning is very direct: `sync: true` means the real values of this field should go into ES, and `sync: false` means this field will not have a full-text index for field values.

Why can't all fields be synchronized? Because primary keys, foreign keys, and technical identifier fields generally will not be key values in natural language questions. If all of them were synchronized as well, it would only add noise.

This should be considered in the context of how users actually ask questions. Users are more likely to say "North China region," "Gold member," "Digital category," "Hebei Province," rather than "region_id equals 3," "customer_id equals 10086," "product_id equals 7788."

Therefore, what is suitable for synchronizing into ES is usually "business values that people will directly say in questions," not "technical values used internally by the system for association and identification."

### 4.3 What you actually get when querying real field values from DW

Project file path: `shopkeeper-agent/app/repositories/mysql/dw/dw_mysql_repository.py`

```python
async def get_column_values(self, table_name: str, column_name: str, limit: int = 10):
    # distinct 只取值域，不取重复明细行
    sql = f"select distinct {column_name} from {table_name} limit {limit}"
    result = await self.session.execute(text(sql))
    # 返回单列结果列表，例如 ["华北", "华东", "华南"]
    return result.scalars().fetchall()
```

Two points need attention here:

- What is queried is the set of distinct values for a certain field
- It will first apply `distinct`

That is to say, what is obtained here is not raw detail records, but a sample of the field's value domain. In fact, in the field-value full-text index step, a sufficiently large `limit` is used to collect as much of the complete real value set as possible.

If this is still a bit abstract, you can directly translate it into concrete SQL to see.

Suppose the current field is `dim_region.region_name`; then the query is roughly:

```sql
select distinct region_name from dim_region limit 100000
```

The returned result might be:

```python
# dim_region.region_name 的去重值列表
["华北", "华东", "华南", "西南"]
```

For another example, if the field is `dim_customer.member_level`, the query is roughly:

```sql
select distinct member_level from dim_customer limit 100000
```

The returned result might be:

```python
# dim_customer.member_level 的去重值列表
["黄金会员", "白银会员", "铂金会员"]
```

This makes it easier to understand: what this Repository layer retrieves is not "rows," but "a list of values."

This also illustrates an implementation premise: the distinct values of dimension fields are usually limited and controllable, so using a sufficiently large `limit` to approximate the full value set is an acceptable simplification here.

### 4.4 Why wrap values into ValueInfo first

Project file path: `shopkeeper-agent/app/entities/value_info.py`

```python
@dataclass
class ValueInfo:
    # 字段值记录的唯一标识，通常由 column_id + value 拼出来
    id: str
    # 字段真实值，例如“华北”“黄金会员”“数码”
    value: str
    # 这个真实值所属的字段，例如 dim_region.region_name
    column_id: str
```

Its role can be summarized in one sentence: **organize real field values into a data object that flows uniformly within the system.** These three fields respectively represent: `id` is the unique identifier of this field value record, `value` is the real field value, and `column_id` indicates which field this value belongs to.

The `id` here will be concatenated as:

```python
# 用“字段 id + 字段值”组成 ES 文档唯一 ID
f"{column_info.id}.{current_column_value}"
```

For example: `dim_region.region_name.华北`, `dim_customer.member_level.黄金`, `dim_product.category.数码`.

In this way, uniqueness is guaranteed while the field context is naturally preserved.

Wrapping these into `ValueInfo` first, rather than directly piecing together an ES dictionary and writing it, also has a very practical engineering benefit: **separating the "business object" from the "storage format."**

It can be viewed as two stages:

1. First, at the business layer, clarify what information this field-value record actually contains
2. Then, at the Repository layer, clarify how this information should be written into ES

The benefit of writing it this way is that later, even if you do not write these field values into ES but instead want to process them for other purposes, the `ValueInfo` object itself can still be reused.

### 4.5 What ValueESRepository is responsible for in this pipeline

Project file path: `shopkeeper-agent/app/repositories/es/value_es_repository.py`

```python
class ValueESRepository:
    # 字段真实值统一写入这个 ES index
    index_name = "value_index"
    index_mappings = {
        # 关闭动态映射，避免写入时偷偷生成不可控字段
        "dynamic": False,
        "properties": {
            # 唯一标识只需要精确匹配，不需要分词
            "id": {"type": "keyword"},
            "value": {
                # 真实业务值要支持全文检索，所以使用 text
                "type": "text",
                # 写入时使用中文分词器建立倒排索引
                "analyzer": "ik_max_word",
                # 查询时使用同一套分词逻辑，提高匹配稳定性
                "search_analyzer": "ik_max_word",
            },
            # 字段 id 用来精确定位所属字段，不需要分词
            "column_id": {"type": "keyword"},
        },
    }

    def __init__(self, client: AsyncElasticsearch):
        self.client = client

    async def ensure_index(self):
        if not await self.client.indices.exists(index=self.index_name):
            await self.client.indices.create(
                index=self.index_name, mappings=self.index_mappings
            )

    async def index(self, value_infos: list[ValueInfo], batch_size=20):
        if not value_infos:
            return

        # 分批写入 ES，降低单次 bulk 请求压力
        for i in range(0, len(value_infos), batch_size):
            batch_value_infos = value_infos[i : i + batch_size]
            # ES bulk 需要“操作描述 + 文档内容”交替排列
            batch_operations = []
            for value_info in batch_value_infos:
                # 先告诉 ES：下一条文档要 index 到哪个索引、使用哪个 _id
                batch_operations.append(
                    {"index": {"_index": self.index_name, "_id": value_info.id}}
                )
                # 再追加真正的文档内容
                batch_operations.append(asdict(value_info))
            await self.client.bulk(operations=batch_operations)
```

This repository layer is mainly responsible for two things:

1. Ensure that the field value index exists
2. Batch write `ValueInfo` into ES

The responsibility division here is also very clear: `Service` is responsible for preparing "which values should be written in," and `Repository` is responsible for handling "how ES should be built and written."

Breaking down the internal actions of the Repository, there are two steps:

1. `ensure_index()`: first prepare the index structure
2. `index()`: then write `ValueInfo` batch by batch

This breakdown is very similar to the approach used earlier in the Qdrant pipeline: first ensure the collection exists, then perform batch upsert. Whether it is a vector database or a full-text index store, the same engineering habit is followed here: **prepare the storage container first, then write data in batches.**

### 4.6 Why the mapping is designed this way

The most valuable ES concept to establish here is this: **whether field values can be correctly full-text searched depends heavily on the mapping.**

The most critical parts of the current mapping are four:

1. `dynamic: false`
   Disable dynamic mapping to keep the index structure stable

2. `id: keyword`
   Because `id` is only a unique identifier and does not need tokenization

3. `column_id: keyword`
   Because it only precisely points to the owning field, and also does not need tokenization

4. `value: text + ik_max_word`
   Because this field is the one that actually needs full-text search, it must use the `text` type and a Chinese tokenizer.

The judgment logic here can be remembered directly:  
If a field needs to support full-text search, it must be of type `text`; while `keyword` is more suitable for exact matching and is not appropriate for this kind of natural language value matching scenario.

There is also a detail worth establishing here: `analyzer` controls how documents are tokenized when written, and `search_analyzer` controls how queries are tokenized. In the current implementation, both are set to `ik_max_word`, meaning that field values are segmented according to the same set of Chinese tokenization rules when written to the index, and user queries for these values are segmented according to the same set of Chinese tokenization rules as well. Once the tokenization logic on the write side and the query side remains consistent, retrieval results usually become more stable.

### 4.7 Why bulk operations use an alternating "operation + data" structure

This is also one of the places in ES where beginners most easily get confused.

In the current batch write code, what is actually passed to `bulk` is:

```python
# 操作行：告诉 ES 写入目标和文档 _id
batch_operations.append(
    {"index": {"_index": self.index_name, "_id": value_info.id}}
)
# 数据行：紧跟在操作行后面，表示要写入的文档内容
batch_operations.append(asdict(value_info))
```

It is not a simple "list of data objects", but rather a set of alternating structures: the previous item tells ES what operation to perform next, and the next item tells ES what data corresponds to that operation. This is also why the `operations` here is not a normal list but must use this alternating structure.

If we actually expand two `ValueInfo` entries, it becomes more intuitive:

```python
# ES bulk 里每条文档都由“操作行 + 数据行”组成
[
    # 操作行：声明下一条文档写入哪个索引、使用哪个 _id
    {"index": {"_index": "value_index", "_id": "dim_region.region_name.华北"}},
    # 数据行：真正写入的 ValueInfo 内容
    {
        "id": "dim_region.region_name.华北",
        "value": "华北",
        "column_id": "dim_region.region_name",
    },
    # 第二条文档同样遵循“操作行 + 数据行”的结构
    {"index": {"_index": "value_index", "_id": "dim_customer.member_level.黄金会员"}},
    {
        "id": "dim_customer.member_level.黄金会员",
        "value": "黄金会员",
        "column_id": "dim_customer.member_level",
    },
]
```

You can understand it by thinking of it as an alternating structure of "command line + parameter", "command line + parameter".

## 5. How the two field retrieval chains actually work together

Up to this point, we have fully connected the field retrieval capability. A complete construction of the field-side retrieval capability is essentially about performing two different enhancements around the same batch of `column_infos`:

1. The vector index advances fields into "semantic recall".
2. The full-text index advances fields into "real value matching".

If only vector indexing is done, the system becomes good at finding "fields" but not good at confirming "values"; if only full-text indexing is done, the system becomes good at finding "real values" but not good at handling field-level semantic expressions such as "sales amount", "order amount", or "total transaction amount". Only when both exist at the same time can the later NL2SQL generation stage have the chance to obtain both the correct field candidates and the correct real field value candidates at the same time.

This is also why field vector indexing and field value full-text indexing are more suitable to be understood together in the same chapter. They are not two competing technical solutions, but rather each complements a different direction of retrieval capability around the same batch of field metadata.

## 6. Why metrics must also enter the same metadata knowledge base

If only tables, fields, and field values are built into the knowledge base, the system can certainly already answer many questions, but it still lacks one very critical type of object: **metrics.**

For example, the following expressions: `GMV`, `AOV`, total transaction amount, average order amount.

They are different from fields. Fields are usually atomic attributes in the data warehouse, such as `order_amount` or `order_quantity`; metrics are more like the statistical definitions that are actually used in business analysis discussions. For humans, `GMV` is a very familiar word, but for the system, if you do not explicitly write it into the metadata knowledge base, the model will not naturally know: what this metric means; which underlying fields it is related to; and when a user says "total transaction amount", whether they are talking about a field or a metric.

Therefore, this chapter must take one more step forward: **formally accumulate metrics as knowledge objects, and then build their own semantic recall capability.**

In the current configuration file, metric definitions are placed under `metrics`:

Corresponding project file path: `shopkeeper-agent/conf/meta_config.yaml`

```yaml
metrics:
  - name: GMV
    description: 全称Gross Merchandise Value，表示所有订单的成交金额总和。
    relevant_columns:
      - fact_order.order_amount
    alias: [成交总额, 订单总额]
  - name: AOV
    description: 全称Average Order Value，表示所有订单的成交金额平均值。
    relevant_columns:
      - fact_order.order_quantity
    alias: [平均单价, 平均订单金额]
```

The key fields to focus on here are three:

- `name`: metric name
- `description`: metric definition and definitional scope
- `relevant_columns`: which underlying fields this metric is directly related to

At this point, you can first establish an intuition: fields solve "what raw attributes exist in the database", while metrics solve "which high-frequency statistical objects exist in business analysis". Both types of objects should enter the knowledge base, but the way they are organized is not exactly the same.

## 7. First write metric information and field relationships into Meta MySQL

### 7.1 Main process for writing metric information into the database

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def _save_metrics_to_meta_db(
    self, meta_config: MetaConfig
) -> list[MetricInfo]:
    metric_infos: list[MetricInfo] = []
    column_metrics: list[ColumnMetric] = []

    for metric in meta_config.metrics:
        metric_info = MetricInfo(
            # 当前实现里直接用指标名作为稳定 ID
            id=metric.name,
            name=metric.name,
            description=metric.description,
            relevant_columns=metric.relevant_columns,
            alias=metric.alias,
        )
        metric_infos.append(metric_info)

        for column in metric.relevant_columns:
            column_metric = ColumnMetric(column_id=column, metric_id=metric.name)
            column_metrics.append(column_metric)

    # 指标信息和字段关联关系要放在同一笔事务里，避免只写进去一半
    async with self.meta_mysql_repository.session.begin():
        self.meta_mysql_repository.save_metric_infos(metric_infos)
        self.meta_mysql_repository.save_column_metrics(column_metrics)

    return metric_infos
```

This code does 4 things:

1. Iterate over the `metrics` in the configuration.
2. Organize each metric into `MetricInfo`.
3. Organize the relationships between metrics and underlying fields into `ColumnMetric`.
4. Write both `metric_info` and `column_metric` uniformly within the same transaction.

What deserves the most attention in this code is not the writing style, but the fact that it persists two types of data at once: one type is "what the metric itself is", and the other is "what relationships exist between the metric and fields".

### 7.2 Why do we need both MetricInfo and ColumnMetric

First look at these two business entities:

Corresponding project file paths:

- `shopkeeper-agent/app/entities/metric_info.py`
- `shopkeeper-agent/app/entities/column_metric.py`

```python
@dataclass
class MetricInfo:
    # 指标唯一标识，当前实现直接使用指标名
    id: str
    name: str
    description: str
    relevant_columns: list[str]
    alias: list[str]


@dataclass
class ColumnMetric:
    column_id: str
    metric_id: str
```

`MetricInfo` is responsible for expressing "what this metric itself is", while `ColumnMetric` is responsible for expressing "which fields this metric is related to". These two layers of information cannot be mixed into a single flat table.

The reason is simple: the relationship between metrics and fields is not a simple one-to-one relationship in the first place. One metric may depend on multiple fields, and one field may also be reused by multiple metrics. Therefore, separately extracting the `ColumnMetric` relationship object here is essentially telling the system that: **a metric is not an isolated piece of descriptive text, but also carries a traceable layer of field dependency relationships.**

### 7.3 Why MetricInfo.id directly uses the metric name

This is somewhat different from the field chain. Fields need to use the `table.column` form to distinguish fields with the same name; in the metric configuration, `name` is already required to have business uniqueness, so the current implementation directly uses:

```python
# 指标名本身就是当前配置里的唯一业务标识
id=metric.name
```

For example: `GMV`, `AOV`.

The benefit of this step is that it is simple and direct. Later, whether writing to the metadata database, building vector indexes, or performing metric recall, this stable metric ID will continue to be used.

### 7.4 What the Meta Repository undertakes in this part

Corresponding project file path: `shopkeeper-agent/app/repositories/mysql/meta/meta_mysql_repository.py`

```python
def save_metric_infos(self, metric_infos: list[MetricInfo]):
```

The division of roles here is exactly the same as in Chapter 8 earlier: `Service` decides which business entities should be written in this round and which writes should be placed in the same transaction; `Repository` is responsible for translating these business entities into ORM models and then handing them to `session.add_all(...)` for persistence. When it comes to metrics, the overall engineering layering has not changed, only two new types of business objects have been added.

## 8. Then build a vector index for metric information

### 8.1 Main process for the metric vector index

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def _save_metrics_to_qdrant(self, metric_infos: list[MetricInfo]):
    await self.metric_qdrant_repository.ensure_collection()

    points: list[dict] = []
    for metric_info in metric_infos:
        points.append(
            {
                # 一个指标会拆成多个 point，所以每个 point 都需要独立 ID
                "id": uuid.uuid4(),
                "embedding_text": metric_info.name,
                "payload": asdict(metric_info),
            }
        )

        points.append(
            {
                "id": uuid.uuid4(),
                "embedding_text": metric_info.description,
                "payload": asdict(metric_info),
            }
        )

        for alia in metric_info.alias:
            points.append(
                {
                    "id": uuid.uuid4(),
                    "embedding_text": alia,
                    "payload": asdict(metric_info),
                }
            )

    embeddings: list[list[float]] = []
    embedding_texts = [point["embedding_text"] for point in points]
    embedding_batch_size = 20
    for i in range(0, len(embedding_texts), embedding_batch_size):
        batch_embedding_texts = embedding_texts[i : i + embedding_batch_size]
        # 返回顺序要和输入文本顺序一致，后面才能和 id、payload 对齐
        batch_embeddings = await self.embedding_client.aembed_documents(
            batch_embedding_texts
        )
        embeddings.extend(batch_embeddings)

    ids = [point["id"] for point in points]
    payloads = [point["payload"] for point in points]

    await self.metric_qdrant_repository.upsert(ids, embeddings, payloads)
```

The main line of the metric vector index is basically parallel to that of the field vector index:

1. First ensure that the metric's own collection exists.
2. Split each metric into semantic entry points such as name, description, and aliases.
3. Call the Embedding service to generate vectors in batches.
4. Write `id`, `embedding`, and `payload` into Qdrant together.

### 8.2 Why metrics should also be split into multiple points

The reason is exactly the same as for fields: when users express a metric, they may not directly say the standard metric name. For example, for the metric `GMV`, users may say: `GMV`, total transaction amount, or order total.

If you only create one vector point for the name `GMV`, then later when a user says "total transaction amount", it may not necessarily be recalled stably. Therefore, in the current implementation, one metric will also be split into multiple points around "metric name + metric description + metric aliases".

The essence of this step is the same as the field vector index: **it is not about creating only one point for the object itself, but about creating separate points for multiple semantic entry points of the object.**

### 8.3 Why metrics should be placed in a separate collection

This must be emphasized separately: metric vectors cannot be mixed with field vectors in the same collection.

Although both fields and metrics perform semantic retrieval, they are two different types of objects:

- Fields solve "what raw attributes exist".
- Metrics solve "what business statistical definitions exist".

Later, when the system performs recall, it should naturally be able to distinguish "am I looking for a field this time" or "am I looking for a metric this time". Therefore, the most natural approach is to give each of them its own independent collection.

Corresponding project file path: `shopkeeper-agent/app/repositories/qdrant/metric_qdrant_repository.py`

```python
# 指标向量写入独立的指标 collection
class MetricQdrantRepository:
    collection_name = "metric_info_collection"
```

This forms a one-to-one correspondence with the field vector repository here:

```python
# 字段向量写入独立的字段 collection
collection_name = "column_info_collection"
```

They correspond exactly to each other.

### 8.4 What MetricQdrantRepository is responsible for in this chain

Corresponding project file path: `shopkeeper-agent/app/repositories/qdrant/metric_qdrant_repository.py`

```python
class MetricQdrantRepository:
    collection_name = "metric_info_collection"

    def __init__(self, client: AsyncQdrantClient):
        self.client = client

    async def ensure_collection(self):
        if not await self.client.collection_exists(self.collection_name):
            await self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    # 必须和 Embedding 模型输出维度一致
                    size=app_config.qdrant.embedding_size,
                    # 指标语义召回同样使用余弦距离比较文本向量相似度
                    distance=Distance.COSINE,
                ),
            )

    async def upsert(
        self,
        ids: list[str],
        embeddings: list[list[float]],
        payloads: list[dict],
        batch_size: int = 10,
    ):
        # 按相同下标把 id、向量、payload 重新拼回完整 point
        zipped = list(zip(ids, embeddings, payloads))
        for i in range(0, len(zipped), batch_size):
            batch = zipped[i : i + batch_size]
            batch_points = [
                PointStruct(id=id, vector=embedding, payload=payload)
                for id, embedding, payload in batch
            ]
            await self.client.upsert(
                collection_name=self.collection_name, points=batch_points
            )
```

What it is responsible for is almost the same as the field repository layer:

- `ensure_collection()`: prepare the metric collection.
- `upsert()`: stably write the already prepared metric vector points into Qdrant.

This also illustrates a clear engineering pattern: although fields and metrics are two different business chains, their organization at the storage layer is highly consistent.

## 10. Condensing the entire pipeline into one sentence

If after reading this chapter you want to remember only one high-frequency summary, it can be condensed into the following sentence: **The essence of building field and metric retrieval capabilities is to further advance metadata configuration into searchable, associable, and verifiable knowledge objects.**

Expanding on that a little:

```text
表与字段信息
  -> 写入 Meta MySQL

字段信息
  -> 拆成多个语义点
  -> 向量化后写入 Qdrant

字段真实值
  -> 封装成 ValueInfo
  -> 全文索引后写入 Elasticsearch

指标信息与字段关系
  -> 写入 Meta MySQL

指标信息
  -> 拆成多个语义点
  -> 向量化后写入 Qdrant
```

The first three pipelines address "how fields and field values can be correctly recalled," while the last two address "how metrics can be understood by the system and associated with underlying fields."

---

**Chapter Summary:**

- The field vector index addresses the question of "which field does it resemble," allowing field names, field descriptions, and field aliases to participate in semantic recall.
- The field value full-text index addresses the question of "whether it is an actual field value," allowing business values such as `华北地区`, `黄金会员`, and `数码` to be matched accurately.
- Metric information ingestion addresses the question of "what the metric itself is and which fields it depends on"; `MetricInfo` stores metric definitions, and `ColumnMetric` stores the relationships between metrics and fields.
- The metric vector index addresses the question of "which metric does it resemble," allowing different expressions such as `GMV`, `成交总额`, and `平均订单金额` to be recalled to the corresponding metric.
- `Service` is responsible for orchestrating the entire build process, `Meta Repository` for structured data persistence, `Qdrant Repository` for field and metric vector persistence, `ES Repository` for field value full-text index persistence, and `DW Repository` for querying actual field values.

At this point, the main thread of the metadata knowledge base has essentially been tied together. When we later truly enter the implementation phase of the data Q&A agent, the reason the system can organize context around tables, fields, field values, and metrics is precisely because of the foundation built in this chapter together with the previous chapters.
