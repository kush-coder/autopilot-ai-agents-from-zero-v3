## 1. Project Directory Structure

Before starting to write code, let's first clarify one very important thing: **plan the project structure clearly.**

In the current repository, the core structure of the backend project `shopkeeper-agent` is as follows:

```text
shopkeeper-agent/
├── app/                  # 后端源码主目录
│   ├── agent/            # 问数智能体与 LangGraph 图流程，例如节点、状态、上下文、图编排
│   ├── api/              # 对外 HTTP 接口层，对应 FastAPI 路由、依赖注入和请求参数结构
│   ├── clients/          # 各类基础服务客户端，例如 MySQL、ES、Qdrant、Embedding 服务
│   ├── conf/             # 配置类与配置加载工具，把 YAML 配置转换成代码可直接使用的对象
│   ├── core/             # 通用基础能力，例如日志、生命周期管理、请求上下文等
│   ├── entities/         # 业务实体定义，承接比 ORM 更贴近业务含义的数据结构
│   ├── models/           # ORM 模型，主要对应 MySQL 中的表结构
│   ├── prompt/           # 提示词加载工具，负责读取和组织静态 Prompt 资源
│   ├── repositories/     # 数据访问层，封装 MySQL / Qdrant / ES 的具体读写逻辑
│   ├── scripts/          # 工具脚本，例如构建元数据知识库、初始化或同步数据
│   └── services/         # 业务逻辑层，负责把客户端、仓储层和智能体能力真正串起来
├── conf/                 # 项目级 YAML 配置文件，例如数据库、向量库、ES、LLM、日志等配置
├── docker/               # 本地开发环境相关文件，例如 docker-compose 和自定义镜像资源
│   ├── elasticsearch/    # Elasticsearch 相关文件，例如 Dockerfile、插件或初始化资源
│   ├── embedding/        # Embedding 服务相关文件，例如模型目录或推理服务配置
│   └── mysql/            # MySQL 初始化 SQL、建表脚本或测试数据导入文件
├── logs/                 # 本地运行时日志输出目录
└── prompts/              # 静态提示词文件，和 app/prompt 中的加载工具配合使用
```

One design principle deserves special attention here:

> All source code is uniformly placed under the `app` package, while "non-source content" such as configuration files and prompts should be kept outside the source code directory as much as possible.

The purpose of doing this is to clearly separate "code" from "configuration / resources" and avoid the project becoming increasingly messy as it grows.

If you have done Java or Spring Boot development before, you can draw the following analogy:

- `api` is somewhat like `controller`
- `services` is somewhat like `service`
- `repositories` is somewhat like `mapper` or `repository`

First establish an overall impression:

- Source code is placed in `app`
- Configuration is placed in `conf`
- Prompts are placed in `prompts`
- Scripts are placed in `app/scripts`

**For this section, remember this:** `app` contains source code, `conf` contains configuration, and `prompts` contains static prompts; later when you encounter concepts like clients, repositories, services, and scripts, first refer back to this structure diagram to find their locations.

## 2. Configuration Parameter Management

Although this chapter belongs to the basic services part, it will not immediately dive into integrating a specific service. Instead, it will first sort out the **configuration parameter management** that all these services depend on in common.

The reason is simple: many components in this project depend on configuration, for example:

- MySQL address, username, and password
- Elasticsearch address
- Qdrant address
- Embedding service address
- The LLM's `API Key`

If these values are hardcoded directly in the source code, there are two obvious problems: whenever the environment changes, the code has to be modified everywhere; and configuration and logic become coupled together, making maintenance inconvenient.

So a more reasonable approach is:

1. Write configuration separately into YAML files
2. Then use a tool to load the YAML configuration into Python objects
3. Subsequent code uniformly accesses configuration items through object attributes

| Service        | Browser access address                                        | Description                                                     |

### 2.2 YAML Quick Start

`YAML` is essentially also a structured data format. It is very similar to `JSON`, and both can express:

- Objects
- Arrays
- Multi-level nested structures

However, the syntax of `YAML` is usually more concise, making it more suitable for manually maintained configuration files.

Online YAML-to-JSON conversion tool: https://tool.ip138.com/yamljson/

For example, if we want to represent an object in `JSON`, it is usually written like this:

```json
{
  "name": "zhangsan",
  "age": 18,
  "height": 1.8
}
```

When converted to `YAML`, it can be written as:

```yaml
name: zhangsan
age: 18
height: 1.8
```

As you can see, `YAML` does not require writing as many braces, quotes, and commas as `JSON`, so it looks cleaner.

If you want to represent an array, a common form in `JSON` is:

```json
["a", "b", "c"]
```

In `YAML`, the most common way to write it is:

```yaml
- a
- b
- c
```

Of course, `YAML` also supports the square-bracket syntax that is more similar to `JSON`, but in configuration file scenarios, the dash-based form for representing array elements is more commonly used.

Taking it further, if it is a more complex structure such as an "array of objects," `YAML` can still express it. For example:

```yaml
- name: zhangsan
  age: 18
- name: lisi
  age: 20
```

If converted to `JSON`, the corresponding syntax is:

```json
[
  {
    "name": "zhangsan",
    "age": 18
  },
  {
    "name": "lisi",
    "age": 20
  }
]
```

There is a very important syntax point to remember here: `YAML` is very sensitive to indentation.

In other words:

- Properties at the same level must be aligned
- Child properties must be indented one level deeper than their parent
- For objects in an array, subsequent fields must also stay aligned with the first field

So when you look at the `app_config.yaml` file in the current project, you can understand it directly as follows:

- The outermost `logging`, `db_meta`, `db_dw`, `qdrant`, `embedding`, `es`, and `llm` are all first-level objects
- Each object then contains its own child properties
- These structures are ultimately loaded into the configuration objects used later in the code

If you only want to understand "why the project uses YAML instead of JSON," you can also remember one sentence: **JSON is more like a data exchange format, while YAML is more like an engineering configuration format.**

Because in configuration file scenarios, developers care more about:

- Whether it is easy to read
- Whether it is easy to modify
- Whether the hierarchy is clear

And in these respects, `YAML` is usually more suitable than `JSON`.

### 2.3 Configuration Loading Tool

The YAML configuration loading tool used in this project is `OmegaConf`. For specific usage, refer to the OmegaConf official website.

Official website: https://omegaconf.readthedocs.io/en/2.3_branch/index.html

The main thread of this section is very clear:

- First, define a set of `dataclass` that corresponds to the YAML structure
- Then read the contents of the YAML file
- Finally, merge the "configuration structure" and "configuration values" and convert them into a configuration object whose properties can be accessed directly

The benefit of using OmegaConf is straightforward: configuration items first have an explicit structure definition, and when accessing configuration, you can also write it directly in a more intuitive form such as `app_config.xxx`. As a result, you do not need to hardcode string keys everywhere in the later code.

The code used to read the configuration file is placed in the `shopkeeper-agent/app/conf/app_config.py` file. You can also create the corresponding file in the corresponding folder according to the following path.

The core content is as follows:

```python
from dataclasses import dataclass
from pathlib import Path

from omegaconf import OmegaConf


# 文件日志配置，对应 logging.file 这一组参数
@dataclass
class File:
    enable: bool
    level: str
    path: str
    rotation: str
    retention: str


# 控制台日志配置，对应 logging.console 这一组参数
@dataclass
class Console:
    enable: bool
    level: str


# 把 file 和 console 两组日志配置再组合成 logging 总配置
@dataclass
class LoggingConfig:
    file: File
    console: Console


# 数据库配置
# 这里的结构既会给元数据库 db_meta 用，也会给数据仓库模拟库 db_dw 用
@dataclass
class DBConfig:
    host: str
    port: int
    user: str
    password: str
    database: str


@dataclass
class QdrantConfig:
    host: str
    port: int
    embedding_size: int


# Embedding 服务配置，对应 YAML 里的 embedding 分组
@dataclass
class EmbeddingConfig:
    host: str
    port: int
    model: str


# Elasticsearch 配置，对应 YAML 里的 es 分组
@dataclass
class ESConfig:
    host: str
    port: int
    index_name: str


# 大模型配置，对应 YAML 里的 llm 分组
@dataclass
class LLMConfig:
    model_name: str
    api_key: str
    base_url: str


# AppConfig 是整个项目配置的总入口
# 这里的字段名，需要和 app_config.yaml 的顶层字段保持一致
@dataclass
class AppConfig:
    logging: LoggingConfig
    db_meta: DBConfig
    db_dw: DBConfig
    qdrant: QdrantConfig
    embedding: EmbeddingConfig
    es: ESConfig
    llm: LLMConfig


# 从当前文件 app/conf/app_config.py 出发，回到项目根目录
# 再定位到 conf/app_config.yaml 这个配置文件
config_file = Path(__file__).parents[2] / 'conf' / 'app_config.yaml'

# 读取 YAML 配置内容
context = OmegaConf.load(config_file)

# 根据 AppConfig 生成一份“结构化配置 schema”
schema = OmegaConf.structured(AppConfig)

# 把“配置结构”和“配置值”合并，再转换成真正可直接访问属性的对象
app_config: AppConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))

if __name__ == '__main__':
    # 简单测试：验证配置是否能正常读取
    print(app_config.es.host)
```

Run the file to verify; success:

```bash
(shopkeeper-agent) didilili@DidililiMacBook-Pro shopkeeper-agent % python3 app/conf/app_config.py
localhost
```

There are two points here that are especially worth remembering first:

- `Path(__file__).parents[2] / 'conf' / 'app_config.yaml'`
  The purpose of this line of code is to reliably locate the configuration file in the project root directory based on the location of the current file, rather than hardcoding an error-prone relative path.

- `OmegaConf.structured(AppConfig)` + `OmegaConf.load(...)` + `OmegaConf.merge(...)`
  This set of operations essentially does "define the structure first, then load the content, and finally merge them into a configuration object."

### 2.4 Path-Related Knowledge

Before truly understanding `OmegaConf`, it is recommended to first understand separately why the configuration file path is written this way. This knowledge is not only used in `OmegaConf`; you will also encounter it repeatedly later when reading prompt files, log directories, and script configuration files.

If you are not very familiar with this path code yet, you can expand your understanding a little here.

First, look at this line:

```python
config_file = Path(__file__).parents[2] / "conf" / "app_config.yaml"
```

It contains three knowledge points: **absolute paths, relative paths, and `pathlib` path operations**.

**First, what is an absolute path, and what is a relative path?**

- **Absolute path**
  is a complete path written from the system root directory, for example:
  `/Users/tools/Desktop/agent/shopkeeper-agent/conf/app_config.yaml`
- **Relative path**
  is a path described relative to a certain "current location", for example:
  `conf/app_config.yaml`
  or
  `../conf/app_config.yaml`

On the surface, relative paths are shorter, but there is one place where they can easily trip you up:

> In a Python program, relative paths are usually relative to the current working directory where the program was started, not relative to the current `.py` file itself.

What does this mean?

For example, suppose you write:

```python
OmegaConf.load("conf/app_config.yaml")
```

If you happen to start the program from the `shopkeeper-agent/` root directory, this path may be correct.  
But if you start it from another directory, or start it indirectly through another script, this relative path may fail to find the file.

Therefore, in engineering projects, **hard-coding relative paths directly is usually not reliable enough**.

**Second, what is `__file__`?**

`__file__` is a special variable provided by Python that represents **the path of the current Python file itself**.

For example, in `app/conf/app_config.py`, `__file__` would roughly be:

```python
/Users/tools/Desktop/agent/shopkeeper-agent/app/conf/app_config.py
```

With it, we no longer depend on "which directory the program was started from"; instead, we can locate configuration files based on "where the current file itself is".

**Third, why use `pathlib.Path`?**

Because building paths purely with string concatenation is cumbersome and not robust enough.

For example, when manually concatenating strings, you may encounter these problems: how to find the parent directory; different path separators on Windows versus macOS / Linux; poor readability when joining multiple directory levels.

`pathlib` is a tool in Python's standard library specifically designed for handling paths, and it takes care of these details for us.

For example:

```python
Path(__file__)
```

This means wrapping the current file path into a `Path` object.  
This makes it more natural to perform operations like "finding the parent directory" and "joining subdirectories".

Each part of this line of code can be broken down as follows:

```python
Path(__file__)          # 当前文件路径
Path(__file__).parents  # 当前文件的父目录链
Path(__file__).parents[2]
```

Where:

- `parents[0]` means the parent directory
- `parents[1]` means two levels up
- `parents[2]` means three levels up

Applied to the current project:

- The current file is `shopkeeper-agent/app/conf/app_config.py`
- Its parent directory is `shopkeeper-agent/app/conf`
- Two levels up is `shopkeeper-agent/app`
- Three levels up is `shopkeeper-agent`

Therefore:

```python
Path(__file__).parents[2]
```

This locates the `shopkeeper-agent` project root directory. The next part:

```python
/ "conf" / "app_config.yaml"
```

is a very convenient way of writing in `pathlib`, meaning to continue appending subpaths. In other words, it appends to the root directory:

```text
shopkeeper-agent/conf/app_config.yaml
```

So the complete meaning of this entire line of code is: starting from the current `app_config.py` file, reliably return to the `shopkeeper-agent` root directory, then enter `conf/app_config.yaml`, thereby obtaining the absolute path to the configuration file.

This is essentially a more reliable engineering practice:

- Does not depend on the current working directory where the command is executed
- Does not manually concatenate string paths
- Makes path writing clearer and more cross-platform

If we expand this step into a more intuitive pseudo-flow, it looks like this:

```text
当前文件 app/conf/app_config.py
  -> 回到项目根目录 shopkeeper-agent
  -> 进入 conf 目录
  -> 找到 app_config.yaml
```

### 2.5 OmegaConf Loading Explanation

Besides the path itself, the set of calls involving `OmegaConf` is also worth breaking down separately.

First, look at these three lines:

```python
context = OmegaConf.load(config_file)
schema = OmegaConf.structured(AppConfig)
app_config: AppConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
```

When seeing this for the first time, it often feels a bit convoluted. But what it does can be summarized in one sentence: **first read the configuration content, then prepare the configuration structure, and finally merge the two and convert them into a truly usable configuration object.**

It can be understood in four steps.

**Step one, what does `OmegaConf.load(config_file)` do?**

```python
context = OmegaConf.load(config_file)
```

The purpose of this step is straightforward: open the YAML file, read the configuration content, and convert it into a configuration object that `OmegaConf` can handle. Roughly speaking, what happens here is "first read out the configuration file content." If we only go this far, we can already access the configuration, for example:

```python
context["db_meta"]["host"]
```

Or in some scenarios it can also be written as dot access. However, this approach is still not ideal in engineering projects, because: the configuration structure is not clear enough; editor hints are not friendly enough; when there are many nested configurations, the usage experience deteriorates; and when certain key names are typed incorrectly, it is not easy to detect immediately.

This also explains why **structured configuration** needs to be introduced further here.

**Step two, what does `OmegaConf.structured(AppConfig)` do?**

```python
schema = OmegaConf.structured(AppConfig)
```

This step is not reading the YAML content, but rather reading the `dataclass` structure that we defined ourselves.

In other words, the focus here is not "what the configuration values are", but:

- What fields exist at the top level of the entire configuration
- What type each field corresponds to
- Whether a field contains nested objects

For example:

```python
@dataclass
class ESConfig:
    host: str
    port: int
    index_name: str
```

What it expresses is:

- The `es` configuration group should contain `host`
- It should also contain `port`
- It should also contain `index_name`

Another example:

```python
@dataclass
class AppConfig:
    logging: LoggingConfig
    db_meta: DBConfig
    db_dw: DBConfig
    qdrant: QdrantConfig
    embedding: EmbeddingConfig
    es: ESConfig
    llm: LLMConfig
```

What it expresses is the top-level structure of the entire configuration file. In other words, `AppConfig` is essentially the "structure specification" for `app_config.yaml`.

If you have written TypeScript, you can think of this relationship as analogous to writing `interface` / `type` for a JSON or configuration file—used to declare what top-level fields exist, what nested objects look like, and roughly what types the scalars are; the dataclass here plays a similar role, except that validation and merging happen at Python runtime (with OmegaConf) rather than at TypeScript's compile-time type checking.

For now, this distinction is enough: `context` is the "configuration content"; `schema` is the "configuration structure".

**Step three, why is `merge` still needed?**

```python
OmegaConf.merge(schema, context)
```

This is the most critical step. Because the previous two steps each only obtained one thing: `schema` has only structure and no concrete values; `context` has concrete values but is not structured enough.

So what needs to be done here is to combine them.

The result after merging can be viewed as:

- Knowing which fields exist
- Also knowing the actual values of these fields
- While still retaining the benefits brought by the structured definition

That is to say, it is not simply "reading the YAML" and being done; instead, it is about aligning the "configuration content" with the "configuration structure".

**Step four, why is `to_object` needed at the end?**

```python
app_config: AppConfig = OmegaConf.to_object(...)
```

The purpose of this step is to convert the previously merged configuration into a real Python object.

After doing this, accessing the configuration becomes more natural:

```python
app_config.db_meta.host
app_config.es.host
app_config.llm.model_name
```

Compared with dictionary access, this approach has several obvious advantages: more intuitive; better editor autocompletion; clearer nested access; and closer to the "configuration class object" experience that many people are familiar with.

In other words, if you only read the YAML into a dictionary, although it works, the experience is not as good as "converting it into an object".

This entire process can be remembered as the following chain:

```text
YAML 文件
  -> OmegaConf.load 读取配置内容
  -> OmegaConf.structured 准备配置结构
  -> OmegaConf.merge 合并结构和内容
  -> OmegaConf.to_object 转成配置对象
```

If we look at it together with the nested configuration in the current project, this approach becomes even easier to understand.

For example, suppose the YAML contains this section:

```yaml
es:
  host: localhost
  port: 9200
  index_name: data_agent
```

Then the corresponding structure would be:

```python
@dataclass
class ESConfig:
    host: str
    port: int
    index_name: str
```

And the way it is ultimately mounted onto the overall configuration object is:

```python
@dataclass
class AppConfig:
    es: ESConfig
```

So in the end we can naturally write:

```python
app_config.es.host
```

This is also the most important value of this entire set of practices: **seamlessly mapping the hierarchical structure in the YAML file to the object structure in Python.**

The final `app_config` is the configuration object that can be used globally throughout the entire project. For example:

```python
app_config.db_meta.host
app_config.es.host
app_config.llm.model_name
```

In other words, subsequent code no longer needs to repeatedly parse the YAML file when using the configuration; it can directly access this object.

**Chapter Summary:**

The focus of this chapter is not to actually connect all the basic services, but rather to first understand the **project structure and configuration entry point**.

- From the project structure perspective, the backend main project `shopkeeper-agent` adopts a relatively clear layered organization: `clients` handles external dependencies, `repositories` handles data access, `services` handles business logic, and `api` handles API exposure.
- From the runtime dependency perspective, MySQL, Qdrant, Elasticsearch, Embedding, and the backend API have all already secured their places in the configuration, and all subsequent client managers will revolve around these addresses and ports.
- From the configuration management perspective, this project does not directly pass YAML around as a dictionary everywhere; instead, it merges the configuration structure and configuration content into a unified object through `dataclass + OmegaConf`.

The next chapter will formally enter the retrieval basic services, namely **Qdrant and Elasticsearch**. The former is responsible for **semantic similarity retrieval**, and the latter is responsible for **full-text search**.
