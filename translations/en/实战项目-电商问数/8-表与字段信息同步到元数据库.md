# 8 - Shopkeeper Data Q&A: Syncing Table and Field Information to the Metadata Database

---

**Chapter learning objectives:**

- Understand why the first step in building a metadata knowledge base must be persisting table and field information into `Meta MySQL`.
- Understand the complete chain of "configuration description -> business entity -> DW supplements real information -> Meta MySQL persistence".
- Establish a clear layered understanding: `Service` is responsible for orchestrating the process, `DW Repository` is responsible for querying the real structure, `Meta Repository` is responsible for persistence, and `Mapper` is responsible for object conversion.

**Study advice:** In this chapter, first grasp the single persistence chain: the configuration file describes table fields, the system supplements the real structure from the data warehouse, then converts it into internal entities, and finally writes it to Meta MySQL. Details such as ORM, Repository, and transactions all serve this chain. When reading code, focus on which data comes from configuration, which data comes from DW, and which data ultimately ends up in the metadata database.

**Corresponding code branch:** `08-metadata-table-column-sync`

---

In the previous chapter, we already explained the entry point of "metadata knowledge base construction": how the script starts, how configuration is loaded, and how the service layer receives `config_path` and enters the actual business process.

Starting from this chapter, we officially enter the first truly implemented business chain: **converting the tables and fields described in the configuration file into unified internal system data objects and writing them to `Meta MySQL`.**

This step is fundamental, but also very critical. Because the subsequent field vector indexes, field value full-text indexes, and SQL generation context organization all build on top of this batch of structured metadata. In other words, **only when table information and field information are first stably persisted can the subsequent retrieval and data Q&A chains have a reliable foundation.**

## 1. Position of this chapter in the overall construction process

Returning to `MetaKnowledgeService.build(config_path)`, the table chain corresponds to the following section:

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def build(self, config_path: Path):
    context = OmegaConf.load(config_path)
    schema = OmegaConf.structured(MetaConfig)
    meta_config: MetaConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))

    if meta_config.tables:
        column_infos = await self._save_tables_to_meta_db(meta_config)
        await self._save_column_info_to_qdrant(column_infos)
        await self._save_value_info_to_es(meta_config, column_infos)
```

As long as `tables` exists in the configuration, the system will do three things in sequence:

1. First write table information and field information to `Meta MySQL`
2. Then build vector indexes for fields based on `column_infos`
3. Finally, based on the `sync` flag in the configuration, build field value full-text indexes for some fields

This chapter only covers the first step, namely:

```python
column_infos = await self._save_tables_to_meta_db(meta_config)
```

You can think of this chapter as: **first clarifying "what a field is", and later explaining "how fields are retrieved".**

## 2. First grasp the main line: What exactly does _save_tables_to_meta_db(...) do

Before going into details, let's first look at the most core method in this chapter.

Corresponding project file path: `shopkeeper-agent/app/services/meta_knowledge_service.py`

```python
async def _save_tables_to_meta_db(self, meta_config: MetaConfig) -> list[ColumnInfo]:
    table_infos: list[TableInfo] = []
    column_infos: list[ColumnInfo] = []

    for table in meta_config.tables:
        table_info = TableInfo(
            id=table.name,
            name=table.name,
            role=table.role,
            description=table.description,
        )
        table_infos.append(table_info)

        column_types: dict[str, str] = await self.dw_mysql_repository.get_column_types(
            table.name
        )
        for column in table.columns:
            column_values: list = await self.dw_mysql_repository.get_column_values(
                table.name, column.name, 10
            )
            column_info = ColumnInfo(
                id=f"{table.name}.{column.name}",
                name=column.name,
                type=column_types[column.name],
                role=column.role,
                examples=column_values,
                description=column.description,
                alias=column.alias,
                table_id=table.name,
            )
            column_infos.append(column_info)

    async with self.meta_mysql_repository.session.begin():
        await self.meta_mysql_repository.save_table_infos(table_infos)
        await self.meta_mysql_repository.save_column_infos(column_infos)

    return column_infos
```

What it does is actually very clear:

1. Iterate through each table in the configuration and first construct `TableInfo`
2. Query the real types of all fields in this table from `DW`
3. Then iterate through each field under this table and query some real values as examples
4. Construct `ColumnInfo`
5. Open a transaction and write table information and field information uniformly to `Meta MySQL`

So the entire content of the following chapter essentially breaks down these five steps layer by layer.

## 3. Step 1: How tables and fields in configuration become business entities

The most important understanding at this layer is: **configuration files are not directly written to the database; configuration files are first converted into business entities.**

If your understanding of the differences between "configuration file, business entity, ORM model, mappers" is not yet solid, it is recommended to review the conceptual explanation at the beginning of Chapter 7. Starting from Chapter 8, it is assumed that you have already accepted one premise:

- The configuration file is responsible for describing "what to process this time"
- Business entities are responsible for representing "how the system internally expresses this data uniformly"
- `Mapper` is responsible for converting between business entities and ORM models
- ORM models are responsible for mapping data to database tables

In other words, this chapter is not about inserting `YAML` row by row into the database, but about first organizing the descriptions in the configuration into unified internal system data objects.

### 3.1 First look at what the configuration looks like

Corresponding project file path: `shopkeeper-agent/conf/meta_config.yaml`

```yaml
tables:
  - name: dim_region
    role: dim
    description: 地区维度表，用于描述订单发生的地理区域信息。
    columns:
      - name: region_id
        role: primary_key
        description: 地区唯一标识。
        alias: [地区ID, 区域ID]
        sync: false

      - name: region_name
        role: dimension
        description: 订单所属的大区名称，如华东、华南等。
        alias: [地区, 区域, 大区]
        sync: true
```

This configuration is mainly responsible for telling the system two things: which tables and which fields should enter the metadata knowledge base; and what the business semantics of these tables and fields are.

What you can see here is mostly business description information, such as: table role `role`, field role `role`, field description

### 3.2 Next, look at the system's internal unified data objects

Corresponding project file paths:

- `shopkeeper-agent/app/entities/table_info.py`
- `shopkeeper-agent/app/entities/column_info.py`

```python
@dataclass
class TableInfo:
    id: str
    name: str
    role: str
    description: str


@dataclass
class ColumnInfo:
    id: str
    name: str
    type: str
    role: str
    examples: list[Any]
    description: str
    alias: list[str]
    table_id: str
```

Here, `TableInfo` is the table metadata object circulating internally in the system, and `ColumnInfo` is the field metadata object circulating internally in the system.

They are not yet ORM models, but lighter data carriers more oriented toward business semantics.

### 3.3 Why ColumnInfo.id does not directly use the field name

Corresponding code:

```python
id=f"{table.name}.{column.name}"
```

The reason is simple: in a real data warehouse, there will be a large number of fields with the same name. For example, many tables contain fields with the same name such as `id`, `customer_id`, `product_id`, `date_id`.

If only the field name were used as the unique identifier, fields with the same name in different tables would soon conflict. Therefore, the current project designs the field ID as: **table name + dot + field name**

For example:

- `fact_order.order_amount`
- `dim_customer.customer_id`
- `dim_product.category`

This way, fields have stable and clear uniqueness within the system.

### 3.4 Why type and examples are not directly obtained from configuration

Look at the construction code of `ColumnInfo`:

```python
column_info = ColumnInfo(
    id=f"{table.name}.{column.name}",
    name=column.name,
    type=column_types[column.name],
    role=column.role,
    examples=column_values,
    description=column.description,
    alias=column.alias,
    table_id=table.name,
)
```

What is worth noting here is:

- `role`, `description`, `alias` come from configuration
- `type`, `examples` come from runtime queries

Behind this lies a very important engineering principle: **for real information that the system can obtain automatically, try not to require users to manually maintain duplicates as much as possible.**

Field types are inherently part of the database table structure, and example values inherently exist in real data. If these contents also require users to manually fill them in the configuration, two obvious problems will arise: high maintenance cost, and easy disconnection from the real data warehouse. Therefore, the configuration file is mainly responsible for describing **business semantics**, while the program is responsible for supplementing **real structure and real samples** at runtime.

## 4. Step 2: Why is there a dedicated DW Repository

As we saw earlier, field types and field example values are not directly given in the configuration, but are queried from the data warehouse at runtime.
This responsibility falls on `DWMySQLRepository`.

Corresponding project file path: `shopkeeper-agent/app/repositories/mysql/dw/dw_mysql_repository.py`

```python
async def get_column_types(self, table_name: str) -> dict[str, str]:
    sql = f"show columns from {table_name}"
    result = await self.session.execute(text(sql))
    return {row.Field: row.Type for row in result.fetchall()}


async def get_column_values(self, table_name: str, column_name: str, limit: int):
    sql = f"select distinct {column_name} from {table_name} limit {limit}"
    result = await self.session.execute(text(sql))
    return result.scalars().fetchall()
```

These two methods respectively do two things:

- `get_column_types(table_name)`: Query the real types of all fields in a table
- `get_column_values(table_name, column_name, limit)`: Query a portion of real values of a certain field

### 4.1 Why field types are queried once per table

First look at this line of code:

```python
column_types = await self.dw_mysql_repository.get_column_types(table.name)
```

It is placed in the outer table loop because the query granularity of field types is "per table".

For example, querying `fact_order` may return results similar to:

```python
{
    "order_id": "varchar(30)",
    "customer_id": "varchar(20)",
    "order_amount": "float",
}
```

Then, when iterating over fields later, you can directly use:

```python
column_types[column.name]
```

to get the real type of the current field.

### 4.2 Why field example values are queried one column at a time

Now look at this line of code:

```python
column_values = await self.dw_mysql_repository.get_column_values(
    table.name, column.name, 10
)
```

It is placed in the inner field loop because the query granularity of example values is "per field".

For example:

```sql
select distinct category from dim_product limit 10
```

may return:

```python
["饮料", "休闲食品", "粮油调味", "家居清洁"]
```

These values will ultimately be written to:

```python
examples=column_values
```

and stored in `ColumnInfo.examples`.

One point deserves special attention here: **what this chapter obtains are "example values", not all values of that field.**

Therefore, the goal of this layer is not to directly build a full-text index, but to first attach a small portion of representative real samples to the field metadata. The truly large-scale field value synchronization will be expanded in the later `Elasticsearch` chapter.

## 5. Step 3: Why Service processes business entities first instead of directly operating on ORM

This is a layered awareness that is very worth establishing in this chapter. In the current project, the `Service` layer does not directly construct ORM models of `SQLAlchemy`, but first processes business entities such as `TableInfo` and `ColumnInfo`. The key purpose of doing this is not to "add one more layer", but to achieve **decoupling**.

If the `Service` layer directly depended on ORM models, it would bring an obvious problem: business logic would be directly bound to the underlying storage implementation, and once the ORM model changes, the business layer code would also need to change.

Now, with this layering:

- The `Service` layer only cares about how business objects are organized
- The `Repository` layer only cares about how the bottom layer writes to the database

This is also why the same batch of `ColumnInfo` can later be used to build `Qdrant` vector indexes and participate in `Elasticsearch` value indexes, without requiring the business layer to carry ORM objects everywhere.

## 6. Step 4: What are Meta Repository and Mapper actually responsible for

Now we already have two types of business entities: `TableInfo` and `ColumnInfo`. The next step is to write them into `Meta MySQL`. This responsibility lies in `MetaMySQLRepository`.

Corresponding project file path: `shopkeeper-agent/app/repositories/mysql/meta/meta_mysql_repository.py`

```python
async def save_table_infos(self, table_infos: list[TableInfo]):
    models = [TableInfoMapper.to_model(table_info) for table_info in table_infos]
    self.session.add_all(models)


async def save_column_infos(self, columns_info: list[ColumnInfo]):
    models = [ColumnInfoMapper.to_model(column_info) for column_info in columns_info]
    self.session.add_all(models)
```

The most important point here is not `add_all()`, but that: the input exposed by `Repository` to the outside is still business entities, not ORM models.

In other words, the `Service` layer only needs to hand over the "data objects that have already been organized at the business level" to the repository layer. As for how to convert and how to persist, these are absorbed downward by the repository layer.

### 6.1 The role of Mapper is translation

Corresponding project file paths:

- `shopkeeper-agent/app/repositories/mysql/meta/mappers/table_info_mapper.py`
- `shopkeeper-agent/app/repositories/mysql/meta/mappers/column_info_mapper.py`

```python
class TableInfoMapper:
    @staticmethod
    def to_model(table_info: TableInfo) -> TableInfoMySQL:
        return TableInfoMySQL(**asdict(table_info))


class ColumnInfoMapper:
    @staticmethod
    def to_model(column_info: ColumnInfo) -> ColumnInfoMySQL:
        return ColumnInfoMySQL(**asdict(column_info))
```

The role division here is very clear:

- `TableInfo` and `ColumnInfo` are business entities
- `TableInfoMySQL` and `ColumnInfoMySQL` are ORM models
- `Mapper` is responsible for converting the former into the latter

Therefore, the entire database write chain can be compressed into the following:

```text
MetaConfig
  -> TableInfo / ColumnInfo
  -> TableInfoMapper / ColumnInfoMapper
  -> TableInfoMySQL / ColumnInfoMySQL
  -> Meta MySQL
```

### 6.2 add_all() does not mean actually committing to the database

Many beginners, when first encountering ORM, see:

```python
self.session.add_all(models)
```

and easily think that "it has already been written into the database". In fact, this is not the case.

What `add_all()` does, essentially, is only:

- Add these ORM objects to the current `Session`
- Tell the ORM: these objects need to be persisted later

It is not yet the final commit action. The actual data persistence happens at the transaction commit stage.

## 7. Step 5: Why transactions should be centrally managed in the Service layer

Returning to the main method of this chapter:

```python
async with self.meta_mysql_repository.session.begin():
    await self.meta_mysql_repository.save_table_infos(table_infos)
    await self.meta_mysql_repository.save_column_infos(column_infos)
```

What is used here is:

```python
async with session.begin():
```

This approach is very appropriate in the current scenario because it makes the transaction boundary very clear: "saving table information" and "saving field information" belong to the same batch of business operations, and they must either succeed together or fail together.

What lies behind this is a very important layering principle:

- `Repository` is responsible for "how to write"
- `Service` is responsible for "how to organize these write operations into a business transaction"

So placing the transaction boundary in the `Service` layer is reasonable. It also has two very practical benefits: 1. If all operations in the context succeed, the transaction commits automatically. 2. If an exception is thrown partway through, the transaction rolls back automatically.

This makes the code cleaner and less error-prone than manually writing `try/except + commit + rollback`.

## 8. Reviewing the Entire Chain

At this point, we can string together the complete sequence for "synchronizing table information and field information into the metadata database":

1. The script reads `meta_config.yaml`
2. `MetaKnowledgeService.build(config_path)` enters the table chain
3. Traverse each table in the configuration and construct `TableInfo`
4. Use `DWMySQLRepository.get_column_types(...)` to query the actual types of all fields in that table
5. Traverse each field in that table, then use `DWMySQLRepository.get_column_values(...)` to query sample values
6. Construct `ColumnInfo`
7. Open a transaction
8. `MetaMySQLRepository` receives the business entities, and `Mapper` converts them into ORM models
9. `session.add_all()` adds these ORM objects to the current `Session`
10. After the transaction ends, everything is committed together and the data is actually written to `Meta MySQL`

If we compress this process into one sentence, it can be remembered as: **Configuration descriptions first become business entities, the business entities are then supplemented with real structures and samples, and finally they are persisted to the metadata database transactionally.**
