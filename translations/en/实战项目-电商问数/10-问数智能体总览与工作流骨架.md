In the previous chapters, we have basically built the metadata knowledge base for "Shopkeeper Data Q&A." The system now knows what tables exist, what fields exist, what the fields mean, which real values appear in the fields, and how business metrics are defined. The specific capabilities are as follows:

- Table information and field information have been saved to `Meta MySQL`
- Field semantic information has been written to `Qdrant`
- Real field values have been written to `Elasticsearch`
- Metric definitions and metric-field relationships have been saved to `Meta MySQL`
- Metric semantic information has also been written to `Qdrant`

But this knowledge does not automatically answer user questions. Users input natural language, for example: `统计华北地区的销售总额`

To turn that sentence into executable SQL, at minimum the following must be determined:

- Whether "North China" is a real value of some field;
- Whether "total sales" is more like a field or a business metric;
- Whether to query a fact table, or whether dimension tables need to be joined;
- If filtering by region is required, which field and which `join` condition should be used;
- If the user mentions "last year" or "this month," how the current date should be added to the context;
- Whether the final generated SQL can be interpreted and executed by the database.

Therefore, the data Q&A agent is not simply about throwing the question at an LLM and having it directly generate SQL. A more reliable approach is: **first retrieve context, then organize context, then generate SQL, and finally validate and execute SQL.** What this chapter does is first set up the skeleton of this workflow.

## 1. Overall Workflow of the Data Q&A Agent

Looking at it from the highest level first, the complete flow of the data Q&A agent is roughly as follows.

![Full workflow of the LangGraph-based data Q&A agent: keyword extraction, multi-route retrieval, merge and filter, SQL generation and validation, and other nodes](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/2/2-3-1-1.jpg)

If each step is mapped to a node name in the code, it can first be remembered as the following line:

```text
START
  -> extract_keywords
  -> recall_column / recall_metric / recall_value
  -> merge_retrieved_info
  -> filter_table / filter_metric
  -> add_extra_context
  -> generate_sql
  -> validate_sql
  -> correct_sql 或 run_sql
  -> END
```

There are three design points here that need to be understood first.

**First**, after keyword extraction, field information, metric information, and field values can be retrieved in parallel. They all depend on the user question and keywords, but there is no mandatory ordering among themselves.

**Second**, the retrieval results cannot be handed directly to the LLM for SQL generation. During the retrieval phase, it is usually better to retrieve more, to avoid missing key information; but the SQL generation phase needs context that is as clean and accurate as possible. Therefore, merging and filtering are still needed in between.

**Third**, after generating SQL, it cannot be executed directly. The SQL generated by the LLM may have incorrect field names, incorrect table names, incomplete `join` conditions, or may not conform to the current database dialect. Therefore, the SQL must be validated afterward; if validation fails, it then enters the correction flow.

This workflow looks more troublesome than "directly generating SQL," but it is closer to the real practice of enterprise-level data Q&A systems: at each step, let the model guess a little less and let the system provide a little more certain information.

## 3. Review of LangGraph-Related Concepts

LangGraph has already been covered systematically in Chapters 22 to 26. This chapter is not about going through the API manual again, but about putting these concepts back into the "Shopkeeper Data Q&A" project and doing a project-level review.

One sentence worth remembering first: **the data Q&A agent is suited to LangGraph not because it looks more advanced, but because it is naturally a stateful, branching, observable workflow.**

The diagram below places the most common LangGraph concepts in this chapter into a single picture. When reading the code, do not mix them together: `StateGraph` manages structure, `State` manages shared data, `Node` does local processing, `Edge` manages the next step, and `Runtime Context` holds runtime dependencies.

![The five core LangGraph pieces in the Shopkeeper Data Q&A agent: StateGraph, State, Node, Edge, Runtime Context, and Streaming](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/10/10-3-0-1.svg)

If you want to compare with the official documentation, you can refer to LangGraph's [Choosing APIs](https://docs.langchain.com/oss/python/langgraph/choosing-apis), [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), and [Use the Graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api).

### 3.1 Why This Project Is Suitable for LangGraph

If the data Q&A agent were just a simple chain:

```text
Prompt -> Model -> SQL
```

Then an ordinary chained call would be enough. But the actual data Q&A flow is not a straight line; it at least has these characteristics:

- It has multiple clear steps: extracting keywords, retrieving, merging, filtering, generating SQL, validating, and executing;
- It has shared state: later nodes need to read the keywords, retrieval results, SQL, and error information written by earlier nodes;
- It has parallel branches: after keyword extraction, fields, metrics, and field values can be retrieved simultaneously;
- It has conditional branches: if SQL validation passes, execute it; if it fails, correct it;
- It requires real-time observability: the frontend needs to see which node is currently executing.

So LangGraph is used here because it happens to break this kind of flow into a clear structure:

```text
Graph    负责把整套流程编译成可运行对象
State    负责节点之间共享数据
Node     负责具体处理步骤
Edge     负责流程流转
Runtime  负责注入运行时依赖和流式输出能力
```

### 3.2 Graph: Not a Drawing, but an Executable Workflow

`Graph` is not a "flowchart drawn for people to look at," but an executable workflow structure composed of nodes and directed edges.

In this project, what `graph.py` does can be summarized as:

```text
定义 State Schema
  -> 创建 StateGraph
  -> add_node 注册节点
  -> add_edge / add_conditional_edges 连接节点
  -> compile 得到可运行 graph
  -> astream 执行图并流式输出
```

This is consistent with the minimal LangGraph build process in Chapter 22:

1. Define `State`
2. Define `Node`
3. Define `Edge`
4. Compile `Graph`
5. Execute `Graph`

`StateGraph` is more like a builder for the graph. You keep registering nodes and connecting edges on it; only after calling `compile()` do you get a graph object that can actually run.

```python
graph_builder = StateGraph(...)  # 搭建阶段：注册节点、连接边
graph = graph_builder.compile()  # 运行阶段：执行、流式输出、调试
```

`compile()` is not a dispensable formal step. It has at least three layers of meaning:

- Perform basic checks on the graph structure, such as whether there are unconnected isolated nodes;
- Solidify the nodes, edges, and state schema into an executable object;
- Reserve an entry point for later runtime capabilities such as checkpoints, breakpoints, and caching.

Understood this way, the responsibility of `graph.py` is very clear: the first half is "building the graph," and only the final `compile()` turns this graph into a truly runnable data Q&A agent.

### 3.3 State: Shared State, Not a Dictionary for Arbitrary Variables

`state` is the data shared by the entire graph at runtime. Each node can read the current `state` and return only the small subset of fields it wants to update.

> This part can be read alongside the official [Graph API - State](https://docs.langchain.com/oss/python/langgraph/graph-api#state).

There is a very important sentence in Chapter 23: **State = Schema + Reducer.**

At the current stage of this project, we first use `TypedDict` to define a minimal State Schema:

```python
class DataAgentState(TypedDict):
    query: str
    error: str
```

What this schema declares is: in the graph of the data Q&A agent, these are at least the fields that currently need to flow through it.

The official documentation also mentions that there are three common ways to write a State Schema:

| Writing Style                 | Suitable Scenario                                                 |
| -------------------- | -------------------------------------------------------- |
| `TypedDict`          | The lightest, suitable for tutorials and most engineering scenarios, with clear types and low runtime cost |
| `dataclass`          | More convenient when default values are needed                                     |
| `Pydantic BaseModel` | Used when stronger runtime validation is needed, but at a higher performance cost                 |

This project currently chooses `TypedDict` for a simple reason: the state fields in the data Q&A pipeline are relatively clear, and at the tutorial stage we also want readers to focus on "how state flows between nodes" rather than getting caught up in a complex data validation model from the start. Later, when moving to production-level interfaces, if stricter input/output validation is needed, introducing Pydantic separately will be more natural.

When a node executes, it usually does not return the complete state, but rather a partial update. The most typical example in this chapter's code is the `validate_sql` node temporarily returning:

```python
return {"error": None}
```

LangGraph will merge this partial update back into the global `state`. No special `Reducer` is currently configured, so the default is overwrite update: the new value replaces the old value.

You can use this rule to judge whether data should go into `state`:

```text
后续节点还要用、需要被观测、需要参与分支判断的数据，放进 state。
只在当前函数里临时用一下的数据，不要放进 state。
```

In the data Q&A agent, typical `state` fields include:

```text
query                  # 用户问题
keywords               # 抽取出的关键词
retrieved_column_infos # 字段召回结果
retrieved_metrics      # 指标召回结果
retrieved_values       # 字段取值召回结果
table_infos            # 合并后的表结构上下文
metric_infos           # 合并后的指标上下文
sql                    # 生成出的 SQL
error                  # SQL 校验错误
```

Therefore, do not rush to design `DataAgentState` completely in this chapter. Later, as each node is implemented, add the data that the node actually reads and writes.

### 3.4 Node: A Node Does Only One Thing and Returns a Partial State Update

Nodes are where the real "work" happens in the graph. They can call an LLM, query a database, do ordinary Python computation, or simply organize formats.

> This part can be read alongside the official [Graph API - Nodes](https://docs.langchain.com/oss/python/langgraph/graph-api#nodes).

In this project, a node function generally looks like this:

```python
async def extract_keywords(
    state: DataAgentState,
    runtime: Runtime[DataAgentContext],
):
    ...
```

The two most important parameters here are:

- `state`: reads and writes business intermediate state;
- `runtime`: reads the runtime context, or outputs progress through `stream_writer`.

According to the official documentation, a node function can also receive `config`. In this project, they can first be distinguished as follows:

| Parameter      | Meaning                                                  | Currently a key focus in this project |
| --------- | ----------------------------------------------------- | ---------------------- |
| `state`   | The current graph state; the node reads it and returns a partial update                  | Key focus               |
| `runtime` | The runtime context, including capabilities such as `context` and `stream_writer`  | Key focus               |
| `config`  | Configuration information for this run, such as thread ID, configurable parameters, and tracing information | Not expanded in detail for now         |

When reading node code, it is enough to first grasp one main thread:

```text
节点读取 state
  -> 使用 runtime.context 里的依赖做事
  -> 必要时用 runtime.stream_writer 输出进度
  -> 最后返回 Partial State
```

The official documentation also mentions that after a regular Python function is registered as a node, LangGraph wraps it into a runnable object. This detail means the node can later gain capabilities such as tracing, asynchronous execution, and batch processing. But in this project's tutorial, you can first understand it with a simpler statement: **a node is a function that "reads state, does work, and returns partial updates."**

Chapter 24 also emphasized an engineering habit: **nodes should return Partial State instead of returning the entire State every time.**

For example, in this chapter, `validate_sql` only needs to temporarily tell the conditional edge that "there is currently no error," so it returns:

```python
return {"error": None}
```

It should not also return all the other fields that are not part of its responsibility. Doing so has two benefits:

- The node's responsibility is clearer, making it easier to know exactly what this node changed when reading the code;
- It avoids mistakenly overwriting state that is not within the current node's responsibility, which is especially important when there are parallel branches later.

In the context of the data Q&A agent, it is best for a node to do only one thing:

```text
extract_keywords       -> 只抽关键词
recall_column          -> 只召回字段
merge_retrieved_info   -> 只合并召回信息
validate_sql           -> 只校验 SQL 并写入 error
run_sql                -> 只执行 SQL 并输出结果
```

### 3.5 Edge: normal edges represent fixed order, conditional edges represent runtime branching

`edge` is responsible for describing how nodes transition to each other. This project currently uses two main types: normal edges and conditional edges.

> This section can be read alongside the official [Graph API - Edges](https://docs.langchain.com/oss/python/langgraph/graph-api#edges) and [Conditional branching](https://docs.langchain.com/oss/python/langgraph/use-graph-api#conditional-branching) documentation.

Normal edges are used for fixed order:

```python
graph_builder.add_edge("add_extra_context", "generate_sql")
graph_builder.add_edge("generate_sql", "validate_sql")
```

This means that after adding context, SQL is generated, and after SQL is generated, the SQL is validated.

Conditional edges are used for runtime branching:

```python
graph_builder.add_conditional_edges(
    source="validate_sql",
    path=lambda state: "run_sql" if state["error"] is None else "correct_sql",
    path_map={"run_sql": "run_sql", "correct_sql": "correct_sql"},
)
```

The business semantics corresponding to this code are:

```text
如果 validate_sql 没有写入错误信息
  -> 进入 run_sql

如果 validate_sql 写入了错误信息
  -> 进入 correct_sql
```

Flow control should not be scattered across a bunch of `if/else` statements; instead, it should be expressed as much as possible through the graph's edges. This makes the workflow structure clearer and also makes it easier to draw diagrams and debug.

One more point to note here: **a node can have multiple outgoing edges.**

In this project, the most typical example is the three-route retrieval after keyword extraction:

```python
graph_builder.add_edge("extract_keywords", "recall_column")
graph_builder.add_edge("extract_keywords", "recall_value")
graph_builder.add_edge("extract_keywords", "recall_metric")
```

These three edges do not express "first retrieve fields, then retrieve values, then retrieve metrics," but rather:

```text
关键词抽取完成后
  -> 字段召回、字段取值召回、指标召回都可以开始
```

This is exactly why a data Q&A agent is suitable to be expressed as a graph. Many of its steps are not simple serial relationships, but rather "the front produces a common input, the back has multiple branches that each process it, and finally they merge."

For conditional edges, there is also a detail to pay attention to: the `path` function is only responsible for deciding the next step based on the current `state`, and it is not suitable for modifying state on the side. If a node needs to both update state and decide the next hop, LangGraph also has a more advanced [`Command`](https://docs.langchain.com/oss/python/langgraph/graph-api#command) capability. However, in this chapter, we will first separate "state updates" from "workflow branching": nodes are responsible for returning state updates, and conditional edges are responsible for choosing the subsequent node.

### 3.6 START / END: entry and exit of the graph

`START` and `END` are two special virtual nodes built into LangGraph.

> This section can be read alongside the official [Graph API - START Node](https://docs.langchain.com/oss/python/langgraph/graph-api#start-node) documentation.

In this project:

```python
graph_builder.add_edge(START, "extract_keywords")
graph_builder.add_edge("run_sql", END)
```

This means the entire graph starts from `extract_keywords` and ends after `run_sql`. They are not business nodes and do not execute concrete logic like `extract_keywords`; they only help the graph clarify its entry and exit.

### 3.7 Runtime Context: separating dependencies from state

When Chapter 24 discussed `Runtime`, the most important point was: **do not force runtime dependencies into State.**

Subsequent nodes will use objects such as database connections, vector retrieval repositories, full-text retrieval repositories, and Embedding clients. These objects are not business state but runtime tools. They should not be placed in `DataAgentState`, but rather in `DataAgentContext` and read through `runtime.context`.

This chapter has not yet started placing specific dependencies, so `DataAgentContext` is temporarily empty. The official explanation of Runtime Context can be found in [Graph API - Runtime Context](https://docs.langchain.com/oss/python/langgraph/graph-api#runtime-context).

Incidentally, let us explain the generic notation in `Runtime[DataAgentContext]`. You can simply understand it as:

```text
我要使用 LangGraph 的 Runtime，
并且告诉它：我的 runtime.context 结构是 DataAgentContext。
```

Currently `DataAgentContext` has no specific fields yet, but this type shell is placed here first so that when dependencies are added later, the node signatures do not need to be changed.

### 3.8 Streaming: this project uses the custom stream for now

Streaming output is another key point of this chapter. `invoke()` is more like "wait until the entire graph finishes running and then get the final result," while `stream()` / `astream()` are more like "observe what is happening in the graph while it runs." The official documentation can be found at [Streaming](https://docs.langchain.com/oss/python/langgraph/streaming).

LangGraph's `stream_mode` has multiple modes:

| Mode       | What it is good for viewing                                      |
| ---------- | ----------------------------------------------- |
| `values`   | Complete State snapshot after each node executes                 |
| `updates`  | Which fields each node updated this time                      |
| `messages` | Large model output token by token                             |
| `custom`   | Custom events actively written by nodes through `stream_writer` |
| `debug`    | Debugging information                                        |

The current choice for this project:

```python
stream_mode="custom"
```

The reason is straightforward: what the frontend cares about most is "which step is currently being executed," "what the final query result is," and "whether there are any errors." All of these are suitable for nodes to actively write using `runtime.stream_writer`.

### 3.9 Which LangGraph capabilities this project does not yet cover

LangGraph also has many advanced capabilities, such as `Send`, `Command`, node caching, retries, state persistence, time travel, subgraphs, multi-agents, and A2A.

These capabilities are all important, but the first version of the current data Q&A agent does not need to use all of them yet. This chapter starts with the most intuitive set of capabilities:

```text
StateGraph
TypedDict State
普通节点
普通边
条件边
Runtime Context
Custom Streaming
```

Once this main data Q&A chain is working, if more complex production capabilities need to be supported later, the following can be gradually introduced:

- Use persistence to save long-task state and support failure recovery;
- Use finer-grained streaming events for frontend observability;
- Use subgraphs to split complex sub-processes;
- Use multi-agents to split roles such as "data analyst, SQL engineer, and result interpreter."

from langgraph.runtime import Runtime

from app.agent.context import DataAgentContext

async def extract_keywords(state: DataAgentState, runtime: Runtime[DataAgentContext]):

The current node only does two things: output a progress message, and then `await asyncio.sleep(0.5)`.

## 6. Assemble the workflow graph in graph.py

Next comes the most important file of this chapter.

Corresponding project file path: `shopkeeper-agent/app/agent/graph.py`

First import the objects required by `LangGraph`, as well as the previously written state, context, and node functions.

```python
import asyncio

from langgraph.constants import END, START
from langgraph.graph import StateGraph

from app.agent.context import DataAgentContext
from app.agent.state import DataAgentState
```

Then create the graph builder.

```python
graph_builder = StateGraph(
    state_schema=DataAgentState,
    context_schema=DataAgentContext,
)
```

What this means is: next, we are going to build a state graph. The shared state during graph execution is understood according to `DataAgentState`, and the runtime context is understood according to `DataAgentContext`.

### 6.1 Register nodes

After creating `StateGraph`, register the previously written node functions into the graph:

```python
graph_builder.add_node("extract_keywords", extract_keywords)
graph_builder.add_node("recall_column", recall_column)
graph_builder.add_node("recall_value", recall_value)
graph_builder.add_node("recall_metric", recall_metric)
graph_builder.add_node("merge_retrieved_info", merge_retrieved_info)
graph_builder.add_node("filter_metric", filter_metric)
graph_builder.add_node("filter_table", filter_table)
graph_builder.add_node("add_extra_context", add_extra_context)
graph_builder.add_node("generate_sql", generate_sql)
graph_builder.add_node("validate_sql", validate_sql)
graph_builder.add_node("correct_sql", correct_sql)
graph_builder.add_node("run_sql", run_sql)
```

The first parameter of `add_node(...)` is the node name, and the second parameter is the corresponding node function. It is recommended to keep the node name consistent with the function name, so that connecting edges, reading logs, and looking at flowcharts later are all more straightforward.

### 6.2 Add normal edges

After the nodes are registered, edges are still needed to describe fixed transition relationships.

```python
graph_builder.add_edge(START, "extract_keywords")

graph_builder.add_edge("extract_keywords", "recall_column")
graph_builder.add_edge("extract_keywords", "recall_value")
graph_builder.add_edge("extract_keywords", "recall_metric")

graph_builder.add_edge("recall_column", "merge_retrieved_info")
graph_builder.add_edge("recall_value", "merge_retrieved_info")
graph_builder.add_edge("recall_metric", "merge_retrieved_info")

graph_builder.add_edge("merge_retrieved_info", "filter_table")
graph_builder.add_edge("merge_retrieved_info", "filter_metric")

graph_builder.add_edge("filter_table", "add_extra_context")
graph_builder.add_edge("filter_metric", "add_extra_context")

graph_builder.add_edge("add_extra_context", "generate_sql")
graph_builder.add_edge("generate_sql", "validate_sql")
```

What this code expresses is:

```text
START
  -> extract_keywords
  -> recall_column / recall_value / recall_metric
  -> merge_retrieved_info
  -> filter_table / filter_metric
  -> add_extra_context
  -> generate_sql
  -> validate_sql
```

There are two parallel structures here.

The first is that `extract_keywords` is connected to three retrieval routes at the same time. This means field retrieval, field value retrieval, and metric retrieval all depend on keywords, but there is no ordering relationship among them.

The second is that `merge_retrieved_info` is connected to both `filter_table` and `filter_metric` at the same time. Table filtering and metric filtering both depend on the merged context and can also be executed independently.

This is the value of using a graph structure: it can directly express the workflow relationship of "one node splitting into multiple branch routes, which later converge again."

### 6.3 Add conditional edges

After `validate_sql`, the transition is not fixed; instead, the next step must be decided based on the validation result.

```python
graph_builder.add_conditional_edges(
    source="validate_sql",
    path=lambda state: "run_sql" if state["error"] is None else "correct_sql",
    path_map={"run_sql": "run_sql", "correct_sql": "correct_sql"},
)
graph_builder.add_edge("correct_sql", "run_sql")
graph_builder.add_edge("run_sql", END)
```

The business meaning of this code is:

```text
如果 state["error"] is None
  -> 进入 run_sql

如果 state["error"] is not None
  -> 进入 correct_sql
```

At the current stage, SQL has not actually been validated yet, so `validate_sql.py` only temporarily returns:

```python
return {"error": None}
```

The `{"error": None}` here is to allow the conditional edge to correctly proceed to `run_sql`. Later, when SQL validation is actually implemented, `validate_sql` will write real error information based on the validation result, and only then will this conditional branch carry its full business meaning.

Finally, compile the graph.

```python
graph = graph_builder.compile()
```

After compilation, `graph` is the workflow object that can actually be run.

### 6.4 Draw the flowchart to check the structure

After all nodes and edges have been added, you can draw the graph first to check it.

```python
print(graph.get_graph().draw_mermaid())
```

After execution, you will get a piece of `Mermaid` syntax. Put it into a Markdown editor that supports `Mermaid`, and you will be able to see the workflow diagram.

When checking, focus on the following points:

- Whether `START` enters `extract_keywords` first;
- Whether `extract_keywords` is connected to all three retrieval routes at the same time;
- Whether all three retrieval routes converge into `merge_retrieved_info`;
- Whether `merge_retrieved_info` enters both table filtering and metric filtering at the same time;
- whether it splits into `run_sql` and `correct_sql` after `validate_sql`;
- whether `correct_sql` ultimately returns to `run_sql`;
- whether `run_sql` enters `END`.

This step is well worth doing. Once the workflow graph is connected incorrectly, no matter how well the internal logic of the nodes is written later, it will still execute in the wrong order.

## 7. Use streaming output to observe execution progress

The data Q&A agent is not an ordinary function call. It accesses large language models, vector stores, full-text indexes, and databases, and may also go through SQL validation and correction. It is completely normal for a single query to take several seconds or even tens of seconds.

If the frontend gives no feedback the whole time, users cannot tell whether the system is executing normally, stuck on a node, or has already reported an error. Therefore, this project needs to output progress in real time during workflow execution.

LangGraph's streaming capabilities can be found in the official [Streaming](https://docs.langchain.com/oss/python/langgraph/streaming) documentation. If you only care about custom events actively written inside nodes, focus on [Streaming - Custom data](https://docs.langchain.com/oss/python/langgraph/streaming#custom-data).

### 7.1 Write progress inside nodes

In the current nodes, strings are used to demonstrate streaming output first.

```python
writer = runtime.stream_writer
writer("抽取关键词")
```

As long as the workflow execution reaches this node, external callers can receive this message through streaming without waiting for the entire graph to finish executing.

There is also `get_stream_writer()`. It is another way to obtain the writer.

```python
from langgraph.config import get_stream_writer


def node(state: DataAgentState):
    writer = get_stream_writer()
    writer({"type": "progress", "step": "抽取关键词"})
```

Essentially, both approaches obtain the same thing: **a writer function that can write custom data into the current graph execution stream.**

The current node functions in this project already declare the `runtime` parameter, so using `runtime.stream_writer` directly is more natural. One sentence to remember: as long as the final call is to `writer(...)`, and `stream_mode="custom"` is set when executing the graph, this content can be received externally through streaming.

When actually connecting to the frontend later, the strings can be replaced with a unified event protocol.

```python
writer({"type": "progress", "step": "生成SQL", "status": "running"})
```

This chapter first verifies the mechanism; the formal frontend and backend event protocol will be organized later.

### 7.2 Use astream to receive streaming output

If you only need to execute a graph normally, you can use a method similar to `invoke`. However, normal invocation usually only returns the final result after the entire graph finishes, and cannot access the content written by intermediate nodes in real time.

This project needs real-time progress output, so it uses `astream(...)`.

```python
async for chunk in graph.astream(
    input=state,
    context=context,
    stream_mode="custom",
):
    print(chunk)
```

At the current stage, `DataAgentState` and `DataAgentContext` are still empty structures, so pass empty objects directly during testing.

```python
state = DataAgentState()
context = DataAgentContext()
```

`stream_mode="custom"` means that it only receives custom content written inside nodes through `stream_writer`.

For now, remember these common streaming modes:

| Mode       | Meaning                              |
| ---------- | ------------------------------------- |
| `values`   | Output a complete state snapshot after each node executes        |
| `updates`  | Output only the state updated by this node after each node executes  |
| `custom`   | Output custom data written by `stream_writer` |
| `messages` | Output tokens generated during large language model generation          |
| `debug`    | Output debugging information                          |

The current project mainly focuses on frontend progress display, so it uses `custom`.
