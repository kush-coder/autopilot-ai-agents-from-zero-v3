## 1. Chapter Introduction

### 1.1 Project Introduction

"Shopkeeper Data Q&A" is an agent project for enterprise data analysis scenarios. The problem it solves is very clear: allow users to obtain desired analysis results from a data warehouse through chat-like interactions without writing SQL by hand.

If you are a developer, product manager, operations staff, or even a business stakeholder, you will usually encounter a situation like this:

- I want to know the total sales amount for North China.
- I want to see which products have the highest sales for each brand.
- I want to calculate the total order amount for male users.

These questions are essentially not "chat questions" but rather **data query questions**. Traditional approaches usually require developers or data analysts who know SQL to complete them; what "Shopkeeper Data Q&A" aims to do is automatically convert "natural language questions" into "executable SQL queries" and then return the query results to the user.

In one sentence, this project is a typical `NL2SQL` agent project. `NL2SQL` means: `Natural Language to SQL`, that is, "natural language to SQL." The user is only responsible for asking questions, while the system uses a large language model to understand the question and generate SQL, then executes the query against a database or data warehouse, and finally returns the results to the user.

**One-sentence takeaway:** What "Shopkeeper Data Q&A" does is translate "questions humans can understand" into "SQL that a database can execute."

## 2. Background of the Data Q&A Project

### 2.1 Why Enterprises Need a "Data Q&A" System

Enterprises generate large amounts of data every day. Taking e-commerce as an example, many key user behaviors on the platform are accumulated as data, such as:

- Which products were browsed and favorited
- Which products were added to the cart and ultimately ordered
- How much was paid, and which region the user came from and what user category they belong to

This data is initially stored to support the business system itself. For example:

- Orders need to be saved so that users can view their order records later
- Shopping carts need to be saved so that users can see previously added items the next time they open the app
- User information needs to be saved so that the system can identify who the current user is

But the value of data clearly goes beyond just "keeping the business running."

Once data accumulates to a certain scale, we also want to perform further analysis based on this data, for example:

- Which region has higher sales
- Which user groups are more likely to make purchases, and analyze user preferences
- Which brand has performed best recently

These questions no longer belong to daily business operations but fall within the scope of data analysis and business decision-making. The fundamental purpose of an enterprise building a "data Q&A" system is to lower the barrier to data analysis and allow more people to use data directly.

## 3. Data Warehouse Fundamentals

Before formally looking at fact tables and dimension tables, let's first put the relationships between several data layers into a single diagram. The business database is responsible for supporting the operation of transaction systems, the teaching data warehouse is responsible for handling analytical queries, and the metadata knowledge base organizes "which tables, fields, metrics, and values exist" for use by the data Q&A agent.

![Relationships among the business database, teaching data warehouse, metadata knowledge base, and data Q&A agent](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/1/1-3-0-1.svg)

### 3.1 Why Not Directly Query the Business Database

You might ask: since business data is already stored in a database, why not query the business database directly instead of building a separate "data warehouse"? The reason is simple: the goals of business databases and analytical queries are not the same.

The core task of a business database is to support the stable operation of online business. It is more concerned with the following three things: placing orders quickly, making payments quickly, and querying order details quickly.

Analytical queries, on the other hand, usually have the following characteristics: they need to scan large amounts of data and perform aggregate calculations, such as `sum`, `count`, `avg`; they often require multi-table joins, grouping, and sorting; and they are heavier queries with higher consumption of computing resources.

If a large number of analytical SQL queries are run directly on the business database, they can cause obvious problems: increased database load; slower online API responses; and in severe cases, even impact normal business operations.

Therefore, in real enterprise environments, business data is usually synchronized to a system specifically designed for analysis, and that system is the **data warehouse**.

### 3.2 What Is a Data Warehouse

You can first think of a "data warehouse" as a large warehouse specifically used to store analytical data.

It has three key characteristics:

1. It stores large amounts of historical data from business systems.
2. It mainly serves statistical analysis rather than directly serving online transactions.
3. Its data organization is usually redesigned for "analytical convenience."

This means that a data warehouse is not simply a copy of the **business database** moved over unchanged; instead, data is organized, modeled, and processed during synchronization to make subsequent analysis more efficient and clearer.

In the big data ecosystem, there are many common implementations of data warehouses, such as `Hive`. You can first understand `Hive` as an analytical engine designed for data warehouse scenarios. On the surface, it also lets us write SQL, but underneath, it converts those SQL statements into distributed computing tasks and hands them over to a big data cluster for execution, thereby handling larger-scale analysis tasks.

However, this tutorial will not actually deploy `Hive`. The reason is simple: it usually also depends on big data infrastructure such as `Hadoop`, which requires a heavy environment. For beginners, it is easy to shift attention to platform setup rather than the data Q&A system itself.

Based on this consideration, the current teaching environment directly uses `MySQL` to simulate a data warehouse scenario. Although the underlying implementation does not actually use `Hive`, the core workflow of the project remains unchanged: **generate SQL, execute SQL, and return analysis results**. This preserves the core ideas of a data Q&A system while keeping the environment complexity within a range more suitable for learning.

Therefore, this project can be understood as: fully experiencing the core design of an enterprise-grade data Q&A system in a more accessible way.

> **Simply put:**
> Data in a data warehouse usually **originates from business databases**, but it is not copied over exactly as-is, one-to-one.
> It is typically **cleaned, organized, and remodeled** according to analytical scenarios.
> **Business databases** mainly support daily business operations, while **data warehouses** mainly serve statistical analysis, data insights, and business decision-making.

### 3.3 Differences Between Business Databases and Data Warehouses

If you have understood the previous sections, you can use the following table for a quick comparison:

| Comparison Item | Business Database | Data Warehouse |
| -------- | -------------------------------- | -------------------------------------------- |
| Main goal | Support daily business operations | Support statistical analysis and business decision-making |
| Common scenarios | Placing orders, payments, order queries, inventory updates | Statistics on sales by region, sales analysis by brand, user profiling |
| Common types | Usually relational databases, such as `MySQL` | Common implementations include `Hive`; in this project, `MySQL` is used to simulate |
| Query characteristics | Many single-record queries, frequent writes, emphasis on high concurrency | Many aggregate calculations, large data scans, many multi-table joins |
| Design focus | Ensure consistency, fast response, stable writes | Convenient statistics, convenient grouping, convenient analysis |
| Data source | Directly from business systems | Usually derived from organized results after synchronization from business systems |
| Modeling approach | More normalized design | More commonly dimensional modeling |

**One-sentence takeaway:** Business databases exist to "run" the business, while data warehouses exist to "use" the data.

### 3.4 Why Data Warehouses Are Better Suited for Analysis

The reason data warehouses are suitable for analysis is not just that they are separated from business databases; more importantly, they usually adopt a modeling approach that is better suited for analysis.

In business databases, table structures often follow normalized relational database design, with the goals of:

- Reducing redundancy
- Ensuring data consistency
- Serving daily business writes and queries

But in analysis scenarios, what we care more about is:

- Whether metrics can be easily calculated
- Whether dimensions can be easily filtered and grouped
- Whether SQL can be written clearly, stably, and maintainably

Therefore, a common modeling approach in data warehouses is called **dimensional modeling**.

Here we can also build a clearer understanding: moving from a business database to a data warehouse usually involves data processing steps such as extraction, cleaning, and transformation, and **modeling**, more precisely, is the step of "redesigning table structures according to analytical requirements."

## 4. Introduction to Dimensional Modeling

### 4.1 Introduction to Dimensional Modeling

Dimensional modeling is a very classic design method in data warehousing. **Simply put, it designs table structures around "which metrics need to be examined when analyzing a business event, and from which perspectives to observe it."**

In this design, tables are usually divided into two major categories: fact tables and dimension tables.

You can first grasp these two core definitions:

- Fact table: records "what happened"
- Dimension table: describes "under what object, time, place, and attributes this event occurred"

### 4.2 Common Modeling Approaches

In enterprise data systems, modeling approaches are not limited to dimensional modeling. Different modeling approaches usually serve different goals.

| Modeling Approach | Main Scenarios | Core Characteristics | Suitable for This Project |
| ----------------------- | -------------------------------- | ------------------------------------------- | ---------------------------------- |
| `ER` modeling / normalized modeling | Business databases, transaction systems | Emphasizes reducing redundancy and ensuring consistency, typically `3NF` design | Not very suitable as the primary model for a data Q&A system |
| Dimensional modeling | Data warehouses, report analysis, BI, data Q&A systems | Splits tables into fact tables and dimension tables, with a clear query approach | **Most suitable for this project** |
| `Data Vault` modeling | Enterprise data warehouse foundations, complex multi-source integration | Emphasizes traceability, scalability, and ease of continuously integrating new data | More suitable for foundational construction, not suitable as an introductory mainline |
| Wide table modeling / denormalized modeling | Fixed reports, high-frequency analytical queries | Flattens commonly used fields as much as possible in advance to reduce `join` during queries | Can be used as a supplementary method, but not the focus of this project |

It is easier to remember the relationship among them in one sentence: **business databases more commonly use ER/normalized modeling, analytical scenarios more commonly use dimensional modeling, and large enterprise data warehouse foundations sometimes also use Data Vault modeling.**

The reason this tutorial focuses on dimensional modeling is that "Shopkeeper Data Q&A" needs to solve the problem of "how to perform statistical analysis and generate SQL more naturally." For this goal, dimensional modeling is the most intuitive and serves as the best entry-level approach for analytical queries.

### 4.3 Explanation of the Data Warehouse Model in the Current Project

The following diagram shows an example of the fact table and dimension tables in the current project after the data warehouse adopts dimensional modeling. You can use this simplified diagram to understand the relationships between them:

![Star schema model of the Shopkeeper Data Q&A teaching data warehouse: the fact table fact_order and the dimension tables dim_customer, dim_product, dim_region, and dim_date](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/1/1-4-2-1.png)

In the teaching environment for this project, we use one fact table `fact_order` and four dimension tables `dim_product`, `dim_customer`, `dim_region`, and `dim_date` to simulate a simplified e-commerce data warehouse.

To make this diagram easier to understand, here are two legend explanations:

- **Key icon**: indicates that the field is a **primary key**, used to uniquely identify a record in the table
- **Red dot**: indicates that the field is a **key dimension field**, typically used as a filter condition or grouping field. The values of these fields will also be examined more closely later.

If we break this model down by field roles, it can be understood as follows:

- `fact_order` (fact table, order information): `order_id` is the primary key; `customer_id`, `product_id`, `date_id`, and `region_id` are foreign keys; `order_quantity` and `order_amount` are measure fields
- `dim_product` (dimension table, product information): `product_id` is the primary key; `product_name`, `category`, and `brand` are dimension fields
- `dim_customer` (dimension table, customer information): `customer_id` is the primary key; `customer_name`, `gender`, and `member_level` are dimension fields
- `dim_region` (dimension table, region information): `region_id` is the primary key; `province`, `region_name`, and `country` are dimension fields
- `dim_date` (dimension table, time information): `date_id` is the primary key; `year`, `quarter`, `month`, and `day` are dimension fields

**A dimension table usually consists of “1 primary key + multiple dimension fields,” while a fact table usually consists of “1 primary key + multiple foreign keys + multiple measure fields.”**

Among them, `fact_order` is the core fact table. It records the business event of "placing an order." Each row corresponds to one order action and contains both the foreign keys that link to each dimension and the numeric fields that can be aggregated, for example:

- Four foreign keys: `customer_id`, `product_id`, `region_id`, and `date_id`, which are used to associate with the customer, product, region, and date dimensions respectively
- One quantity field: `order_quantity`, representing how many items were purchased in this order
- One amount field: `order_amount`, representing the total amount of this order

Numeric fields like `order_quantity` and `order_amount` here are usually also called measures. They are exactly the objects most often aggregated and calculated during later statistical analysis.

The role of dimension tables is to provide supplementary descriptive information. For example, the `dim_product` table is used to describe product names, categories, and brands; the `dim_customer` table is used to describe customer names, genders, and membership levels; the `dim_region` table is used to describe provinces, regions, and countries; and the `dim_date` table is used to describe time attributes such as year, quarter, month, and day.

One more point needs special emphasis here: the model in the current tutorial is a simplified data warehouse example for teaching purposes. In a real enterprise data warehouse, there is usually more than one fact table. Business events in an enterprise are often not limited to just "placing an order"; they may also include adding to cart, payment, order returns, favorites, browsing, and many other behaviors. Generally speaking, each core business event may correspond to an independent fact table.

In other words, what is commonly seen in a real data warehouse is often:

- Multiple fact tables, each recording different types of business events
- These fact tables sharing some of the same dimension tables
- Dimensions such as users, products, regions, and time often being reused across multiple fact tables

For example, an order fact table, an add-to-cart fact table, and a return fact table may all be associated with the same customer dimension table, the same product dimension table, the same region dimension table, and the same date dimension table. The benefit of this design is that different business events can be counted separately, while the analytical perspectives used to observe these events remain unified.

In this tutorial, however, to help everyone learn the core ideas clearly first, we have kept only one `fact_order` fact table and four commonly used dimension tables. Although the model is simplified, it is already sufficient to help us understand the core analytical logic of an intelligent data Q&A system.

### 4.5 Understanding Fact Tables and Dimension Tables with a Few Questions

Suppose we want to ask the following questions: What are the total sales for each region? What are the total sales for each brand? What is the total order amount for male users?

You will find that although these questions look different on the surface, the approach to writing SQL for them is very similar:

1. First find the fact table that carries the core metric, such as `fact_order`
2. Then, based on the analysis dimension, join the corresponding dimension table
3. Finally, perform filtering, grouping, and aggregation

For example:

- To calculate sales by region, join `dim_region`
- To calculate sales by brand, join `dim_product`
- To calculate the total order amount for male users, join `dim_customer`

If you want to quickly grasp the commonalities among these three questions, you can also look at the following summary table first:

| Question             | Fact table       | Dimension table         | Join field                                            | Statistic field                  | Aggregation method |
| ---------------- | ------------ | -------------- | --------------------------------------------------- | ------------------------- | -------- |
| Total sales by region   | `fact_order` | `dim_region`   | `fact_order.region_id = dim_region.region_id`       | `fact_order.order_amount` | `sum`    |
| Total sales by brand   | `fact_order` | `dim_product`  | `fact_order.product_id = dim_product.product_id`    | `fact_order.order_amount` | `sum`    |
| Total order amount for male users | `fact_order` | `dim_customer` | `fact_order.customer_id = dim_customer.customer_id` | `fact_order.order_amount` | `sum`    |

If we refer back to the diagram above, these questions can be further broken down into the following query approaches:

- **What are the total sales for each region?**

First, take the order amount field `order_amount` from `fact_order`, then join the region dimension table `dim_region` through `fact_order.region_id = dim_region.region_id`, group by `dim_region.region_name`, and finally apply the `sum` aggregation to `fact_order.order_amount`.

- **What are the total sales for each brand?**

This question follows exactly the same approach as the previous one, except that the analysis dimension changes from "region" to "brand." Therefore, we still start from `fact_order`, use `fact_order.product_id = dim_product.product_id` to join the product dimension table `dim_product`, group by `dim_product.brand`, and then apply the `sum` aggregation to `fact_order.order_amount`.

- **What is the total order amount for male users?**

The key point of this question is that "male users" is a filter condition rather than a grouping dimension. Therefore, we still start from `fact_order`, join the customer dimension table `dim_customer` through `fact_order.customer_id = dim_customer.customer_id`, then use `dim_customer.gender = '男'` as the filter condition, and finally apply the `sum` aggregation to `fact_order.order_amount`.

If future questions also include time conditions, such as "Count the total sales by region in 2024", then simply join `dim_date` on top of the existing model. After joining through `fact_order.date_id = dim_date.date_id`, use `dim_date.year = 2024` as the filter condition.

This is the value of dimensional modeling: it makes the structure of analytical SQL more stable, the approach more consistent, and it is also more suitable for agents to understand and generate.

If the above example is compressed further into a general template, most analytical SQL can actually be understood using the following approach:

```sql
select 维度字段, 聚合函数(度量字段)
from 事实表
join 维度表 on 事实表.外键 = 维度表.主键
where 过滤条件
group by 维度字段
```

In Shopkeeper Data Q&A, the large language model ultimately does something similar: first determine **which table is the fact table**, **which tables are dimension tables**, and **which fields the filter conditions fall on**, then organize these relationships into SQL.

## 5. Project Positioning

### 5.1 What Shopkeeper Data Q&A Mainly Does

After understanding data warehousing and dimensional modeling, the core goals of Shopkeeper Data Q&A become much clearer.

Many people, when first encountering `NL2SQL`, naturally think of the most direct approach: give the user's question directly to the model, along with a prompt such as "Please convert this question into SQL", and let the model generate the query on its own.

This idea sounds natural, but in real projects it is usually not enough. The reason is simple: the model itself does not know which tables exist in your current data warehouse, what fields each table contains, how fields are related, which fields are dimensions, and which are measures. Without this context, it is difficult for it to generate correct SQL reliably.

Can we then simply stuff the table structures and field information of the entire data warehouse into the prompt at once and hand it to the model? This looks like a solution, but in practice it also has obvious problems:

- Data warehouses often contain many tables and many fields, so the prompt can easily become too long
- The context length of a large language model is limited, and too many tables and fields can easily exceed the limit
- Even if the limit is not exceeded, too much irrelevant information can interfere with the model's judgment and slow down response time

Therefore, the truly viable approach is not to "give all tables to the model", but to first build a **metadata knowledge base** for the **data warehouse**, then retrieve the most relevant tables, fields, field values, and metric definitions based on the user's question, and finally provide that context to the model to generate SQL.

If you do not yet fully understand "what exactly a metadata knowledge base is, how it relates to the data warehouse, and how the system actually retrieves information", that is fine. For now, it is enough to grasp the main thread: **the data warehouse is responsible for storing analytical data, the metadata knowledge base is responsible for helping the agent understand that data, and the agent then performs data queries based on both.**

The more detailed system architecture, synchronization process, retrieval mechanism, and execution flow will be explained in the next chapter [Chapter 2: Overall Project Architecture and Agent Workflow](2-%E9%A1%B9%E7%9B%AE%E6%95%B4%E4%BD%93%E6%9E%B6%E6%9E%84%E4%B8%8E%E6%99%BA%E8%83%BD%E4%BD%93%E6%B5%81%E7%A8%8B.md).

For example, if a user inputs:

- Count the total sales in North China
- Count the top three products by sales volume in each region

What the system ultimately needs to achieve is not a vague "explanation of the question", but actually generating executable SQL and providing reliable results. This is the biggest difference between a "data query agent" and an ordinary chatbot.

It can also be viewed as a **retrieve relevant metadata first, then generate SQL** approach. When we discuss the system architecture later, we will formally expand on its relationship with the `RAG` approach. For this reason, the subsequent focus of this project is not just "how to call a large language model", but more importantly "how to organize, retrieve, and utilize metadata well".

### 5.2 A Minimal Understandable Data Query Pipeline

If you want to remember the entire project in one sentence first, you can remember the following minimal pipeline:

1. The user first asks a natural language question, such as "Count the total sales in North China".
2. The system first finds the fields, field values, and metric definitions most relevant to this question from the metadata knowledge base.
3. The large language model generates SQL based on this context.
4. The system first validates the SQL and automatically corrects it if necessary.
5. After the SQL passes validation, it is actually executed, and the query results are returned to the user.

This minimal pipeline is exactly the main thread of the remaining chapters of the whole project: **the user asks a question, the system first finds relevant knowledge, then generates SQL, and finally executes the query.**
