# 3.9 - Dify Case Study: Product Review Analysis

---

## Case Study Overview

### Nodes Used

| Node Name         | Type / Capability          | Purpose                                                                 |
| ---------------- | -------------------------- | ----------------------------------------------------------------------- |
| **Start**        | Chat flow input            | Receives a CSV file uploaded by the user (product review data) as the data source for the subsequent flow. |
| **Document Extractor** | Transform → Document Extractor | Parses the uploaded CSV document and outputs a document object usable by downstream nodes. |
| **Extract Text** | Transform → Code Execution | Extracts the raw text content from the document for segmentation and metadata extraction. |
| **Segment Metadata** | Transform → Code Execution | Segments the text by table/row structure to prepare input for "Extract Metadata." |
| **Extract Metadata** | LLM + Structured Output | Extracts fields such as product title, ASIN, link, and star rating statistics from the segmented results to obtain metadata. |
| **Analyze and Suggest** | LLM (e.g., DeepSeek) | Based on negative review content, analyzes and provides suggestions from four dimensions: the product itself, store service, logistics, and price. |
| **Analyzing Prompt** | Direct Reply | Outputs intermediate prompts such as "Analyzing..." to the user during the analysis process. |
| **Aggregate Generated Results** | Code Node | Merges metadata and the text from "Analyze and Suggest" into a unified `final_result` structure. |
| **Organize Output** | LLM | Organizes output according to a fixed Markdown template (images, links, review count, analysis, suggestions). |
| **Output Final Result** | Direct Reply | Returns the organized Markdown report to the user. |

### Technical Highlights

- **Chatflow Selection**: This case study requires multiple outputs to the user (such as "Analyzing..." and the final report), so Chatflow is used instead of Workflow; Chatflow supports inserting "Direct Reply" nodes anywhere in the flow and has no end-node restrictions.
- **File Input**: The Start node is configured to accept `input_file` (CSV). After the user uploads product review data, it triggers the entire flow.
- **Document and Text Processing Pipeline**: Document Extractor → Extract Text → Segment Metadata → Extract Metadata, which converts the CSV into structured metadata (including product_title, asin, star rating statistics, etc.).
- **LLM Analysis**: The "Analyze and Suggest" node uses a system prompt to constrain the role (Taobao product analyst), analysis principles (objective, systematic, solution-oriented), analysis dimensions (product/service/logistics/price), and output format (product analysis + product selection improvement suggestions), ensuring structured and reusable output.
- **Code Node**: During the aggregation stage, Python is used to merge `meta_data` and `analysis_and_suggestion` into `final_result`, making it easier for the subsequent "Organize Output" and "Output Final Result" nodes to use.
- **Structured Presentation**: The "Organize Output" node calls the LLM again to format the content according to a fixed Markdown template (image, link, count, analysis, suggestions), which is ultimately presented to the user through "Output Final Result."

### Workflow Overview

```
开始(input_file: CSV)
    ↓
文档提取器 → 解析上传文档
    ↓
提取文本 → 得到原始文本
    ↓
切分元数据 → 按表结构切分
    ↓
提取元数据 → 大模型抽取 product_title、asin、星级等 → meta_data
    ↓
直接回复「正在分析提示」
    ↓
分析和建议(meta_data 对应评论文本) → 四维度分析 + 选品建议 → analysis_and_suggestion
    ↓
汇总生成结果(代码：meta_data + analysis_and_suggestion) → final_result
    ↓
整理输出(大模型：按 Markdown 模板格式化) → 格式化报告
    ↓
输出最终结果(直接回复) → 返回用户
```

## 1. Configuration and Single-Node Testing

### 1.1 Comparing Workflow and Chatflow

On the Dify platform, the differences between Chatflow and Workflow are as follows:

| Feature Dimension | Chatflow                                                        | Workflow                                                        |
| :---------------- | :-------------------------------------------------------------- | :-------------------------------------------------------------- |
| Core Goal         | `实时交互`, focusing on natural language dialogue and contextual understanding | `批量处理与自动化`, focusing on executing complex logic efficiently and reliably |
| Interaction Mode  | `多轮对话`, supports multiple user inputs, and the AI can follow up with questions or adjust responses | `单次执行`, input is completed in one go, and the flow executes in the preset node order before outputting the final result |
| Context Memory    | ✅ `支持`. Built-in conversation memory (`sys.conversation_id`) can associate historical conversations | ❌ `不支持`. Stateless execution, does not retain conversation history; each execution is independent |
| Output Method     | Supports streaming output (results are displayed progressively) | Results are given all at once after the entire flow has finished executing |
| Trigger Mechanism | Mainly triggered by `用户实时输入`                            | Supports triggering via `定时任务、API事件、文件上传`, among other methods |
| Typical Scenarios | Customer service inquiries, educational consultation, creative collaboration | Report generation, data cleaning, batch API calls |

The design goals and use cases of the two are fundamentally different. In short, **Chatflow is specialized for interactive scenarios that require "multi-turn conversations," while Workflow excels at handling "one-time automation" tasks**.

**A Deeper Understanding of Chatflow:**

Chatflow can be understood as an **"intelligent brain" designed specifically for conversations**. Its core value lies in handling complex tasks that require back-and-forth communication.

- `上下文关联`: When a user first asks "Recommend a laptop" and then adds "with long battery life," Chatflow understands that "long battery life" is a follow-up to "laptop" and can give a precise recommendation.

- `动态调整`: In creative writing, users can ask the AI to adjust style, word count, or plot direction, and Chatflow can dynamically optimize based on the previous conversation content.

Therefore, if your application scenario requires human-like back-and-forth communication with users and remembering conversation history, you should choose Chatflow.

**A Deeper Understanding of Workflow:**

Workflow is more like a **precise and reliable "automated factory assembly line"**. It excels at breaking down complex tasks into a series of clear steps and then executing them automatically.

- `逻辑严谨`: Through code nodes, conditional branches, loops, and other nodes, very complex business logic can be built, such as "If the order amount is greater than 1000 yuan, transfer to manual review; otherwise, automatically approve."

- `无需人工干预`: Once trigger conditions are set (such as 2:00 AM every day), it can run automatically to complete repetitive tasks like batch generation of daily reports and syncing inventory data.

Therefore, when you need to process batch data, execute scheduled tasks, or build stable and reliable backend automation flows, Workflow is the best choice.

**How to Choose: A Four-Step Decision Method**

Facing your business requirements, you can quickly make a decision by answering the following questions:

1. **Does it require multiple user inputs?** Yes -> Choose Chatflow.
   - For example: Legal consultation often requires asking about case details multiple times.
2. **Is it a batch processing task?** Yes -> Choose Workflow.
   - For example: Processing the upload of 1000 product information entries at once.
3. **Does the result need to be displayed step by step?** Yes -> Choose Chatflow.
   - For example: First showing a plan outline, then showing details, allowing users to interrupt at any time.
4. **Does it require scheduled or event-based triggering?** Yes -> Choose Workflow.
   - For example: Automatically generating sales reports every day.

**Advanced Technique: Using Them Together**

In complex business systems, Chatflow and Workflow can work together to form more powerful solutions. For example:

- **Customer Service System**: The frontend uses Chatflow to receive users and understand their problems; when a ticket needs to be created, it automatically triggers the backend Workflow to dispatch the ticket to the corresponding department and send email notifications.
- **Data Analysis Assistant**: Users ask about business data through Chatflow. After Chatflow collects the requirements, it triggers a Workflow to execute complex data queries and analysis in the background, and then returns the results to Chatflow, which presents them to the user in natural language.

### 1.2 Creating a Chatflow

Dify's Workflow can only receive user input once (Start node) and output once (End node).

This project requires multiple outputs (printing logs), and only Chatflow can satisfy such a requirement. The latter's `直接回复` node can be added anywhere after the workflow Start node to output content via `直接回复` nodes. In addition, Chatflow does not have an `结束` node.

#### 1.2.1 Can This Case Be Changed to Workflow?

**Yes.** Looking at the chain of "Upload CSV → Parse → Extract Metadata → Analyze and Suggest → Aggregate → Organize Output," the logic is **single-pass and linear**, with no multi-turn dialogue, so it can definitely run with Workflow and output the same final report at the **End node** as it does now.

**What problems would arise?** As explained earlier in the document: Workflow can only have **one input (Start node) and one output (End node)**, and there is no mechanism to "send messages to the user in the middle of the flow"; Chatflow, on the other hand, supports inserting **"Direct Reply"** nodes anywhere in the flow and does not have the restriction of "there must be only one end node." Therefore, after changing to Workflow:

| Dimension                       | Chatflow (current)                       | After Changing to Workflow             |
| ------------------------------- | ---------------------------------------- | -------------------------------------- |
| **Final Report**                | ✅ Available                             | ✅ Available (output at End node)      |
| **Intermediate "Analyzing..." Prompt** | ✅ Available (Direct Reply node)     | ❌ **Not available**; users can only see the result after everything finishes running |
| **Output Timing**               | Can be split into two times: first "Analyzing...", then the final report | Only once: the final result when the flow ends |

Conclusion: **Functionally, it can meet the requirements** (the same analysis results and report), but it will **lose intermediate progress prompts like "Analyzing..."**, and users will feel like "there is no feedback for a long time after uploading, and then the result comes out all at once."

**Suggestion**: If you do not mind the absence of intermediate prompts, you can change it to Workflow, which has simpler logic and is easier to invoke through **API, scheduled tasks, batch triggers**, and other methods. If you want to keep the "Analyzing..." experience, continue using Chatflow.

#### 1.5.1 Configuration

The code is as follows:

```python
def main(text_arr: list):
    text = ''
    if isinstance(text_arr, list):
        text = text_arr[0]
    else:
        text = text_arr
    return {
        "text": text
    }
```

The document extractor sometimes outputs a string, and sometimes a string array with only one element; this node's purpose is to uniformly process it into a single string when the output is a string array.

**Why do the input and output content look the same in testing?** Because in this test, the document extractor happened to return a **string** (not an array), so the code takes the `else` branch and returns it directly via `text = text_arr`, leaving the string content unchanged. The significance of this step lies in: ① **Type unification**: regardless of whether the upstream provides a string or a single-element array, this node's output is **guaranteed to be a string**, so the downstream "Split Metadata" only needs to handle one type; ② **Output variable name unification**: downstream consumes this node's `text`, rather than the document extractor's potentially varying output structure. If in a particular run the document extractor outputs a `["..."]` array, this node will take `[0]` and output it, at which point the input (array) and output (string) will differ in type and form.

### 1.6 Split Metadata

#### 1.6.1 Configuration

This is a code node whose purpose is to separate the two sections of text, "product metadata" and "review table", and keep only the metadata section for the next step "Extract Metadata" to perform structured extraction with an LLM.

The entire content output by the upstream "Extract Text" roughly consists of: at the beginning, product information (product_title, asin, product_link, image_url, crawl time, star rating statistics, etc.), followed by the entire review table starting from the header `| rating | title | content | date | verified |`. This node uses the fixed delimiter `| rating |` (i.e., the review table header) to perform a `split` and takes the **first half** `text_arr[0]` as `meta_str`, so that downstream only needs to process the "pure metadata" text, avoiding stuffing large amounts of review text into the "Extract Metadata" LLM, which both saves tokens and reduces interference.

![Product Review Analysis Case Operation Screenshot](../../../../images/3.9/3.9-1-6-1.png)

The code is as follows

```python
def main(text: str):
    text_arr = text.split(r"| rating |")
    return {
        "meta_str": text_arr[0],
    }
```
